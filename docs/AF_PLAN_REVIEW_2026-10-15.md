## 재현한 문제와 수정 우선순위

### R1 · P1 — 모집을 닫으면 미종료 행사의 주최자가 탈퇴할 수 있음

위치: [safety-service.ts:469](../src/server/safety-service.ts#L469), `withdraw()`의 주최 행사 검사.

조건과 재현:

1. 시작이 내일인 모집글을 만들고 참가자를 확정한다.
2. 정상 모집 설정 API의 서비스로 `open=false`를 적용한다.
3. 주최자가 회원 탈퇴를 실행한다.
4. 탈퇴가 성공하고 주최자는 `closed`가 되지만, 미래 행사와 확정 신청은 그대로 남는다.

원인은 주최 책임 확인을 `event_settings.open=true`에 묶은 것이다. 모집 마감과 행사 종료는 서로 다른 상태인데, 닫힌 모집은 미종료여도 검사에서 빠진다. 기본 주최자만 관리하는 행사라면 주최자는 이후 인증·관리·공지·취소 업무를 수행할 수 없다.

메모리 PostgreSQL에 전체 마이그레이션을 적용한 격리 재현에서 `futureEventRemains=true`, `confirmedParticipantRemains=true`, `hostClosed=true`, `hostCannotAct=true`를 확인했다.

수정 방향: 모집 상태와 별도로 미종료 행사·유효 참가·환불 책임을 확인하고, 정리가 끝나기 전 탈퇴를 제한한다. 모집 마감, 진행 중, 취소 후 미처리 환불, 정상 종료의 경계를 회귀 검사에 추가한다.

### R2 · P2 — 미참석으로 정정된 QR 참가자가 인증 후기를 등록할 수 있음

위치: [event-operations-service.ts:392](../src/server/event-operations-service.ts#L392), 같은 파일의 `canReview` 351행. 비교: [event-aftercare-service.ts:190](../src/server/event-aftercare-service.ts#L190).

QR 입장과 확정 신청이 있지만 담당자가 전적을 `no_show`로 정정한 경우, 종료 후 할 일에서는 후기 대상에서 제외된다. 반면 후기 조회/등록은 QR와 `confirmed`만 확인하므로 `canReview=true`가 되고 실제 등록도 성공한다.

격리 재현 결과: `aftercareItems=0`, `canReview=true`, `writeAccepted=true`, `persistedReviews=1`. 현재 출석 정정과 인증 후기 기준이 어긋난다.

수정 방향: 할 일·후기 조회·후기 등록·후기 집계에 같은 현재 참가 자격 정책을 적용한다. 미참석 정정과 복구, 주최자 제외, 실제 참가 후 금전 환불과의 구분도 함께 검증한다.

### R3 · P2 — 크루 양도 후 과거 계정 경고의 이의신청 권한이 새 리더에게 넘어감

위치: [appeal-service.ts:43](../src/server/appeal-service.ts#L43), [0062_member_appeal_integrity.sql:7](../drizzle/0062_member_appeal_integrity.sql#L7). 조치 저장: `safety-service.ts:323`.

실제 크루 생성→가입 승인→크루 주최자 경고→원대상 이의신청→정상 리더 양도로 재현했다. 원래 경고받은 회원의 조치는 목록에서 사라지고 추가 의견은 `NOT_FOUND`로 실패한다. 경고받지 않은 새 리더는 그 조치를 조회하고 새 신청을 만들 수 있다.

이의신청 소유권이 조치 당시의 회원이 아니라 현재 `crews.owner_id`를 따라가기 때문이다. 원래 이의신청 원문이 새 리더에게 그대로 공개되는 현상까지 확인한 것은 아니다. 확인한 결함은 과거 계정 조치의 귀속·조회·접수 권한이다.

수정 방향: 조치 당시 대상 회원을 불변 정보로 보존하고 서비스와 DB 가드를 같은 기준으로 바꾼다. 이전 데이터는 현재 소유자에게 일괄 귀속하지 말고 당시 근거로 처리한다. 기존 마이그레이션을 고치는 대신 새 마이그레이션으로 보완해야 한다.

### R4 · P2 — 기기 시계가 빠르면 인기글 버튼을 눌러도 조회가 실패함

위치: [sliper-community.tsx:776](../src/components/sliper-community.tsx#L776), 같은 패턴 340·658·693·782행. 서버 검사: [community-service.ts:157](../src/server/community-service.ts#L157).

인기 진입·기간 변경·지금 기준으로 새로 보기는 브라우저 `new Date()`를 `rankingAt`으로 전달한다. 서버는 자신의 현재 시각보다 조금이라도 미래인 값을 거절한다. 기기 시계가 60초 빠른 상태에서는 클릭할 때마다 `400 VALIDATION`이 반복된다.

실제 서비스 함수에 DB 접근 금지 Proxy를 전달한 재현에서 `actualErrorCode=VALIDATION`, DB·네트워크 요청 0회를 확인했다.

수정 방향: 첫 조회와 새로보기는 서버가 기준 시각을 정하게 하고, 서버가 반환한 값을 이후 페이지에서 고정 재사용한다. 클라이언트 시계 오차와 한국 날짜/주 경계를 함께 검사한다.

### R5 · P2 — 주제 연결 표시와 실제 검색이 Unicode 공백에서 달라짐

위치: [topic-service.ts:30](../src/server/topic-service.ts#L30). 클라이언트 정규화: [topics.ts:61](../src/domain/topics.ts#L61).

`#미션\u00A0레이스`처럼 내부에 NBSP가 들어간 정상 입력 태그는 JS의 `\s`에서 공백이 제거되어 주제가 연결된 것으로 표시된다. PostgreSQL의 `[[:space:]]`는 같은 문자를 남겨 주제 목록·개수에서 해당 글/자료를 누락시킨다. U+2003과 U+FEFF도 재현했다.

실제 로컬 PostgreSQL의 읽기 전용 트랜잭션과 SELECT에서 UI 일치 true / DB 일치 false를 확인했다. 기존 태그·DB를 수정하지 않았다.

수정 방향: JS와 SQL이 동일한 Unicode 공백 규칙을 사용하도록 통일하고, 글/자료·관련 링크·필터·개수가 일치하는지 검사한다.

### 태그와 반응의 같은 행 배치

### 같은 Wi-Fi에서 개발 서버 열기

`npm run dev:lan`은 현재 연결된 Wi-Fi/이더넷의 실제 사설 IPv4를 고른다. Wi-Fi를 우선하고 가상 어댑터·루프백·공개 주소를 제외하며 오래된 DHCP 주소를 그대로 재사용하지 않는다. 감지한 주소는 Next 자식 프로세스의 `SLIPER_LAN_HOST`에만 전달하고 `.env`나 `.env.local`을 다시 쓰지 않는다.

이 주소는 개발 자산을 허용할 정확한 origin과 로컬 테스트 인증 host 검사에 함께 사용한다. 임의 origin·와일드카드나 LAN에서 고정 회원으로 자동 로그인하는 방식은 허용하지 않는다. 실행기는 격리된 로컬 DB·개발 인증 환경에서만 동작한다.

휴대폰은 같은 Wi-Fi에 연결한 뒤 터미널에 표시되는 휴대폰용 주소로 접속하고 별도로 로그인해야 한다. PC의 `127.0.0.1` 쿠키가 휴대폰에 공유되지는 않는다. HTTP LAN 접속은 보안 컨텍스트가 아니므로 Web Push·카메라 QR 스캔·위치 권한의 브라우저 제한은 유지하며, 해당 기능의 실제 검증에는 HTTPS 환경이 필요하다.

최초 재현 로그는 수정 전 증거로 남긴다. 특히 소스의 원래 SQL과 일치하는지 검사하는 `.local/af-topic-normalization-review.ts`는 수정 이후 회귀 도구가 아니며, 현재 동작 검증은 정식 주제 테스트를 사용한다.

## F 후속 준비 — DB 실측 점검과 참가자 전용 연락처

Supabase 프로젝트 URL을 받아 Git 제외 `.env.supabase.local`에 URL과 빈 입력 키를 준비했다. 현재 로컬 `.env`를 바꾸지 않았고 원격 DB·Storage·OAuth는 비밀값 입력 전이므로 연결하지 않았다. [입력 안내](SUPABASE_CONNECTION_PREPARATION.md)를 참고한다.

별도 `deploy:db-check`는 명시한 실행 DB에 실제 접속해 읽기 전용 트랜잭션·TLS 관측·실행 역할/소유자 분리·RLS·브라우저 차단·전체 마이그레이션 원장과 파일을 확인한다. 기존 준비 화면/API와 `deploy:check`는 설정 형식 검사로 유지했다. [DB 점검 도구](PRODUCTION_DATABASE_AUDIT.md).

새 도구는 기존 로컬 DB의 `0007_participation_integrity`, `0042_records_integrity` 두 적용 해시가 현재 파일과 다른 것을 발견했다. 적용 순서와 시각은 67개 모두 맞지만 당시 SQL 바이트를 복원하지 못했으므로 엄격한 마이그레이션 감사는 **FAIL**로 유지한다. 관련 함수·트리거·제약의 현재 정의 대조는 일치했고 기존 데이터·해시·이전 SQL을 덮어쓰지 않았다. 테스트가 이 불일치를 정확히 검출하는 것과 DB가 출시 검사를 통과하는 것은 별도다. Supabase 신규 대상의 전체 적용·검증이나 별도 백업/이관 절차가 필요하다.

확정 참가자·지정 담당자만 보는 행사 연락처를 별도 서버 전용 테이블/API로 구현했다. 주최자만 전화·이메일·문의 링크를 명시적으로 등록/수정/공개 중단하고, 대기·취소·환불·숨김·차단·계정 제한을 매번 확인한다. 프로필/공개 문의를 자동 이전하지 않으며 익명 주최자의 신원을 덧붙이지 않는다. 정상 탈퇴와 같은 트랜잭션에서 값을 제거하고 닫힌 모달에도 값을 남기지 않는다. [참가자 전용 연락처](EVENT_PRIVATE_CONTACT.md).

실제 행사 관리/신청 화면의 Chrome 검사에서 Node와 브라우저의 한국어 AM/PM 표기가 달라 hydration이 어긋나는 기존 문제도 발견했다. 환불·행사 시작·신청/결제 시각을 고정 KST 숫자 표시로 통일했고 환불 계산은 유지했다.
