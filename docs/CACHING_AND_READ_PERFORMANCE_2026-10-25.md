# 캐시와 조회 성능 개선

기준: 2026-10-25. 데이터 원본은 Supabase PostgreSQL·비공개 Storage에 유지한다. 아래 캐시는 서버 프로세스 메모리에만 존재하는 임시 사본이며 서버 재시작 때 사라진다. 별도 Redis 서비스·패키지·DB 테이블을 추가하지 않았다.

## 확인한 원인과 개선

홈·이야기·번개의 목록은 매번 페이지 수와 여러 추천 영역, 이미지·영상 메타데이터·반응 집계를 조회했다. 응답에는 개인 반응과 알림도 섞이므로 전체 API/HTML을 공용 CDN에 저장하면 회원 간 정보가 섞일 수 있다. 업로드 이미지는 모든 응답이 no-store였고 파일 다운로드 전 비공개 버킷도 매번 확인했다.

이번에는 공개 목록의 비싼 조회 결과를 짧게 재사용하고, 현재 권한과 개인 반응을 별도로 확인한다. 이미지는 접근 확인 이후 브라우저 재검증과 서버 바이트 캐시를 적용한다.

## 적용 범위

| 대상 | 보관 시간·상한 | 갱신·권한 |
| --- | --- | --- |
| 홈·이야기·번개 공개 목록 | 20초, 공개 조회 캐시 전체 128개/직렬화 데이터 16MiB | 재사용 시 현재 글 상태·수정 버전·운영 숨김 확인, 개인 반응 반영 |
| 홈 추천·오늘/이번 주/이번 달 이야기 | 30초, 위 공개 조회 캐시와 상한 공유 | 한국 날짜를 키에 포함해 날짜 경계 분리, 권한 재확인 |
| 사진 파일 바이트 | 5분, 256개/32MiB | 권한 확인 후 사용, 프로젝트·버킷·종류·파일별 분리, 삭제 시 무효화 |
| 일반 공개 글 첨부 사진의 브라우저 사본 | private, no-cache, must-revalidate | 매 요청 현재 접근 검사 후 ETag가 같으면 304, 본문 재전송 생략 |
| 공식 로고 등 /images 정적 파일 | 1시간, 이후 백그라운드 재검증 허용 | 공개 브랜드 자산만 해당 |
| 참가·회고·행사 기록 사진, 프로필 사진 | 브라우저 no-store | 서버 파일 사본을 재사용해도 매 요청 기존 회원/부모 권한을 확인 |

보관 크기는 캐시 데이터 기준이며 JS 객체·Map·진행 중 요청의 메모리 오버헤드는 별도다. 영상 파일은 바이트 캐시에서 제외했다. 본문 사진은 지연 로딩과 비동기 디코딩을 적용했다.

다음 조회는 공용 목록 캐시를 우회한다: 내 글·북마크·관심 피드·미답변 필터, 검색어, 현재 좌표/거리 검색, 이어 보기 커서, 6페이지 이후. 위치나 개인 조회를 공용 키에 저장하지 않는다. 차단 회원이 있는 사용자는 정확한 목록 수와 페이지 구성을 위해 기존 회원별 조회를 사용한다. 최초 페이지를 공유해도 다음 페이지 커서는 현재 회원에 맞춰 생성한다.

글 상세·댓글·알림·참가/결제·마이페이지·유료 자료 본문과 아카이브 조건 검색은 이번 공용 캐시 대상에 포함하지 않았다. 이 API들의 private/no-store 정책을 유지한다. 공개 목록이라도 최종 API 응답에는 개인 상태가 있으므로 브라우저나 CDN의 공용 응답 캐시로 바꾸지 않는다.

## 정확성과 접근 제어

- 캐시에는 비회원에게 공개되는 목록만 저장한다. 응답마다 복제한 사본에 현재 회원의 좋아요·북마크·본인 글·투표 선택을 반영하므로 공용 사본이 오염되지 않는다.
- 캐시 적중 시 ID로 한 번의 DB 조회를 수행해 삭제/숨김·수정 버전, 현재 작성자 이름, 채택 답변·인증 후기·연결 장소의 공개 상태, 모집 가능 여부를 확인한다. 수정/삭제/숨김이 발견되면 캐시를 버리고 현재 권한으로 다시 조회한다. DB 확인에 실패하면 과거 데이터로 응답하지 않는다.
- 참가 정원·결제·승인 판단은 기존 트랜잭션에서 수행한다. 캐시된 목록으로 정원을 확정하거나 권한을 부여하지 않는다.
- 성공한 글/댓글 등록·수정·삭제·채택·반응·투표·프로필 변경 후 해당 서버의 목록 캐시를 비운다. 조회수 기록·알림 읽음은 전체 캐시를 비우지 않는다. 집계·조회수·새 후보의 표시에는 짧은 TTL만큼 지연이 있을 수 있다.
- 동시에 들어온 동일 조회는 하나의 로딩 Promise를 공유한다. 오래된 로딩이 무효화 후 끝나도 다시 캐시를 채우지 못하게 한다. 실패 결과는 캐시에 저장하지 않는다.
- 사진 GET/HEAD/If-None-Match 모두 **현재 접근 검사 이후** 처리한다. 공개 글 사진은 부모 글 상태·숨김·작성자 차단을 한 DB 문장으로 확인한다. 비공개 기록/회고 사진과 프로필 사진에는 브라우저 ETag를 발급하지 않는다.
- 업로드 UUID와 객체 경로는 변경 불가능하며 교체할 때 새 UUID를 발급한다. 저장소 업로드의 upsert=false를 유지하고 파일 ID/크기로 ETag를 구분한다. Storage 비밀키나 서명 URL을 브라우저 캐시 키에 넣지 않는다.

Supabase Storage 자체의 CDN 제공 여부와 이 앱의 회원 인가 경로는 별개다. 이 프로젝트는 비공개 버킷의 공개 전환이나 권한 검사 없는 직접 URL을 만들지 않았다. 참고: [Supabase Storage CDN](https://supabase.com/docs/guides/storage/cdn/fundamentals).

## 실제 측정

같은 PC에서 실제 Supabase에 연결하고 익명 공개 목록 20개를 조회했다. 최초 연결·개발 서버 컴파일 시간은 비교에서 제외했다. 같은 워커·연결 풀의 반복 조회 3회를 비교한 결과다.

| 구분 | 기존 직접 조회 | 캐시 적중 |
| --- | --- | --- |
| 서비스 조회 중앙값 | 746ms | 471ms |
| 서비스 조회 범위 | 722~969ms | 464~507ms |
| 목록의 DB 문장 수 | 2회 | 1회 |

약 37%의 서비스 조회 시간 감소를 확인했다. 별도 HTTP 검사에서는 공개 목록 969→485ms, 빈 인기 이야기 결과 526→28ms였다. 이는 특정 환경의 소수 측정이며 전체 페이지·로그인 회원·실서비스 부하의 보장값은 아니다. 최초 캐시 채우기는 기존 조회를 수행하고, 비어 있지 않은 결과는 최신 인가를 위해 DB 왕복이 남는다. OAuth·개인 알림·원격 DB 네트워크·개발 모드 컴파일은 별도다.

실제 공개 업로드 사진은 최초 216,472바이트를 반환하고 같은 ETag의 재요청은 304와 0바이트 본문을 반환했다. HEAD에서도 파일 본문을 읽지 않았다. 헤더와 접근 확인 요청은 남아 있으므로 모든 네트워크/DB 사용량이 0이 되는 것은 아니다.

DB 조회 부하와 Storage 다운로드·이미지 전송량을 줄이는 변경이다. 청구 금액 감소율은 실제 방문량·캐시 적중률·사용 요금제에 따라 달라 별도 운영 지표로 확인해야 한다.

## 검증과 파일

- 전체 검사 **1,034개 통과**, 비밀값·서식·타입·Drizzle 검사 통과. 별도 미디어 통합 검사 1개도 통과했다. 최종 운영 빌드와 서버 추적 116개 검사를 통과했고 비밀 설정·워커 의존성 오류는 0개였다.
- 캐시 회귀 11개: 만료, 동일 요청 합치기, 실패 재시도, 용량/LRU 제한, 로딩 중 무효화, 회원별 상태, 숨김/수정/삭제/이름, 차단과 페이지 수, 회원별 커서, 작성 후 갱신, 빈 결과.
- 별도 미디어 통합 검사 1개: 공개 사진 304/HEAD, 따뜻한 사본 이후 숨김·삭제·차단 거부, 미첨부 사진의 업로더 권한·no-store.
- 실제 HTTP 6개 요청과 공개 이미지 GET/304/HEAD, 정적 로고 헤더를 확인했다. Chrome Android 390px에서 목록·상세 열기/닫기·탐색·이야기 이동을 확인했고 페이지 오류/가로 넘침은 0개였다. 검증 브라우저의 변경 API는 차단했다.
- 원본 src/public/drizzle과 격리 빌드 소스가 일치했다. standalone 2,540개 파일에서 비밀 설정 파일·외부 연결·영상 워커 패키지를 발견하지 않았다.
- 주요 코드: `src/server/bounded-cache.ts`, `discovery-cache-store.ts`, `community-queries.ts`, `image-object-cache.ts`, `image-delivery.ts`, `media.ts`, `profile-photos.ts`. RSC와 community 읽기 API가 동일 경계를 사용한다. DB 스키마/마이그레이션 변경 없음.

## 배포·운영 시 유의점

현재 예정된 단일 Ncloud 서버에서 별도 캐시 인스턴스 비용 없이 사용한다. 여러 Node 프로세스/서버로 확장하면 각 프로세스가 별도 캐시를 가진다. 다른 프로세스의 신규 글·집계는 20~30초 TTL 이후 발견하며 기존 글의 숨김/수정/개인 권한은 각 요청의 DB 확인을 거친다. 갱신 간격을 더 엄격히 맞추거나 여러 서버의 적중률을 합쳐야 할 때는 공용 Redis 캐시·변경 신호를 후속 검토한다.

서버 재시작·배포 시에는 캐시를 다시 채운다. RAM이 많다고 보관 시간을 무조건 늘리지 말고 캐시 적중률, DB CPU/응답 시간, Storage 전송량을 함께 확인한다. 첫 이미지 전송량까지 더 줄이려면 작은 썸네일 파생본을 비공개 미디어 권한 경로 안에서 추가하는 방식이 후속이다.
