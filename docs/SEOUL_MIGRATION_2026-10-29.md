1. 이전·무결성 검증

- Sliper 웹·알림·영상 서비스만 잠시 중단해 최종 스냅샷을 확보했다. 같은 서버의 기존 다른 사이트는 계속 HTTP 200으로 응답했다.
- 최종 암호화 백업: `backup_20261029T030934Z_22b98eda67a91a79`. 사전 백업 `backup_20261029T024235Z_35731f4e089f7712`는 별도 로컬 PostgreSQL 복원으로 검증했다.
- 서비스 87개 + Auth 27개 + Drizzle 이력 1개, 총 115개 테이블의 행 개수·행 해시·인덱스·제약조건·RLS 상태가 원본과 일치했다. 기존 회원 ID를 보존했다.
- 검증 시 회원 7명과 공개 글 26개를 확인했다. 샘플·테스트 표시도 기존 데이터 그대로 유지했다.
- 비공개 파일 7개, 총 6,799,517바이트를 복사해 최종 스냅샷의 SHA-256과 모두 일치함을 확인했다.
- 관리형 Auth 스키마의 DDL과 자체 마이그레이션 이력을 덮어쓰지 않았다. 두 프로젝트의 Auth 컬럼과 기본 마이그레이션 이력이 호환되는지 확인했다.
- 데이터 복원은 단일 트랜잭션으로 처리했다. `pg_restore --schema` 필터가 SCHEMA 생성문을 포함하지 않은 문제는 첫 복원의 전체 롤백 후 명시적인 private 스키마 생성으로 수정했다. 임시 복호화 파일은 원본 해시가 일치할 때만 재사용했으며, 스냅샷 비교 오류는 그대로 실패하도록 유지했다.

2. 실제 운영 연결과 설정

새 프로젝트만 담은 `/etc/sliper/seoul.env`를 생성했고, 다음 Sliper 전용 systemd drop-in이 이를 읽는다.

- `/etc/systemd/system/sliper-web.service.d/30-seoul.conf`
- `/etc/systemd/system/sliper-notifications.service.d/30-seoul.conf`
- `/etc/systemd/system/sliper-video.service.d/30-seoul.conf`

기존 `/etc/sliper/runtime.env`는 보존했다. 따라서 이 파일만 보면 이전 프로젝트 값이 남아 있다. **현재 운영값은 drop-in으로 추가된 `/etc/sliper/seoul.env`가 덮어쓰며, 실제 세 프로세스가 모두 서울 DB와 새 Auth·Storage 키를 사용하는 것을 확인했다.** `APP_ORIGIN`·도메인·TLS·Nginx·VAPID 키는 변경하지 않았다.

새 설정 파일 권한은 `0640 root:sliper`다. 관리자 `postgres` 계정은 이전에만 사용했고 운영 연결에는 사용하지 않는다. 기존 구조처럼 RLS가 활성화된 private 서비스 스키마를 서버 전용 역할이 사용하고, 애플리케이션이 회원별 접근을 검사한다. 해당 역할에는 SUPERUSER·CREATEDB·CREATEROLE 권한이 없으며 Auth 스키마 읽기도 거부된다.

로컬 `.env`, `.env.supabase.local`도 새 연결로 갱신했다. 두 파일의 접근 권한은 사용자와 SYSTEM으로 제한했다. 수동 백업용 `.local/backup-settings/production.env`는 서울을 가리키며, 기존 접속 정보는 같은 접근 제한 폴더의 `source-sydney.env`로 보존했다. 비밀값은 문서·Git·로그에 기록하지 않았다.

4. 응답 시간 변화

| 요청                          | 이전 측정        | 서울 전환 후 측정 |
| ----------------------------- | ---------------- | ----------------- |
| 운영 서버 → DB 단순 왕복      | 208~212ms        | 5ms, 5회          |
| 비회원 글 목록 API, 반복 조회 | 약 466~487ms     | 43~70ms           |
| 로그인 글 목록 API            | 약 1,066~1,084ms | 109~200ms         |
| 로그인 글 상세 API            | 약 1,294~1,314ms | 84~94ms           |
| 마이페이지 전체 응답          | 약 2,867~2,870ms | 143~255ms         |
| 공개 이미지 약 216KB          | 약 529~550ms     | 73~93ms           |
| 같은 이미지 ETag 304          | 약 437ms         | 37ms              |

이는 같은 원본 데이터와 전용 계정으로 소수의 읽기 요청을 비교한 결과다. 첫 비회원 목록 표본은 서울에서도 550ms였다. 캐시·연결·SQL 계획 준비에 따른 첫 요청 차이가 남으므로 항상 위 반복 응답 시간이 보장된다는 뜻은 아니다. 페이지는 스트리밍 헤더의 TTFB가 아니라 전체 응답 본문 수신 시간으로 비교했다. 동시 부하 시험이나 실제 휴대폰 성능 측정 결과는 아니다.

원래 분석의 핵심이었던 한국 웹 서버와 시드니 DB 사이의 지연이 주요 병목임을 이전 후 측정으로 확인했다. 별도 Redis를 추가하거나 Ncloud 인스턴스를 증설하지 않았다.

5. 남은 개선과 운영 범위

- 이미지의 최종 응답은 아직 `private, no-store`다. 기존 공통 인증 프록시와 이미지 재검증 정책의 충돌 수정은 별도 코드 작업으로 남는다.
- 마이페이지 순차 조회·글 상세의 알림 의존성·인증 조회 경로 최적화도 아직 코드상 그대로다. 가까운 DB로 이동해 응답이 줄었지만 개선 여지는 있다.
- 기존 시드니 프로젝트와 암호화 백업은 삭제하지 않았다. 서울에서 새 쓰기가 재개됐으므로 이후 원복은 신규 변경분을 보존하는 절차가 필요하다.
- 실제 휴대폰의 새 도메인 푸시 수신 검증은 이번에 추가 수행하지 않았다. 기존 구독·전달 작업 데이터는 이전했고 알림 워커는 정상 실행 중이다.
- 사용자가 보류한 카메라 검증·정기 백업·추가 보관소 구축은 재개하지 않았다. 기존 인증서 갱신과 BetterStack 감시 설정은 유지했다.
