# CRUD와 로컬 DB

## 데이터 경로

첫 화면은 RSC → 공통 서비스 → Drizzle → PostgreSQL 순서로 조회한다. 글 작성·수정·삭제는 Server Actions로 처리한다. 댓글·반응·조회수·이미지·알림은 REST 경로를 사용한다. 별도 클라이언트 상태에는 서버 응답만 보관하며, 저장에 성공한 이후 화면 상태를 갱신한다. 저장 후 목록 갱신만 실패한 경우 저장 실패로 취급하지 않아 중복 제출을 유도하지 않는다.

| 경로 | 메서드 | 동작 |
| --- | --- | --- |
| /api/community | GET | 목록, 추천 3개, 알림, 작성 가능 상태 |
| /api/community/posts | POST | 게시글 작성 |
| /api/community/posts/:id | GET / PATCH / DELETE | 상세·최상위 댓글 첫 페이지 / 수정 / 소프트 삭제 |
| /api/community/posts/:id/comments | GET | 최상위 댓글 또는 지정한 부모의 직접 답글 페이지 |
| /api/community/posts/:id/like | POST | `{ active: boolean }` |
| /api/community/posts/:id/bookmark | POST | `{ active: boolean }` |
| /api/community/posts/:id/view | POST | 서버가 방문자 쿠키를 검증하고 조회 기록 |
| /api/community/comments | POST | 댓글 또는 답글 작성 |
| /api/community/comments/:id | PATCH / DELETE | 본문 수정 / 소프트 삭제 |
| /api/community/notifications | GET | 본인 알림 커서 페이지와 전체 미읽음 수 |
| /api/community/notifications/read | POST | `{ id?: UUID }`, 생략 시 본인 전체 읽음 |
| /api/community/uploads | POST | multipart `file`, 실제 이미지 디코딩·재인코딩 |
| /api/media/:id | GET | 공개된 글 첨부 또는 본인 임시 업로드 |

JSON 응답은 `{ ok: true, data }` 또는 `{ ok: false, error: { code, message } }`다. 목록 파라미터는 `category`, `kind`, `search`, `view`, `sort`, `cursor`, `limit`이다. 기본 24개, 최대 48개이며 다음 페이지 토큰을 반환한다. 최신순은 작성 시각·UUID, 인기순은 좋아요 수·작성 시각·UUID를 기준으로 keyset 커서를 사용한다. 시각은 PostgreSQL의 마이크로초 정밀도를 유지한다. 커서는 필터·정렬·작성자 범위에 묶여 다른 조회 조건에서 사용할 수 없다. 최신순은 중간 삭제나 새로운 글 삽입 후에도 이전 경계에서 이어 읽는다. 인기순은 현재 좋아요 수를 사용하므로 조회 사이에 순위가 바뀌면 이동한 글이 누락되거나 다시 나타날 수 있으며 클라이언트는 ID로 중복을 제거한다. 고정 시점의 순위를 보장하는 스냅샷은 제공하지 않는다.

본문과 댓글은 길이를 검증하고, RSC/REST 공통 DTO에서 auth ID와 익명 닉네임을 제외한다. raw HTML을 비활성화한 Markdown을 렌더링하고 외부 Markdown 이미지는 직접 로드하지 않는다.

## 트랜잭션과 삭제

모집글은 `applicationUrl`에 외부 신청 페이지를 저장한다. 모집글은 외부 신청 링크 또는 직접 모집 정보(장소·일정·시간·비용)를 입력하며, 후기·이야기로 변경하면 행사 정보를 제거한다. HTTP(S) URL만 허용하고 상대 경로·실행 가능한 스킴·자격 증명이 포함된 URL은 거부한다. 상세 화면의 ‘신청하기’는 이동할 호스트를 표시하고 `noopener noreferrer`가 적용된 새 탭으로 열린다. 신청 완료 여부는 외부 플랫폼에서 관리하며 Sliper에서 신청 완료로 기록하지 않는다. 외부 링크가 없는 모집글은 ‘참여 문의’로 상세 화면의 댓글 입력에 연결한다. 실제 주소가 없는 예시 글에 임의의 링크를 채우지 않는다. `0003_recruitment_application_link.sql`로 기존 데이터를 보존하면서 nullable 열을 추가했다.

게시글 행 잠금 아래 수정·삭제·댓글·반응을 처리해 삭제된 글에 새로운 활동이 추가되는 경쟁을 막는다. 댓글과 알림은 같은 트랜잭션에 생성한다. 본문 작성자는 수정할 수 없으며, 이미지 소유권 검증 실패 시 글 변경도 롤백한다. 좋아요·북마크·조회는 유일 제약과 멱등 쓰기를 조합한다.

글 삭제는 제목·본문을 비우고 목록·상세·미디어 응답을 차단한다. 댓글 삭제는 본문과 공개 작성자 정보를 숨기며 자식 댓글을 유지한다. 삭제 이벤트에 연결된 알림도 제거한다. 실제 이미지 파일은 즉시 삭제하지 않고 로컬에 보관한다. 운영 전 임시 업로드와 삭제된 글 첨부의 보존 기간 및 정리 작업이 필요하다.

상세 조회는 최상위 댓글 첫 20개와 `nextCommentCursor`를 반환한다. 댓글 경로는 `parentId`를 생략하면 최상위 댓글, 지정하면 해당 부모의 직접 답글을 조회한다. `cursor`, `limit`을 지원하며 기본 20개·최대 50개다. 응답은 `{ items, nextCursor }`이며 댓글마다 직접 답글 수인 `replyCount`를 포함한다. 작성 시각·UUID 오름차순으로 이어 읽는다. 클라이언트는 부모별 커서를 보관하고 답글을 펼칠 때 불러와 평탄한 배열로 합친 뒤 반복 순회한다. 논리 깊이는 제한하지 않고 화면 들여쓰기만 제한한다. 댓글 변경 응답은 `{ post, comment, parent }`로 변경 항목만 합쳐 이미 펼친 댓글과 페이지 위치를 유지한다.

알림은 기본 20개·최대 50개이며 `{ items, nextCursor, unreadCount }`를 반환한다. 100개를 초과한 과거 알림도 이어 읽을 수 있고 `unreadCount`는 전체 수신함 기준이다. 초기 화면 응답은 `notifications`, `notificationNextCursor`, `unreadCount`를 포함한다. 읽음 응답은 `{ id, readAt, unreadCount }`이며 처리 시작 시각 이후 도착한 알림을 읽음으로 바꾸지 않는다. 화면을 열 때 갱신하며 실시간 push는 제공하지 않는다. 이미 불러온 알림은 읽음 처리 후에도 유지한다.

## 개발 인증 경계

`src/server/identity.ts`의 `currentActor()`는 다음 조건을 모두 만족할 때만 로컬 개발 작성자 UUID를 반환한다.

- `NODE_ENV=development`
- `SLIPER_AUTH_MODE=development`, `LOCAL_DATABASE=1`
- DB가 `127.0.0.1:55432/sliper_dev`
- 요청 Host가 `127.0.0.1:3000` 또는 `localhost:3000`

기본 실행/Origin은 `http://127.0.0.1:3000`이다. UI·API는 client authorId를 받지 않는다. 모든 쓰기는 서버 소유권을 검사한다. POST/PATCH/DELETE는 `APP_ORIGIN`과 정확하게 일치하는 Origin을 요구한다. 예외로 격리된 로컬 개발 환경에서는 3000번 포트의 `localhost`와 `127.0.0.1` 중 실제 요청 Host와 일치하는 Origin을 허용한다. 두 주소 사이의 교차 요청·다른 포트·외부 Origin은 거절하며 프로덕션에는 이 예외를 적용하지 않는다. 개발 서버는 loopback에만 바인딩한다. 프로덕션의 임시 작성자는 항상 비활성화한다.

로컬의 `auth.users` 최소 스텁은 `scripts/local-bootstrap.ts`에서만 만든다. 이 스크립트는 DB host/port/name/개발 플래그가 다르면 실행을 거부한다. 운영 마이그레이션은 Supabase 관리형 auth를 생성·변경하지 않는다.

## 저장 및 재시작

- `.local/postgres`: PostgreSQL 18 실제 데이터 클러스터
- `.local/postgres.log`: DB 실행 로그
- `.local/uploads`: UUID 파일명의 이미지
- `.env`: 로컬 연결 정보와 방문자 쿠키 서명 키

위 항목은 Git에서 제외했다. DB를 옮길 때 실행 중인 데이터 디렉터리를 단순 복사하지 않고 `pg_dump`/복원과 업로드 파일 백업을 함께 사용한다. 현재 프로젝트는 OneDrive 밖의 `C:\Sliper`로 이동했다. 기존 `.env`, DB 클러스터와 업로드 파일을 유지하고 이 경로에서 DB와 앱을 다시 실행한다. 실행 파일과 런타임 경로는 프로젝트 위치를 기준으로 계산한다. 이 로컬 개발 DB는 운영 저장소로 사용하지 않는다.

현재 실제 Supabase 연결/스토리지/OAuth는 없다. 인증을 연결할 때 서비스·스키마를 유지하고 identity 및 media 저장 어댑터를 교체한다. 로컬의 가상 auth 계정을 운영으로 이식하지 않는다.

## 커뮤니티 확장 (2026-09-30)

원래 9개 관심 카테고리에 `knowledge`(지식), `lab`(콘텐츠 연구소), `crew`(함께 만드는 크루)를 추가했다. 새 게시판은 정해진 세부 주제인 `topic`을 필수로 받고, 최대 5개 `tags`를 지원한다. 목록 파라미터에 `topic`, `tag`가 추가되며 커서 범위에도 반영한다. 기존 후기 데이터를 삭제하지 않고 이야기 탭에서 함께 조회한다. 새 작성 UI는 이야기·모집·투표를 제공한다.

모집은 링크가 있으면 외부 신청 페이지로 이동하고, 없으면 `location`, `eventDate`, `eventFee`를 필수로 받는다. 본문에 내용을 적고 `contactInfo`에 문의 안내를 선택 입력한다. 목록·상세의 제목 오른쪽 버튼은 링크가 있으면 신청하기, 없으면 참여 문의로 표시한다. 내부 예약·결제·참가 확정을 구현한 것은 아니며 문의는 댓글로 진행한다.

| 추가 경로 | 메서드 | 동작 |
| --- | --- | --- |
| /api/community/highlights | GET | 추천 최대 12개·인기 글 6개, 익명 공개 DTO |
| /api/community/posts/:id/vote | POST | `{ optionIndex }`, 본인 투표 생성/변경 |
| /api/community/me | GET / PATCH | 본인 프로필·활동 / 닉네임·소개·지역·아이콘·관심사 수정 |
| /api/community/me/visit | POST | KST 하루 방문 점수 적립, `{}` |

투표는 `posts.poll`에 질문·선택지를 저장하고 `poll_votes`의 글·회원 복합 PK로 1인 1표를 유지한다. 글 행 잠금으로 동시 요청을 처리하며 선택 변경은 기존 표를 교체한다. 공개 응답에는 항목별 수와 본인 선택만 제공하고 투표자 ID를 공개하지 않는다. 첫 투표 이후 질문과 항목은 서비스와 DB 트리거에서 변경을 차단한다. 삭제된 글에는 투표할 수 없고 삭제 시 투표 질문을 지운다.

활동은 `activity_events`에 저장하고 중복 출처 키로 반복 적립을 막는다. 글 +5P(하루 30P), 댓글 +2P(하루 20P), 투표 +1P(하루 10P), KST 하루 방문 +2P다. 점수는 클라이언트에서 지정할 수 없다. 프로필 행 잠금 아래 일별 한도를 확인한다. 글 삭제 후에도 이미 받은 점수와 성취는 남는다. 기존 샘플 글/댓글에는 점수를 소급하지 않는다. 마이페이지는 최근 활동 20개를 보여주며 점수·활동 수는 전체 기록을 집계한다. 이 단계는 로컬 개발 작성자를 사용한다.

메인 배너는 광고가 아직 연결되지 않아 광고 공간 미리보기라고 표시한 자체 안내 3개를 7초 간격으로 순환한다. 추천 콘텐츠는 8.5초 간격으로 이동하고 좌우 버튼·일시정지·모바일 스와이프를 지원한다. 포인터/키보드 탐색 중과 숨겨진 탭에서는 자동 이동을 멈춘다. 동작 줄이기 설정에서는 자동 이동과 루프 애니메이션을 끈다. 추천·인기 콘텐츠는 보이는 탭에서 1분마다 DB를 다시 조회한다. 광고 관리 시스템이나 Supabase Realtime 연결은 포함하지 않는다.

`0004_boards_polls_profiles.sql`, `0005_poll_integrity.sql`을 로컬 DB에 적용했다. 기존 데이터를 유지하고 11개 테이블 모두 RLS 및 raw API 역할 접근 제한을 유지한다. 지식·연구소·크루·투표 기능 확인용 가상 예시 4개를 추가했고 예시 표시로 구분한다. 로그인 화면의 입력은 서버로 전송하지 않으며 OAuth는 후속 연동한다.

## 우선순위 점검 이후 변경 (2026-10-01)

게시글 수정(PATCH와 Server Action)은 `expectedUpdatedAt`이 필수다. 글을 열었을 때 받은 `updatedAt`을 그대로 보내며 클라이언트 시각을 생성하지 않는다. 공개 글의 `updatedAt`은 PostgreSQL 마이크로초 6자리까지 보존한다. 서버는 소유권 확인 후 같은 글 행 잠금 안에서 저장 버전을 비교한다. 이전 버전이면 HTTP 409 `CONFLICT`, 버전 누락/잘못된 형식은 400이다. 실패한 수정은 글·첨부를 변경하지 않는다. 화면은 저장 실패 시 편집 내용을 유지하고 최신 글을 확인하도록 안내한다. 좋아요나 조회수 변경은 글 내용 버전을 바꾸지 않으므로 불필요한 편집 충돌을 만들지 않는다.

```json
{
  "categorySlug": "party",
  "kind": "이야기",
  "title": "수정할 제목",
  "bodyMarkdown": "수정할 본문",
  "expectedUpdatedAt": "2026-10-01T00:00:00.123456Z"
}
```

활동점수의 KST 날짜·일별 한도·방문 중복 키·기록 시각은 잠금 대기 후 동일한 DB 시각을 사용한다. 트랜잭션이 자정 전에 시작됐더라도 적립 기록은 실제 계산한 날에 저장한다. 날짜 범위 양끝은 KST 날짜에서 각각 변환하므로 DB 세션이 서머타임 시간대를 사용해도 24시간이다.

상세 읽기 응답은 요청 이후에 완료된 본인의 글 반응·댓글 생성/수정/삭제 기록을 합성한다. 다른 글의 댓글은 섞지 않고 다음 페이지 커서는 유지한다. 최신 목록이 반영된 이후 도착한 이전 추천/인기 갱신 응답도 적용하지 않는다.

## Chrome 글 상세 모달 수정

`localhost:3000`에서 정상적인 브라우저 Origin이 설정된 `127.0.0.1:3000`과 달라 조회수 요청이 403으로 거절되는 문제를 재현했다. 기존 화면은 조회수 POST를 먼저 기다린 뒤 본문을 읽었으므로 이 요청이 실패하면 모달 자체가 열리지 않았다.

이제 클릭 시 모달을 즉시 열고 GET으로 본문을 읽는다. 로딩·오류·재시도 상태를 모달 안에 표시한다. 조회수 POST는 본문 이후 별도로 실행하며 집계 실패가 읽기를 차단하지 않는다. 닫기·다른 글 선택 시 이전 요청을 취소하고 늦은 결과가 모달을 다시 열지 못하게 한다. 로컬 Origin 예외는 실제 Host 일치와 개발 환경에만 제한했다.

회귀/도메인/DB/서비스 71개, 실제 DB·HTTP 통합 7개 통과. 두 로컬 주소의 GET/조회수/방문 200 및 교차 주소 요청 403을 확인했다. 프로덕션 빌드도 성공했고 운영 모드의 localhost 쓰기 예외 차단(403)을 확인했다. 점검 후 개발 서버를 다시 실행했다. 브라우저 직접 클릭 자동 검사는 환경 정책 제한으로 수행하지 않았다.
