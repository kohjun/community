# Sliper 응답 속도 개선 결과 — 2026-10-16

## 적용 결과

로그인 연동 후 드러난 원격 DB 왕복 지연과 중복 인증/목록 요청을 개선했다. Supabase 프로젝트·리전·DB 역할·스키마·원본 검사·결제/QR/미디어 권한은 유지한다.

준비된 개발 서버에서 같은 익명 요청을 반복 측정한 결과다. 테스트 데이터는 게시글 1개·좋아요 1개이며, 대규모 부하나 실제 회원 세션의 성능을 대표하지는 않는다.

## 1. 대표 주소와 요청 보호

- Supabase 모드에서 서로 다른 두 loopback 주소의 페이지 GET/HEAD만 설정된 대표 주소로 정규화한다. 현재 대표 주소는 `http://127.0.0.1:3000`이다.
- `localhost`의 로그인 쿠키를 복사하거나 다른 호스트와 공유하지 않는다. 다른 주소에서 로그인했다면 대표 주소에서 다시 로그인해야 한다.
- API·OAuth 콜백·상태 변경 요청에는 리다이렉트를 적용하지 않는다. CSRF 원본 검사는 기존처럼 정확한 `APP_ORIGIN`만 허용한다.
- Next 16의 Proxy는 두 loopback 호스트를 정규화해 직접 307을 상대 주소로 바꾼다. `/auth/local-origin`의 GET Route Handler에서 절대 Location을 반환해 반복 이동을 막는다.
- 이동 대상을 URL-safe 인코딩으로 전달해 내부 rewrite의 쿼리 디코딩에서도 검색어·페이지 번호를 보존한다. 대상 origin, 인코딩, 길이, 경로를 다시 확인하며 외부 주소·API·콜백 대상으로 이동하지 않는다.

관련 파일: `C:/Sliper/src/proxy.ts`, `C:/Sliper/src/server/request-origin.ts`, `C:/Sliper/src/app/auth/local-origin/route.ts`.

## 2. 초기 목록 재사용

- 서버 초기 쿼리와 브라우저 쿼리를 같은 기본값과 정렬된 키로 비교한다.
- 필터·페이지·서버가 정한 인기 기준 시각이 같으면 초기 목록을 재사용한다.
- 필터/페이지 변경, 작성 후 갱신, 명시적 재시도와 다른 이력 복원은 필요한 조회를 유지한다.
- 다른 조건 조회가 실패한 뒤 유효한 초기 목록으로 돌아오면 이전 오류와 로딩 상태를 정리한다.
- 후기/이야기, 인기 기간·기준 시각, 관심/북마크, 거리 등 다른 조건은 같은 목록으로 취급하지 않는다.

관련 파일: `C:/Sliper/src/lib/feed-query-key.ts`, `C:/Sliper/src/lib/use-community.ts`, `C:/Sliper/src/components/sliper-community.tsx`.

## 3. DB 조회 배치

- 일반·추천·인기·예정 행사 기본 조회는 기존의 정렬·필터·회원별 차단/숨김 정책을 유지한 채 병렬 실행한다.
- 나온 게시글 ID를 요청 안에서 합쳐 이미지·영상·투표·인증 후기 메타데이터를 한 번씩 조회한다.
- 이 네 종류의 독립 조회는 병렬로 실행한다. 회원의 내 투표와 전체 투표 집계는 구분한다.
- 조회 결과 공유 범위는 단일 호출이다. 서비스 인스턴스가 재사용돼도 다른 회원이나 다음 요청의 결과를 캐시하지 않는다.
- 공개 목록/상세, 회원별 좋아요·북마크·투표, 페이지/커서 방식, 지도 조건과 순위를 유지한다.

관련 파일: `C:/Sliper/src/server/post-reader.ts`, `C:/Sliper/src/server/community-service.ts`.

## 4. 공통 로그인 상태와 회원 전용 요청

- 헤더·알림·푸시 안내·활동 기록이 `SessionProvider`의 상태를 공유한다.
- 동시에 시작한 세션 확인은 같은 진행 중 요청을 사용한다. 짧은 경로 이동과 focus/visibilitychange 중복은 10초의 UI 재확인 간격으로 합친다.
- 이 재사용은 브라우저 UI에만 적용한다. 서버 API는 계속 Auth에서 사용자를 검증하고 DB에서 회원 제한을 확인한다.
- `/api/auth/session`은 인증된 ID와 활성 회원 판정을 한 번의 identity 경로로 얻는다. 그 뒤 독립적인 닉네임·운영 역할 조회를 병렬화한다.
- 로그인/설정 변경과 로그아웃은 강제로 다시 확인한다. 기존 진행 중 응답은 취소하고 세대 번호로 늦은 응답의 반영을 막는다.
- React 개발 Strict Mode의 effect 재실행은 같은 요청을 공유하고, 실제 해제 시에는 취소한다.
- 비회원에게 푸시 설정과 활동 수집 API를 자동 호출하지 않는다. 푸시 설정은 같은 인증 확인 결과에 한 번만 요청하고, 거절된 방문 기록은 해당 세션 확인 상태에서 반복하지 않는다.

관련 파일: `C:/Sliper/src/components/session-provider.tsx`, `C:/Sliper/src/server/identity.ts`, `C:/Sliper/src/app/api/auth/session/route.ts` 및 헤더/알림/푸시/활동 컴포넌트.

## 검증

- 최종 `npm run check`: 비밀값·서식·TypeScript·**954/954 회귀 검사**·Drizzle 정의 검사 통과.
- 기존 OAuth 시작 연결 검사 2개 통과: Google/Kakao 공급자 이동, PKCE, 최소 권한, 외부 원본·위조 returnTo/scope 차단. 실제 사용자의 비밀번호 입력이나 재로그인을 대신 수행한 검사는 아니다.
- 실제 HTTP 보안 비교 9개 통과: 대표 호스트와 필터 보존, API 비이동, 외부 원본 403, 외부 URL/역슬래시/콜백/API 대상 400, 전용 경로 POST 405.
- 별도 익명 Chrome: 초기 목록 재조회 없음, 공통 세션 한 번, 익명 푸시·방문 요청 없음, focus 중복 없음, 카테고리 변경 한 번, 이야기 이동 시 초기 데이터 재사용, JS 오류 없음.
- 인증 API를 가짜 응답으로 대체한 Chrome: 회원 공통 상태 공유, 초기 푸시/알림/활동 한 번, focus 병합, 로그아웃 후 늦은 설정 응답 무시. 실제 DB나 계정으로 쓰기 요청을 보내지 않았다.
- 가짜 목록 실패 Chrome: 실패한 필터에서 초기 목록으로 돌아오면 오류를 지우고 불필요한 재조회를 하지 않는다.
- Android Pixel 7 화면/터치 에뮬레이션: 초기 세션 한 번, 목록·익명 푸시·활동 재조회 없음, JS 오류 없음. 실제 Android 단말 검사를 뜻하지 않는다.
- 운영용 webpack 빌드는 별도 소스 복사본에서 확인하고 서버 trace 정책도 검사한다. 마지막 결과는 Git 제외된 `.local/performance-final-build.log`에 보관한다.

최종 검사 도중 기존 VAPID 테스트의 간헐 실패도 재현했다. Node ECDH의 private scalar가 선행 0 없이 31바이트로 나올 수 있어 유효한 테스트 키가 형식 검사에 실패했다. 네 테스트의 키 생성만 32바이트로 맞췄으며, 실제 짧은 키는 계속 거절하는 회귀 검사를 추가했다. 앱 키 검증과 실제 키 값은 변경하지 않았다.

## 이후 고려할 부분

현재 시드니 연결의 DB 왕복은 여전히 약 150~160ms다. 새 연결·첫 컴파일은 준비된 요청보다 느릴 수 있다. 추가 개선은 앱/DB의 리전 배치와 공개 후보 데이터의 제한적 캐시를 검토하되 별도 측정·권한 검증·이전 계획으로 진행한다.

Redis는 기존 공지방 용도를 유지한다. DB 스키마, 프로젝트 리전, 자격 증명, 실제 사용자 데이터나 결제 정보를 이번 수정에서 바꾸지 않았다.
