## 종합 판단

**행사 운영과 경험의 재사용을 지원하는 기능 기반이 충실한 베타다. 일반 공개 운영의 안정성과 실제 커뮤니티의 활력은 아직 검증을 마쳐야 한다.**

사용자 허용 후 완료한 후속 npm 감사에서 Next.js(Critical)·Zod(High)의 영향 버전을 확인했다. 공개 배포 전 보안 업데이트(P1)를 기존 수정 순서의 맨 앞에 추가한다. [의존성 감사와 현재 코드 적용 조건](DEPENDENCY_AUDIT_2026-10-25.md).

신청 → 승인 → 공지 → QR 참가 확인 → 완료 → 회고/경력 → 자료 재사용을 연결하는 방향은 일관적이다. 좋은 커뮤니티가 되기 위한 신뢰·운영·기록 장치도 상당 부분 구현되어 있다. 현재 우선순위는 새 기능의 수를 늘리는 것보다 기존 연결 오류를 고치고 실제 모임과 대화를 반복해서 쌓는 데 있다.

## 1. 검토 범위와 현재 확인값

- 소스 구조: TS/TSX/CSS 513개, 약 94,491행, 화면 63개, API Route 파일 42개, SQL 마이그레이션 73개. 화면 수에는 회원·관리자·편집 화면도 포함한다.

- 기존 동일 소스의 전체 검사 1,034개 성공과 운영 빌드 성공을 확인했다. 서버 추적 116개, 배포 산출물 감사도 직전 검증에서 통과했다. 이번 리뷰를 위해 전체 검사를 다시 실행한 것은 아니다.
- 기본 테스트 파일은 112개, 별도 integration 파일은 41개다. 기본 검사에도 실제 PGlite 서비스 검사가 포함되며, 모든 HTTP integration 파일이 npm run check에 들어가는 것은 아니다.

- 현재 설정 형식 검사: PASS 8 / FAIL 2 / WARN 7. FAIL은 공개 HTTPS 원본과 광고 설정이다. DB 역할/마이그레이션 경고는 정적 검사 결과이며 실제 역할이 잘못되었다는 판정은 아니다.

실제 기기·Safari·결제 제공자·Ncloud 런타임·원격 권한/버킷 설정·고부하를 이번 리뷰에서 전수 검증하지 않았다.

## 2. 먼저 수정할 확인된 문제

P2는 정상 사용·운영을 해칠 수 있어 후속 수정이 필요한 중간 우선순위다. 다음 순서는 같은 P2 안에서도 영향과 재현 가능성을 고려한 권장 순서다.

### R0 · P1 · 보안 의존성 업데이트를 공개 배포 전에 우선 수행

npm 운영 의존성 감사 결과 영향 패키지는 next 16.3.7(Critical 집계)·zod 4.6.5(High 집계)다. App Router·Server Actions DoS의 기능 조건과 Zod 검증의 도달 경로를 확인했다. Critical 중 SVG 경로는 sharp 0.35.5 우회책을 충족하고, use cache 경로는 사용하지 않아 실제 RCE를 확인했다는 의미는 아니다. next/@next/env 16.4.3·zod 4.6.7 반영과 전체 검사·빌드·재감사를 우선 계획한다. 이번 작업은 검사만 수행했고 패키지는 변경하지 않았다. [공식 근거·조건·수정 계획](DEPENDENCY_AUDIT_2026-10-25.md).

- 정상 닫기 동작 자체의 오류보다는 작성 도구의 복구 장치 미비다. 초안 저장을 추가할 경우 로그아웃·회원 변경·기기 공용 사용과 미디어 권한도 고려한다.

### R10 · 조건부 P2 · LAN 테스트 모드에서 Host 위조로 로컬 계정 사용 가능

- 위치: [identity.ts:33](C:/Sliper/src/server/identity.ts:33), [dev-lan.ts:20](C:/Sliper/scripts/dev-lan.ts:20).
- 격리 로컬 DB 모드의 자동 계정 분기가 요청의 loopback Host를 신뢰한다. LAN 서버에 접속한 다른 기기가 Host/Origin을 loopback으로 위조하면 테스트 비밀번호 없이 레거시 계정 경로를 탈 수 있다.
- **순수 Request 재현:** LAN URL과 위조한 loopback Host/Origin 조합이 출처 검사를 통과했다. 실제 LAN 침투나 회원 데이터 변경 없음.
- 현재 Supabase 모드와 production에서는 이 분기가 비활성이다. 해당 개발 모드를 다시 사용할 때 LAN 바인딩이면 자동 계정 분기를 끄고 서명된 테스트 세션을 요구한다.

## 3. 코드와 설계의 강점

1. 도메인 검증·서버 서비스·UI가 나뉜 단일 애플리케이션 구조는 1인 개발의 현재 단계에 적합하다. DB 트랜잭션과 정원 잠금, 수정 버전 비교, 중복 승인 방지로 실제 상태 변경을 관리한다.
2. Supabase getUser로 인증하고 운영 권한을 DB에서 확인한다. 변경 요청에는 출처 검사·본문 크기 제한·엄격한 입력 검증이 있으며 외부 결제 신호도 서명/시각/금액/중복을 검사한다.
3. private Storage, 객체 ID 교체, 회원 전용 회고/공유, 공지방 권한 재확인과 메시지가 아닌 갱신 힌트를 전달하는 Realtime 설계가 있다.
4. 캐시는 공개 DTO만 공유하고 개인 상태를 사본에 덧붙인다. 메모리 보관 상한·만료·동시 로딩 합치기·숨김 재확인·사진 ETag 이전 인가가 들어 있다. 이번 선별 리뷰에서 회원 간 캐시 혼합은 확인하지 않았다.
5. FFmpeg를 웹 요청에서 분리하고 DB 작업 원장·임대/lock token·SKIP LOCKED·재시도를 사용한다. 중복 클릭 잠금·취소·늦은 응답 무시도 여러 UI에 들어 있다.
6. 행사 결과와 확인 방식, 주최 기록과 수락한 제작 역할, 자료 버전과 사용 사례를 구분하는 방향이 좋다. 매너 온도도 평가 표본/의미를 설명한다.
7. 관리자 신고·문의·분쟁·이의신청, 실제 상태 설명, 이용 지표가 구현되어 있다. 재방문·질문 답변률 등 이미 있는 지표는 다음 운영의 출발점으로 사용할 수 있다.

## 4. 유지보수와 검사 체계

소스 규모가 커졌다. 이벤트 맵 1,389행·홈 1,205행·편집기 967행·번개 954행인 화면과 1,000행 전후의 서비스는 상태 흐름을 추적하기 어렵게 만든다. 전역 CSS는 46개/약 23,919행이며 root layout은 41개를 순서대로 불러온다. 이는 회귀/추적 비용의 근거이며 측정 없이 로딩 지연의 원인으로 단정하지 않는다.

권장하는 정리는 큰 전면 재작성보다 기능 단위의 점진적 분리다. 예를 들어 행사 신청 상태, 작성 초안, 목록 필터, 장소 선택을 각각 작은 상태/컴포넌트로 나누고 화면 스타일을 해당 기능 범위로 옮긴다. 1인 운영에서 마이크로서비스를 추가할 필요는 현재 근거가 없다.

현재 검사 체계는 규칙·트랜잭션·권한에 강점이 있다. 반면 기본 npm run check는 별도 HTTP integration 전체나 저장소에 고정된 브라우저 회귀를 자동 실행하지 않는다. .local에 있던 일회성 Chrome 검증과 재현 가능한 배포 전 검사는 구분해야 한다.

먼저 저장소와 CI에 고정할 흐름:

- 원래 글에서 로그인 → 원래 글 복귀 → 댓글 작성.
- 정원 마감 → 대기 → 자리 안내 → 열린 페이지에서 신청 → 승인/공지방.
- 비회원·이전 작성자·차단/숨김 상태의 행사/미디어 접근.
- 긴 글 입력 → 실수로 닫기 → 복구/명시적 폐기.
- 작은 영상 Range의 실제 upstream 전송량, 삭제 작업 실패 후 재시도.

검사 개수와 별도로 이런 상태 전환의 보장이 필요하다.

## 5. 커뮤니티로서의 평가

Sliper의 장점은 사람들이 함께 연 활동을 기록하고 다시 실행하게 돕는 구조다. 사용자가 실제로 만족하는지는 모임의 안전한 안내, 담당자 응답, 첫 참가 경험, 후기와 다음 행사 반영으로 판단해야 한다.

현재 공개 글의 상당수가 샘플이고 아카이브에 실제 공개 자료가 없으며, 참가 가능한 예정 모집도 확인되지 않았다. 따라서 지금 방문자에게 보이는 가치는 실제 운영 데이터 공급에 크게 달려 있다. 빈 목록과 샘플 구분은 정직하게 구현되어 있지만 그것만으로 재방문 이유가 생기지는 않는다.

모바일 첫 화면에는 헤더·소개·광고 미리보기·세 가지 빠른 이동·카테고리가 먼저 보여 실제 모집 카드가 첫 화면 아래에 걸친다. 가로 넘침은 없으나 ‘지금 참가할 모임 찾기’의 거리에는 개선 여지가 있다. 아카이브도 입문 안내를 읽은 뒤 실제 목록에 도달한다. 광고를 유지하더라도 실제 모집/자료가 충분히 있을 때 첫 화면의 핵심 동선을 앞당기는 실험이 적절하다.

첫 운영은 기존 계획대로 한 지역·주최자 3~5명·취향 2~3개에 집중한다. 실제 모집 → 첫 참가 → 담당자 확인 → 후기/회고 → 개선 한 가지 → 재개최를 반복한다. 목표 인원·목표치 자체를 성과로 표시하지 말고, 실제 모임 수·확정 후 참가율·처음 온 회원의 재참가·24시간 질문 응답률·후기/회고 완료와 자료 재사용을 함께 본다. 재방문 지표 코드는 이미 있으므로 다시 만들기보다 운영 데이터로 검증한다.

## 6. 공개 운영 전에 필요한 것

- 현재 로컬 설정의 공개 HTTPS와 광고 설정 미완료는 코드 결함과 구분한다. 광고가 준비되지 않은 초기 운영은 완전히 비활성화한 상태로 검증할 수 있다.
- 카카오/Google의 기존 로그인 확인 이력은 있으나 공개 HTTPS에서의 왕복·쿠키·회원별 접근을 다시 확인해야 한다. 실제 VAPID/Android/iPhone 알림도 현재 검증되지 않았다.
- 로컬 백업 도구는 production/원격 DB 및 원격 미디어를 거부한다. 로컬 복원 통과가 Supabase 복원을 입증하지 않는다. DB 백업에는 Storage 객체 본문이 포함되지 않으므로 두 자산을 함께 별도 환경에서 복원해야 한다. [Supabase 공식 백업 문서](https://supabase.com/docs/guides/platform/backups).
- 보관 정리는 명시적 CLI 실행이며 현재 웹/알림/영상 Compose에 자동 정리 스케줄이 없다. 실패 알림과 삭제 outbox도 필요하다.
- 워커 heartbeat·오류 경보·로그 회전·백업/복원·롤백을 실제 호스팅에 배치하고 재시작을 시험한다. 로그인 페이지 healthcheck만으로 워커 정상 동작을 판정하지 않는다.
- 외부 결제/환불 공급자 검증 전에는 무료 모임과 검증된 수동 승인 범위로 운영한다. DB 설정의 형식 PASS를 실제 거래 검증 완료로 간주하지 않는다.
- 초기 검색 제외(noindex)는 현재 의도된 상태다. 공개 확장 때 robots/sitemap/공유 미리보기 범위를 결정한다.

## 8. 검증 제한과 추가 감사

애플리케이션 코드 리뷰에서 P0/P1 사고를 재현하지 못했다는 사실이 전수 보안 검증이나 무결함 인증을 뜻하지 않는다. 후속 의존성 감사로 공개 배포 전 업데이트(P1)가 추가됐다. 위 결함들은 소스/격리 재현/공개 화면에서 근거를 확인한 범위만 기록했다.

운영 의존성의 npm audit는 사용자가 메타데이터 외부 전송을 명시적으로 허용한 후 완료했다. 영향 패키지 2개(Critical 1·High 1)를 확인했고 공식 권고 및 현재 코드 조건을 대조했다. 패키지 설치·업데이트·잠금 파일 변경·공격 재현은 수행하지 않았다. [후속 감사 결과](DEPENDENCY_AUDIT_2026-10-25.md).
