# 모임 찾기 → 수요 제안 → 참가 이후 연결

구현 기준: 2026-10-25. 기존 Supabase PostgreSQL·Auth·private Storage와 알림 워커를 사용한다.

## 1. 저장 조건과 정원 대기

- `/discover/saved`: 최대 10개 조건을 저장한다. 지역 문자열·카테고리·제목/태그 검색어·번개/행사·사전 참가비 상한·초보/혼자 참가 안내 여부를 선택한다.
- `/discover/saved/{ID}`: 같은 조건으로 현재 모집을 조회한다. 알림을 꺼도 직접 검색은 가능하다. 지역은 위치 반경이 아닌 장소 문자열 검색이다. 현장 정산 비용은 사전 참가비 상한에 포함되지 않는다.
- 알림은 저장 이후 새로 등록된 모집부터 시작한다. 기본은 조건별 24시간에 최대 1건이며, 즉시 매칭/끄기를 선택할 수 있다. 하루 한 번 알림에서는 저장 조건 화면으로 연결해 나머지 모집도 탐색한다. 같은 모집은 여러 조건에 맞아도 중복 발송하지 않는다. 과거 카테고리/호스트 구독 알림과의 통합 중복 제거는 후속이다.
- 기존 `push:worker`가 조건을 순환 조회하고, 알림함 및 설정된 웹 푸시에 전달한다. 검사 간격은 약 1분이며 배치 제한이나 장애에 따라 지연될 수 있다. 별도 외부 유료 서비스는 추가하지 않았다.
- 대기는 직접 신청하는 행사에서 정원이 찼을 때 등록한다. 외부 플랫폼 행사와 종료/취소 행사는 대상에서 제외한다. 대기와 참가 승인 대기를 구분한다.
- 자리가 생기면 등록 시각·ID 순서로 안내하고 최대 2시간(행사 시작 시각까지)의 신청 기회를 준다. 안내받은 사람은 기존 신청서에 답변하고 제출한다. 번개는 담당자 승인, 유료 행사는 기존 결제 절차를 따른다. 대기 등록만으로 공지방 권한이 생기지 않는다.
- 행사 행 잠금을 일반 신청·자리 안내·승인과 공유한다. 유효한 안내 자리와 대기에서 제출한 번개 승인 요청을 정원에 반영해 다른 신청이 먼저 가져가지 못하게 한다. 기한 만료·취소 시 다음 사람에게 안내한다. 대기열은 행사당 최대 500명이다.

## 2. 이런 모임 열어주세요

- `/ideas`: 지역·취향·가능 날짜·하고 싶은 활동을 제안하고 관심을 표시한다. 20개 단위 페이지와 지역 검색을 제공한다.
- 제안은 기존 이야기의 질문 글로 함께 저장된다. 기존 댓글·수정·삭제·신고 경로를 사용한다. 공개 이야기이므로 개인정보를 포함하지 않도록 안내한다.
- 관심은 계정당 한 번이며 취소할 수 있다. 관심 표시는 참가·결제 확정과 구분한다. 제안 작성자는 관심 접수를 마감/재개할 수 있다. 가능 날짜가 지나면 새 관심 접수를 받지 않는다.
- 주최자는 직접 만든 공개 모집글 주소/ID를 연결한다. 다른 사람의 모집을 임의로 연결할 수 없다. 제안당 최대 10개다. 모집은 별도 신청·승인·결제 절차를 따른다.
- 자동 행사 개설이나 참가자 자동 이전은 하지 않는다. 관심 이용자의 이름·연락처 명단은 공개하지 않고 집계만 제공한다.

## 3. 종료 후 경험·사진·다음 활동

- `/events/{ID}/reunion`: 담당자가 공식 완료한 실제 행사의 경험·사진·주최자 회고·인증 후기·다음 활동 제안을 연결한다. 기존 종료 후 할 일 화면에 진입 링크를 추가했다.
- 주최자 또는 실제 참가가 확인된 회원이 자기 경험 한 건을 작성·수정·삭제한다. 담당자 확인과 QR 확인을 사용하고 현재 미참석 정정은 반영한다. 환불과 실제 참가 기록은 구분한다.
- 공유 범위는 `참가 확인된 사람·담당자만` / `로그인 회원` 중 직접 선택한다. 자동 참가자 명단은 공개하지 않는다. 인증 후기와 점수는 기존 기능의 권한·기준을 그대로 사용한다.
- 사진 최대 6장. 기존 브라우저 사전 압축·서버 WebP 검증·비공개 Storage 업로드를 사용한다. 직접 이미지 URL도 회원·행사·차단·작성자 상태·공유 범위를 재검사한다.
- 사진이 공유에 연결되면 행사 출처를 영구 보관하고 공개 게시글/운영 회고로 재첨부할 수 없게 한다. 공유에서 제외·삭제한 사진은 직접 열람도 차단한다. 출처가 있는 사진의 실물 삭제/개인정보 보존 정책 자동화는 별도 후속이며 30일 미첨부 정리에서 제외한다.
- 여러 화면 수정은 버전을 비교해 덮어쓰기를 막는다. 참가자는 다음 활동 제안을 만들어 원래 행사와 연결할 수 있다.
- 불편한 공유 내용은 모임 주소·작성자와 함께 기존 문의에서 신고할 수 있다. 개별 공유 항목 전용 신고 큐는 후속이다.

## 데이터와 권한

| 테이블/확장 | 역할 |
|---|---|
| `saved_searches` | 소유자별 검색 조건·알림 빈도·다음 검사 시각 |
| `event_waitlist` | 행사별 1인 1대기·순서·안내 기한·제출 상태 |
| `event_ideas` | 이야기 글에 연결된 모임 제안 정보 |
| `idea_interests` | 중복 없는 관심 표시 |
| `idea_events` | 제안과 실제 모집 연결 |
| `event_reflections` | 행사별 개인 경험·공개 범위·사진 ID·수정 버전 |
| `media_assets.reunion_origin_post_id` | 사진 출처·공개 재첨부 금지 |

원본은 PostgreSQL이다. Redis 캐시나 브라우저 저장소가 참가·대기·관심·공유의 원본이 되지 않는다. 새 테이블은 RLS를 켜고 anon/authenticated의 직접 접근을 차단한다. 신뢰하는 서버 실행 역할과 동일 출처 API를 통해 접근하며 API마다 현재 회원·소유자·차단·숨김을 검사한다. 알림 조회와 푸시 발송 직전에도 원본 상태를 재검증한다.

새 DB 마이그레이션: `0070_community_growth`, `0071_growth_scan_fairness`, `0072_growth_integrity`. Supabase 원장 73개, 신규 테이블 6개. 적용 전후 기존 회원·글·신청·행사 설정·이미지의 집계 해시를 비교했고 변경이 없었다.

## 검증

- 전체 `npm run check`: 테스트 1,018개, 비밀값·서식·타입·Drizzle 검사 통과.
- 신규 DB 통합 11개(대기 순서의 마이크로초 정밀도와 가짜 발송기의 푸시 전달 검증 포함): 조건 매칭/중복·빈도, 차단·숨김, 대기 순서/만료/자리 보호, 번개 담당자 승인, 제안 권한·중복 관심, 경험 공유 범위·수정 충돌, 사진 직접 접근·보관·재첨부 거부.
- 후속 집중 검사는 신규 기능과 서비스 워커를 함께 확인했다. 최종 운영 빌드 통과, 서버 추적 116개에서 비밀 파일·영상 워커 의존성 오류 0개. 현재 소스와 빌드 사본이 일치하며 산출물 2,540개에서 비밀 설정 파일·외부 연결이 없음을 확인했다.
- PC 9개 + Android Pixel 7 크기 9개 브라우저 시나리오 통과. 실제 컴포넌트를 사용하되 API는 격리 응답으로 대체했다. 실제 회원 데이터 쓰기·페이지 오류·가로 넘침은 0개다. 실제 휴대폰/Safari 검증은 아니다. 실제 개발 서버에서도 Android 크기의 공통 헤더·메뉴에 가로 넘침이 없음을 확인했다.
- 실제 로컬 서버의 저장 조건·제안 페이지 HTTP 200, 비로그인 API 401, 다른 출처 변경 요청 403 확인. 일반 실행 역할로 새 테이블 조회도 확인했다.
- 현재 환경의 VAPID 키는 비어 있다. 로컬 워커는 알림함과 대기 안내를 처리하며, 실제 휴대폰 웹 푸시는 HTTPS·VAPID·수신 동의 설정 후 검증해야 한다.
- 실제 운영 회원을 사용한 신청·취소나 원격 샘플 글/사진 생성은 하지 않았다. 단위/격리 DB 검사는 실제 다중 인스턴스 부하 시험을 대신하지 않는다.

## 실행

웹: `npm run dev` 또는 배포 구성의 웹 프로세스.
알림/대기: `npm run push:worker`를 별도 프로세스로 상시 실행한다. 웹 서버만 켜면 외부 모드의 워커가 자동 실행되지는 않는다. 배포 구성의 기존 알림 워커 서비스에 그대로 포함된다.
