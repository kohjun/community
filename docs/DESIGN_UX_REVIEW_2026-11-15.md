# Sliper 디자인·사용성 점검 — 2026-11-15

## 판단

현재 Sliper는 **브랜드와 기본 컴포넌트가 갖춰진 베타 서비스**다. 디자인 리뷰 관점의 종합 평가는 **약7/10**이다. 이는 공식 인증 점수·자동화 점수·경쟁사 순위가 아닌 주관적 제품 디자인 평가다. 다음 개선의 중심은 정보 위계, 읽기 대비, 모바일 조작, 반복 패턴의 일관성이다.

Pretendard·파란색·밝은 배경의 방향은 유지할 가치가 있다. 웹게임 카드 화면은 현재 사이트의 비교 기준으로 삼기 좋다. 모임·이야기·자료처럼 목적이 다른 화면은 고유한 정보 구조를 유지하되 검색·필터·버튼·상태 표현은 공통으로 정리하는 것이 좋다.

## 점검 범위와 한계

- 실제 https://sliper.kr 의 홈·이야기·번개·아카이브·플레이어/크루·지도·게임·로그인·회원가입·통합 검색10페이지를 Chrome393×852 및1440×1000, 총20개 화면으로 확인했다.
- 홈·이야기·아카이브·지도를320px 너비에서도 추가 확인했다. 모두 페이지 가로 넘침이 없었다. 20개 기본 화면에서 JavaScript pageerror는0이었다. console 경고 전부·네트워크 실패 전부를 검증한 결과로 해석하지 않는다.
- 이야기의 취향 모달을 실제로 열어 포커스 진입과 Escape 닫기를 확인했고, 공개 글 상세도 확인했다. 폼 제출·결제·개인 정보 변경·신규 테스트 계정 생성은 하지 않았다.
- 비회원 상태의 리뷰다. 로그인 이후 관리·공지방·작성 폼의 모든 상태, 물리적 Android/iPhone, 스크린리더, 전체 WCAG 적합성, 실사용 Core Web Vitals까지 검증하지 않았다.
- 첫 촬영에서 일부 이미지가 아직 로드 중이었지만 재확인에서 홈의 보이는 사진3개 모두 정상 로드됐다. 이를 이미지 누락 문제로 분류하지 않았다.
- 자동 측정에서 작은 버튼으로 분류된 게임 제목은 카드 전체로 확장된 ::after 클릭 영역이 있어 터치 결함에서 제외했다. 비활성 버튼과 이미지/그라데이션 위 텍스트 대비는 단순 계산에서 제외했다.
- 실제 회원·글·기존 게임을 수정하지 않았다. 일반 방문에 따른 사이트 자체 방문/조회 기록은 발생할 수 있다.

## 유지할 점

1. 파란색·흰색·회색과 Pretendard의 조합이 Sliper의 기본 인상을 만든다. 라이트 모드는 기존 사용자 요구를 유지한다.
2. 대부분의 공통 셸이 SiteHeader·SiteFooter를 사용하고, 검색·찜·알림의 역할이 분리돼 있다.
3. 모바일 상단57px·하단68px의 개별 고정 바는 이 점검 화면에서 비교적 적절한 크기다. 본문 여백과 안전 영역 처리도 이미 있다.
4. 키보드 포커스 윤곽, 본문 바로가기, 버튼 이름·선택 상태, 모달 포커스 처리 등 기초 구현이 있다.
5. 홈 캐러셀은 일시정지, 포커스·호버·탭 숨김·동작 감소에 따른 자동 전환 중지를 이미 구현했다. 이런 안전장치는 유지한다.
6. 예시 모집글에는 ‘모임 예시’가 표시되고, 무료 운영 도구도 실제 운영 실적이나 품질 인증과 구분한다. 이 정직한 표시는 유지한다.

보통 글자 대비4.5:1, 큰 글자3:1은 [WCAG 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)이다. 터치44~48px는 이번 개선 목표다. [WCAG2.2의 AA 최소 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)은24px와 간격 등의 예외를 포함하므로,44px 미만이라는 사실만으로 모두 AA 실패라고 판단하지 않는다.

추천 토큰: 로고·포인트는 기존 #0A84FE, 흰 글씨가 올라가는 버튼은 기존 --sl-accent-2인 #0868CC를 활용하면 흰 글씨 대비가 약5.44:1이다. 보조 글자는 기존 --sl-ink-3인 #56647A가 흰색 위6.00:1·현재 회색 배경 위5.49:1이다. 비활성 컨트롤·순수 장식·선과 의미 있는 글자의 색을 구분한다.

### P1-2. 아카이브와 번개에서 결과를 먼저 보여주기

**아카이브:** 모바일393px에서 무료 도구3개 → 첫 호스트 안내 → 주제 탐색 링크 → 전체 조건 폼 순서다. 목록/빈 결과 상태가 약1,913px에서 시작했다. 확인 당시 공개 결과는0건이므로 ‘실제 자료가 아래에 있다’고 단정하지 않는다.

추천 순서: 제목·탭 → 검색어 → 간단한 조건 요약 → 결과 수/자료 또는 빈 상태 → 접힌 ‘첫 진행 가이드’ → 추가 안내. 무료 도구는 삭제하지 않고 가이드 안에서3개를 바로 내려받을 수 있게 한다. 중복되는 초보자 안내 두 영역은 하나로 합친다. 인원·시간·가격만 기본으로 노출하고 난이도·스태프·운영 사례 등은 ‘상세 조건’에서 연다. 공개 자료가 없으면 무료 도구를 명확한 대안으로 연결한다.

**번개:** 소개와 특장점 카드, 활동 카테고리 큰 격자, 추천 태그가 이어져 첫 모임 제목이 약1,413px에서 나타났다. 현재 노출되는 테스트 모임은 실제 운영 콘텐츠와 구분할 필요가 있으며, 이번 리뷰에서는 변경하지 않았다.

추천 순서: 짧은 제목·번개 열기 → 날짜/지역 → 컴팩트한 활동 필터 → 모임 목록. 큰 카테고리 그림 타일은 짧은 칩으로 정리하거나 ‘모든 활동’ 시트로 확장한다. 사용자가 선택한 범주와 자주 쓰는 범주는 앞에 남긴다.

**지도:** 검색·유형·취향·결제 안내·지도/목록 전환이 세로로 쌓여 지도 시작이 대략488px다. 첫 화면에서 실제 지도를 쓸 수 있는 면적이 작다. 모바일은 검색창+필터 요약 한 줄 → 큰 지도 → 선택한 장소의 바텀 시트 순서가 적합하다. 긴 서비스 설명은 첫 이용 도움말로 옮긴다. 지도 SDK의 저작권·필수 컨트롤은 유지한다.

### P3. 공통 디자인 규칙과 상태 표현

- 제목을 기능별로3종 정도로 정한다: 소개형·탐색형·상세형. 모든 페이지 제목을 무조건 동일 크기로 맞추지는 않는다.
- 본문14~16px, 보조 정보12~13px를 기준으로 읽기 대비를 확보한다. 푸터는 기존 작은 크기를 유지하되 색을 흐리게만 하지 않는다.
- 버튼은 주 행동·보조 행동·텍스트 행동으로 구분하고 페이지별 주 행동을 명확히 한다. 모바일 기본 높이는44~48px, 입력은48px 정도가 출발점이다.
- 카드도 모임형(사진·일정·장소·비용), 이야기형(텍스트 우선), 자료형(인원·시간·난이도·이용 조건)의 역할을 구분한다. 반경과 간격은 같은 토큰을 쓴다.
- 참가자/호스트 전환은 권한 변경으로 오해하지 않게 ‘보기 모드’의 의미를 짧게 안내한다. 비회원 로그인 유도는 카드 높이를 줄이고 현재 볼 수 있는 공개 경로를 함께 제시하되, 프로필·행사 기록의 공개 동의는 유지한다.
- 로딩·오류·검색 결과0건·권한 필요를 서로 다른 상태로 표시하고 상황별 다음 행동을 하나씩 둔다.
- 고정 크기의 광고 슬롯·이미지 비율을 유지해 로딩 중 본문이 움직이지 않게 한다. 광고 안내·동작 감소·키보드 포커스는 장식 때문에 사라지지 않게 한다.
- 공통 SearchField·FilterBar·PageHeading·EmptyState·ActionButton을 정리해 전역 CSS 덮어쓰기의 영향을 줄인다. CSS 파일 수만으로 속도 저하를 판단하지 않는다.

## 권장 실행 순서와 완료 기준

1. **공통 색상·터치·검색창:** 대표 텍스트 대비4.5:1 이상, 의미 있는 아이콘/상태3:1 이상, 작은 버튼의 실제 클릭 영역 확대, 검색 아이콘 한 줄 정렬.
2. **아카이브·번개:** 결과 위치를 앞으로 옮기고 안내·고급 필터는 펼치기 방식으로 제공. 결과가 없을 때도 명확한 빈 상태와 대안 제공.
3. **이야기·홈:** 필터 계층 축소, 배너 CTA 복원과 전환 시간 조정. 기존 북마크·태그·정렬·페이지 번호 동작 유지.
4. **지도:** 화면 면적과 선택 장소 시트 구조 개선. Naver 실제 검색·핀·현재 위치·저작권 표시 회귀 확인.
5. **공통 컴포넌트·상태:** 페이지 간 스타일과 상호작용 일관성 정리. 새 기능을 추가하지 않아도 되는 범위다.

각 단계에서320/393/720/1440px, 키보드 Tab·Enter·Escape,200% 확대, 동작 감소, 긴 제목·빈 목록·오류를 확인하고, 실기기 Android/iPhone 검증은 별도 실시한다. ‘모든 화면을 새로 만들기’는 이번 제안의 선행 조건이 아니다.
