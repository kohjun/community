# 슬리퍼 타운 요구사항 초안

작성일: 2026-11-02  
상태: 원본 기획 초안 — 현재 구현 범위와 추가 확정안 반영은 [설계·구현 기록](SLIPER_TOWN_ARCHITECTURE_2026-11-02.md) 참조  
이름: 슬리퍼 타운(가칭)

## 1. 목적과 범위

슬리퍼 안에 사람들이 아바타로 함께 접속해 이동하고, 만나서 이야기하고, 기존 웹게임을 시작할 수 있는 작은 3D 소셜 공간을 만든다. 첫 공간은 **밝고 캐주얼한 야외 광장**이다. 이용자는 게임이 없어도 광장에 머무르며 다른 사람과 교류할 수 있다.

이 문서는 개발 전 요구사항이다. 현재 게임에 이 기능이 있다는 뜻이 아니며, 아래의 제안과 미결 사항은 확정된 운영 정책이나 성능 보장이 아니다.

## 2. 현재 서비스와의 관계

- 기존 `/games`에는 게임 탐색과 게임방 생성·참가 흐름이 있다. 건배의 눈치, 수상한 경매장, 제시어 라이어, MBTI 자기소개 등의 게임과 자유 대기실이 제공된다. 실제 구성은 구현 시점의 게임 목록을 기준으로 확인한다.
- 기존 게임방은 로그인한 호스트가 만들고 진행한다. 참가자는 링크·QR로 입장하며, 준비·대기열·재접속 흐름을 사용한다. 호스트는 진행 전용이고 참가 정원에 포함되지 않는다.
- 타운 광장은 **호스트 없이 사람이 자유롭게 입장하고 나갈 수 있는 공간**을 목표로 한다. 게임은 기존 호스트 중심 게임방에서 진행한다. 공용 광장과 개별 게임방의 사용자·권한·인원 제한을 혼동하지 않는다.
- 광장 또는 게임 라운지에서 기존 게임을 선택하고 방을 개설하거나 참가하는 흐름을 제공한다. 기존 방의 로그인·게스트·정원·대기·준비·진행 권한을 그대로 확인한다. 타운 입장 권한이 게임방 입장 권한을 자동으로 보장하지 않는다.
- 참고: [웹게임 공통 구조](WEB_GAME_TEMPLATE_2026-10-30.md), [게임방 설정](GAME_ROOM_SETTINGS_2026-11-02.md), [게임 탐색](GAME_CATALOG_2026-10-31.md).

## 3. 첫 광장의 모습

- 낮 시간의 밝은 하늘과 따뜻한 햇살을 느낄 수 있는 야외 광장.
- 밝은 베이지색 바닥, 부드러운 초록색 잔디와 나무, 슬리퍼의 파란색을 활용한 안내판·부스. 둥글고 단순한 캐주얼 3D 스타일.
- 가운데에는 사람들이 모일 수 있는 분수 또는 슬리퍼를 상징하는 조형물을 둔다. 구체적인 형태는 디자인 단계에서 정한다.
- 중앙 만남의 장소, 게임 라운지, 모임 게시판, 나무 그늘과 벤치가 있는 휴식 공간을 배치한다. 한눈에 길을 찾을 수 있도록 각 장소를 표시한다.
- 카메라는 아바타와 주변 이용자를 함께 볼 수 있도록 위에서 조금 내려다보는 시점을 우선 검토한다. 실제 조작감은 모바일과 PC 시험 후 확정한다.

## 4. 첫 버전의 이용 경험

1. 슬리퍼의 웹게임 영역에서 ‘타운 입장’을 선택한다. 최종 메뉴 위치와 URL은 구현 설계에서 정한다.
2. 광장에 접속하면 기본 아바타와 닉네임이 나타난다. 같은 광장에 접속 중인 다른 이용자를 볼 수 있다.
3. 아바타를 움직이며 광장을 둘러본다. PC에서는 키보드, 모바일에서는 터치 조작을 지원한다. 화면 크기에 맞게 이동·상호작용 버튼을 배치한다.
4. 텍스트 채팅으로 이야기하고 손 흔들기 같은 간단한 인사를 나눈다. 벤치에 앉는 동작을 지원한다.
5. 게임 라운지에서 기존 게임방을 찾아 입장하거나, 권한이 있는 사용자가 기존 흐름에 따라 방을 만든다. 방이 가득 찼거나 입장할 수 없는 경우 기존 정책과 안내를 따른다.
6. 게임이 끝난 뒤 타운으로 돌아갈 수 있다. 돌아갈 광장과 정원이 찼을 때의 동작은 아래 미결 사항에서 정한다.
7. 이용자가 나가거나 연결이 끊기면 다른 이용자에게 상태가 반영된다. 일시 단절 후 재접속 시 중복 아바타 없이 현재 상태를 다시 받는다.

공간과 게임방 사이의 전환 과정에서 진행 중인 게임의 역할·준비·비공개 정보가 유출되거나 기존 게임 상태가 임의로 변경되지 않아야 한다.

## 5. 기능 요구사항

### 공용 광장과 아바타

- 타운은 별도의 진행자 없이 입장·퇴장할 수 있어야 한다. 개별 광장은 독립된 참가자 목록과 위치 상태를 가진다.
- 같은 광장의 참가자는 서로의 아바타, 표시 닉네임, 위치·방향과 걷기/정지 상태를 볼 수 있다. 닉네임과 외형에 사용할 정보의 공개 범위는 가입·게스트 정책을 정할 때 확정한다.
- 이용자 스스로 조작하는 캐릭터와 다른 캐릭터를 쉽게 구별한다. 화면 밖으로 이동하거나 접근할 수 없는 장소에 들어가는 동작은 서버에서 검증한다.
- 다른 이용자의 이동과 행동이 모두에게 자연스럽게 보이도록 동기화한다. 네트워크 지연과 재접속 시에는 최신 서버 상태를 기준으로 복구한다.
- 서버는 입장 권한, 이동 범위·속도, 상호작용 거리와 대상 등을 검증한다. 클라이언트가 임의로 보낸 위치나 정체성을 그대로 신뢰하지 않는다.

### 대화와 상호작용

- 첫 버전에서 광장 내 텍스트 채팅, 손 흔들기 등 간단한 감정 표현, 벤치 앉기/일어서기를 제공한다. 좌석 경합과 빈자리 표시는 구현 단계에서 정책을 정한다.
- 게임 라운지와 모임 게시판은 터치·클릭으로 열 수 있어야 하며, 3D 오브젝트 식별이 어려운 경우를 위해 같은 기능에 접근하는 화면 버튼을 제공한다.
- 채팅에는 기존 서비스의 텍스트 정책을 적용할 수 있어야 한다. 신고·차단, 이용 제한, 채팅 보존 기간과 공개 범위는 기존 정책과 연계해 구현 전에 정한다.
- 상대방의 비공개 계정 식별자나 비밀 게임 상태를 광장 상태 또는 채팅 메시지에 전달하지 않는다.

### 화면과 접근성

- 휴대폰 세로 화면과 PC에서 이동, 채팅, 게임방 진입, 타운 나가기를 사용할 수 있어야 한다. 화면 전환 중 조작 버튼이 주요 내용을 가리지 않아야 한다.
- 닉네임과 중요한 상태는 색상에만 의존하지 않는다. 채팅·메뉴·게임방 진입은 키보드와 보조 기술로도 접근할 수 있는 일반 UI를 제공한다.
- 움직임 줄이기 설정을 존중하고 불필요한 카메라 흔들림을 피한다. 3D 사용이 어렵거나 실패했을 때는 상태와 복귀 경로를 안내한다.

## 6. 1차 범위와 후속 기능

### 1차 목표

- 작은 야외 광장 하나와 기본 아바타.
- 여러 이용자의 실시간 접속·이동·재접속 및 닉네임 표시.
- 텍스트 채팅, 간단한 인사, 벤치 상호작용.
- 광장 안내판·게임 라운지와 기존 게임방 진입·복귀.
- 모임 게시판 UI. 실제 행사 연동 범위는 기존 권한과 공개 범위를 확인해 결정한다.

### 후속 검토

- 근접 음성채팅 및 그룹 음성방. 실제 수신 범위는 서버 측 권한과 전달 범위를 검증하고, 사용자별 음소거·차단을 고려한다.
- 아바타 외형 변경과 저장, 꾸미기 아이템.
- 카페·미니게임장·크루 공간·이벤트 무대 등 추가 장소와 맵 이동.
- 광장 내 미니게임, 이벤트 운영, 인벤토리 및 개인 공간.
- 다수 이용자를 위한 동일 광장 복수 인스턴스와 초대·이동 정책.

근접 음성, 결제·유료 아이템, 상시 유지되는 집이나 대규모 오픈월드는 1차 범위에 포함하지 않는다.

## 7. 기술 방향과 운영 고려사항

- 3D 화면은 Three.js와 React Three Fiber를 우선 후보로 검토한다. 현재 프로젝트의 Next.js·React 버전 및 모바일 브라우저 호환성을 구현 시점에 확인한다.
- 기존 게임방의 SSE는 게임 상태 갱신에 사용된다. 지속적인 아바타 이동을 위해 이를 그대로 고빈도 좌표 동기화에 사용한다고 가정하지 않는다. 양방향 실시간 게임 서버를 검토하며 Colyseus는 후보 중 하나다.
- 광장의 접속·이동·상호작용을 관리하는 서버와 기존 슬리퍼 웹 서비스의 책임을 구분한다. 기존 인증 세션 또는 게스트 세션에서 광장 접속 권한을 검증하는 연결 방식을 별도로 설계한다.
- 이동 입력, 서버 판정, 클라이언트 보간과 위치 복구를 구분한다. 초당 메시지 횟수나 지연 목표는 시험값을 측정한 뒤 정하며, 대기실의 기존 처리량이 3D 월드의 수용량을 보장하지 않는다.
- 연결 상태·인원·오류를 관찰하고, 게임 서버 장애나 배포 시 광장 이용자에게 재접속/안내를 제공한다. 대화와 위치 정보를 어떤 기간 보존할지도 구현 전에 정한다.
- 기존 운영 서버는 다른 서비스와 공유하므로, 새로운 서버·프록시·음성 인프라를 도입하기 전에 자원, 접근 권한, 배포와 비용을 점검한다. 특정 패키지 매니저, 모노레포, Docker 또는 호스팅 방식은 이 문서에서 확정하지 않는다.

## 8. 검증 기준

- 독립된 여러 브라우저 세션에서 같은 광장에 입장하고 서로의 이동·인사·퇴장을 확인한다. 연결을 끊고 다시 들어왔을 때 중복 아바타가 생기지 않는지 확인한다.
- PC와 실제 Android/iPhone 기기에서 입장, 이동, 채팅, 벤치, 게임방 이동과 복귀를 시험한다. 작은 화면·가로 화면·키보드 조작도 확인한다.
- 네트워크 지연·일시 단절·서버 재시작·광장 정원 초과를 시험하고, 표시 및 복구가 일관적인지 확인한다.
- 다른 참가자의 신분 사칭, 이동 범위 위반, 대화·상호작용 남용, 타 게임방 무단 입장과 비공개 정보 노출을 검사한다.
- 광장 인원과 장치별 프레임·메모리·발열·접속 지연 및 서버 자원을 측정한다. **4~8명은 첫 시험을 위한 제안**이며 정식 지원 인원이나 성능 보장이 아니다.
- 운영 반영 전 별도 검증 환경에서 기존 게임방 생성·입장·준비·진행·복귀에 문제가 없는지 회귀 검사한다.

## 9. 구현 전 결정할 사항

1. **입장 대상:** 회원만 공용 광장에 들어갈지, 비회원도 허용할지. 게스트 닉네임, 신고·차단과 세션 정책 포함.
2. **광장 배정:** 모두가 들어가는 공용 광장인지, 초대 전용 공간도 첫 버전에 필요한지. 정원 초과 및 친구와 같은 광장에 입장하는 방법.
3. **게임 전환과 복귀:** 타운에 머무르는 상태에서 방을 열지, 기존 페이지로 이동할지. 원래 광장이 가득 찼거나 종료됐을 때의 처리.
4. **모임 게시판:** 첫 버전에서 실제 공개 행사와 연결할지, 정적인 안내부터 시작할지.
5. **대화 정책:** 전체 광장 채팅과 근처 채팅 중 어떤 범위를 사용할지, 보존·신고·차단 정책.
6. **시각 디자인:** 아바타 형태, 조형물·부스의 상세 디자인, 필요한 에셋 제작 범위.

## 10. 권장 진행 순서

1. 광장 구성과 이용 흐름을 확정하고, 입장 대상·게임방 복귀 정책을 결정한다.
2. 한 기기에서 광장과 기본 아바타를 움직이는 시제품을 만든다.
3. 독립된 여러 브라우저에서 입장·이동·재접속을 검증한다.
4. 채팅과 인사·벤치 상호작용을 연결한다.
5. 기존 게임방 진입과 타운 복귀를 연결한다.
6. 실제 모바일 기기와 제한된 인원으로 시험한 뒤 수용 인원과 추가 범위를 정한다.
