**Sliper 운영 응답 지연 분석 — 2026-10-29 (한국 시간)**

> 후속 반영: 같은 날 서울 리전 이전을 완료해 DB 왕복 5ms와 실제 응답 개선을 확인했습니다. 아래 내용은 이전 전 분석이며 [이전 후 측정 결과](SEOUL_MIGRATION_2026-10-29.md)를 함께 참고하세요.

운영 사이트 https://sliper.kr, Ncloud 서버, 실제 Supabase 연결, 현재 소스와 배포 소스의 데이터 조회를 함께 조사했다. 애플리케이션 코드·운영 설정·업무 데이터는 변경하지 않았다.

핵심 판단은 **DB와 캐시가 없는 것이 아니라, 한국 웹 서버와 시드니 DB 사이의 왕복 지연에 인증·권한·순차 조회가 더해지는 구조**라는 것이다. 추가로 공개 게시글 이미지의 브라우저 캐시 정책이 공통 프록시의 저장 금지 헤더에 막혀 있다. Redis나 서버 증설만으로 이 두 문제를 해결할 수 없다.

1. 실제 운영 요청에서 관찰한 시간

아래 값은 소수의 순차 읽기 요청 결과이며 부하 시험이나 p95 지표가 아니다. 로그인 요청에는 기존 전용 테스트 계정으로 새로 발급받은 정상 Supabase 세션만 사용했다. 사용자 브라우저의 쿠키·토큰은 읽지 않았다.

Next.js 스트리밍으로 페이지 헤더는 20~40ms에 먼저 도착할 수 있다. 이를 콘텐츠 표시 완료 시간으로 해석하면 실제 지연을 놓친다. 위 페이지 수치는 전체 응답 수신 시간이며, 모든 이미지가 보인 시점이나 사용자의 실기기 체감 시간을 직접 뜻하지 않는다.

2. 가장 큰 원인: DB와 웹 서버의 지역 차이

운영 DB 연결 대상은 `aws-0-ap-southeast-2.pooler.supabase.com:6543`이며, Ncloud 웹 서버는 한국 KR-1이다. `ap-southeast-2`는 시드니다. 단순 `SELECT 1`을 운영 서버에서 연속 측정했을 때 약 200~206ms가 걸렸다.

[Supabase 공식 리전 문서](https://supabase.com/docs/guides/platform/regions)는 서울을 `ap-northeast-2`, 시드니를 `ap-southeast-2`로 구분한다.

이는 글 수가 적어도 요청마다 발생하는 지연이다. 독립 조회는 병렬화할 수 있지만, 인증 확인 다음 계정 상태 확인처럼 앞선 결과를 기다리는 조회와 하나의 트랜잭션 안에서 순서대로 수행하는 쿼리는 지연이 누적된다.

이번 읽기 전용 실행 계획에서 목록 본문 SQL은 계획 약 34~40ms, 실행 약 11~100ms였고, 목록 개수 SQL은 실행 약 0.1~0.7ms였다. 캐시 권한 확인 SQL은 실행 약 1.6~5.9ms였지만 애플리케이션에서 결과를 받기까지 약 415~430ms가 걸렸다. 단순 조회와 매개변수·결과 처리가 있는 실제 SQL의 왕복 시간은 동일하지 않으므로, 모든 쿼리를 200ms로 고정해 계산해서는 안 된다. 다만 DB 내부 계산보다 통신·프로토콜·응답 대기가 큰 비중을 차지하는 것은 확인된다.

목록 SQL에는 여러 집계와 가시성 조건이 포함되어 있어 SQL 단순화도 도움이 된다. 이번 결과만으로 특정 인덱스 누락이나 전체 테이블 스캔을 주원인으로 단정할 근거는 없다. JIT 추가 확인 표본에는 JIT 실행이 보고되지 않았다. Supabase 전체 부하·다른 시간대 CPU·풀러 대기는 대시보드 지표를 별도로 봐야 한다.

3. 로그인 후 느려지는 이유

관련 소스:

- `src/proxy.ts:38`: 세션 갱신·검증을 위한 `getClaims()`.
- `src/server/identity.ts:21`: 별도로 `getUser()`를 기다린 뒤 회원 제한 상태를 DB에서 조회.
- `src/app/api/auth/session/route.ts:14`: 이후 닉네임과 운영 권한을 조회.
- `src/components/session-provider.tsx`: 동시 요청을 합치고 10초 재확인 제한을 두지만, 별도 API 요청마다 서버 측 인증은 다시 수행됨.

`getClaims()`가 항상 외부 요청을 한다고 단정할 수는 없다. 비대칭 서명 키에서는 캐시된 공개 키로 검증할 수 있고, 대칭 서명에서는 Auth 서버 검증이 필요하다. 반면 `getUser()`는 최신 사용자 정보를 위해 네트워크 요청을 한다. [Supabase 공식 인증 메서드 설명](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs#choosing-an-auth-method)이 이 차이를 설명한다.

현재 React `cache()`가 동일 서버 요청 안에서 신원 조회를 합치고 있으므로, 요청 안에서 매번 완전히 중복 호출하는 구조라고 표현하면 부정확하다. 문제는 각 페이지·API가 원격 Auth 확인과 DB 회원 상태 확인을 거친 뒤 실제 데이터를 읽는다는 점이다.

일반 조회에서 검증된 claims를 활용할 수 있는지 검토할 가치가 있다. 다만 Auth 측 계정 정지·삭제 반영, 토큰 만료·갱신, 탈퇴·차단 정책의 의미가 달라지지 않도록 설계하고 검증해야 한다. 비검증 세션이나 클라이언트가 보낸 사용자 ID를 신뢰하는 방식으로 바꾸면 안 된다.

`src/server/community-queries.ts:104`는 캐시 적중 후에도 최신 삭제·숨김·차단·개인 반응·모집 상태를 DB에서 확인한다. 별도 진단 프로세스에서 캐시 적중 횟수 증가와 SQL 1회를 확인했다. 캐시가 고장 나서 매번 본문 전체를 재조회하는 것과는 다르다. 이 SQL이 약 0.42초 걸리므로 메모리 캐시 적중이 수 ms 응답으로 연결되지는 않는다.

또한 `src/server/community-service.ts:1029`는 글·댓글·반응·투표·프로필 변경 후 발견용 캐시 전체를 비운다. 실제 이용이 늘면 관계없는 목록도 다시 채워야 할 가능성이 있다. 조회수·방문 기록 자체가 이 전체 초기화를 수행하는 것은 아니다.

캐시 실험은 **별도 프로세스·단일 연결·읽기 전용 트랜잭션**에서 했다. 실제 웹 프로세스의 캐시를 비우거나 적중률을 읽은 것이 아니다. 진단에서는 병렬 SQL도 한 연결로 직렬화되므로, 거기서 측정한 전체 수행 시간을 그대로 운영 응답 시간으로 제시하지 않았다. 운영 웹 프로세스의 시간대별 캐시 적중률은 아직 계측되지 않았다.

5. 이미지: 원본 캐시와 브라우저 캐시 정책이 서로 맞지 않음

`src/server/image-delivery.ts:15`는 일반 게시글 이미지에 `private, no-cache, must-revalidate`와 ETag를 제공한다. 브라우저에 저장하고 재검증해 304로 재사용하려는 설계다. 회원 전용 기록·모임 이미지는 별도로 `no-store`를 유지한다.

그러나 `src/proxy.ts:39`는 `/api/media/{id}`를 포함한 응답에 공통 `private, no-store`를 설정한다. 공개 이미지 한 장의 실제 200 응답과 조건부 304 응답 모두 `private, no-store`였다. 즉 코드의 재검증 캐시 의도가 운영 응답에 반영되지 않는다. 프록시의 범용 헤더 적용과 미디어 경로 정책의 충돌이 우선 수정 대상이다.

같은 공개 이미지(약 216KB)를 읽기 전용으로 반복 조회한 결과:

- 일반 조회: 약 0.53~0.55초.
- ETag를 직접 보낸 조건부 조회: 304, 본문 0바이트, 약 0.44초.
- 별도 새 Chrome의 초기 이미지 요청에서는 약 2.54초도 관찰됨. 저장소 최초 조회·전송·동시 자원 로딩의 영향을 분리한 결과는 아니므로, 전부 Storage 지연이라고 단정하지 않음.

304에서도 서버는 접근 권한 확인을 수행한다. 브라우저 캐시 헤더를 고쳐도 DB 왕복은 남는다. 이 수정은 불필요한 이미지 본문 전송을 줄이는 효과이며 모든 이미지 요청을 0회로 만드는 수정은 아니다.

전체 페이지의 `no-store`를 일괄 제거해서는 안 된다. 쿠키 갱신 응답과 개인 정보는 공유 캐시 대상이 아니며, 회원 전용 미디어의 접근 검사도 유지해야 한다.

6. 화면마다 순차 조회가 지연을 더함

- `src/server/profile-service.ts:15`: 프로필 → 프로필 사진 → 활동 통계 → 개수 집계를 차례로 기다린 후 최근 글·북마크·댓글·이력 4개를 병렬 조회한다. 서비스 호출 자체에는 SQL 8개가 있다. 마이페이지 2.87초의 주요 개선 대상이다.
- `src/server/post-page.ts:29`: 상세 본문·댓글 조회 후 알림함을 별도로 기다린다. 본문이 알림함 결과까지 기다려야 하는 의존성은 줄일 수 있다.
- 홈과 목록 API는 이미 피드·알림을 `Promise.all`로 읽고 있으며, 게시글 묶음도 UNION 기반으로 조회한다. 모든 홈 섹션이 순차 조회된다거나 글 한 개마다 별도의 작성자 쿼리가 발생하는 전형적인 N+1이라고 단정할 근거는 없다.
- 좋아요·댓글·신청 같은 쓰기는 인증, 제한 검사, 트랜잭션, 최신 결과 조회가 포함된다. 이번에는 실사용 데이터 변경을 피하기 위해 쓰기 버튼의 실제 완료 시간을 새로 측정하지 않았다. 읽기 지연과 동일한 원격 왕복이 영향을 줄 구조임은 코드에서 확인된다.

7. 서버 자원과 브라우저 확인

관찰 시점 Ncloud 부하는 0.09~0.15, 가용 메모리는 약 6.5GB, 루트 디스크 사용률은 32%, Sliper 웹 메모리는 약 220MB였다. 웹·알림·영상·TLS 서비스와 기존 다른 사이트는 정상 응답했다. 현재 느린 읽기의 우선 원인을 인스턴스 메모리 부족이라고 볼 증거는 없다. 순간 관찰이므로 사용자가 몰릴 때도 충분하다는 뜻은 아니다.

새 Chrome에서 데스크톱과 393px 모바일 레이아웃을 확인했다. 홈 초기 스크립트 전송량은 약 0.50MB였고, 긴 작업의 최대치는 약 64~68ms였다. 이번 PC에서 수초 단위 JavaScript 정지는 재현되지 않았다. 모바일 결과는 레이아웃 에뮬레이션이며 실제 저사양 Android의 CPU·통신 측정이 아니다.

보이는 메뉴의 Next.js RSC 사전 요청은 관찰됐지만 다수가 짧은 로딩 경계 응답이었다. 이를 모두 전체 페이지 DB 조회로 계산하거나 사전 읽기를 전부 끄면 오히려 이동이 느려질 수 있다. 화면 아래 자료 추천은 별도 `/api/library` 요청으로 약 0.47~1.11초가 걸렸다.

리전 변경은 연결 문자열의 리전 이름만 고쳐서 되는 작업이 아니다. 프로젝트 이전·새 프로젝트 여부, 기존 DB/Auth/Storage/Realtime 데이터와 외부 로그인 콜백의 이전 절차를 검토해야 한다. 이번 조사에서는 이전이나 새 유료 서비스 생성을 수행하지 않았다.

Redis 공유 캐시는 여러 웹 인스턴스의 캐시를 일치시키거나 선택한 데이터를 공유할 때 도움이 된다. 지금처럼 한 웹 프로세스가 이미 메모리 캐시를 사용하고, 적중 후에도 먼 DB의 권한 확인을 기다리는 구조에서는 Redis 추가만으로 큰 폭의 개선을 약속하기 어렵다. 읽기 권한을 오래 저장하는 방식으로 속도를 얻는 것도 현재 삭제·차단 정책과 맞지 않는다.
