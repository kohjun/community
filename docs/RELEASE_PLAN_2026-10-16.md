# Sliper 구현 현황과 실서비스 출시 순서

> 운영 배포 이후 갱신: HTTPS·실제 소셜 로그인·Android 테스트 푸시·경보 이메일은 완료했다. 정기 백업 자동화·별도 보관처는 사용자 요청으로 보류했다. 현재 순서는 [최신 후속 작업 목록](NEXT_WORK_PLAN.md)을 따른다. 아래는 이전 날짜의 출시 계획이다.

> **2026-10-26 후속:** HTTPS Compose·Node 24 Linux 이미지·진행 기반 워커 상태 점검·원격 백업 사전 검사를 보완했다. 아래에는 당시 검증 기록이 포함된다. 최신 명령과 검증 범위는 [Ncloud 실행 구성 준비](NCLOUD_RUNTIME_PREPARATION_2026-10-26.md)를 참고한다.

기준일: 2026-10-16 · 프로젝트: `C:\Sliper`

현재 단계는 **핵심 기능 구현과 Supabase 전환 완료 → 공개 호스팅 및 운영 검증 준비**다. A~F의 기능 개발과 커뮤니티 성숙화 1~5단계는 구현했지만 실제 결제·휴대폰 푸시·공개 배포·운영 복구를 완료한 상태는 아니다. 추가 대형 기능보다 기존 흐름을 배포 환경에서 검증하는 것을 우선한다.

현재 PC가 Next.js 웹·영상 워커·알림 워커를 실행한다. 콘텐츠와 회원 데이터는 Supabase에 저장되지만 PC를 끄면 웹 서비스는 멈춘다.

## 확정된 배포 방향

- **호스팅:** Ncloud 인스턴스 서버. 서버 예산은 사용자가 제시한 월 약 8만 원이며, 구체적인 사양·약정·공인 IP·디스크·트래픽·세금의 최종 견적을 확인하기 전 총 운영비로 확정하지 않는다.
- **예정 공개 주소:** `https://sliper.kr`. 도메인은 아직 구매 전이며 등록 가능 여부·소유권 확보를 먼저 확인한다. 현재 APP_ORIGIN을 미구매 도메인으로 바꾸지 않는다.
- **실행 구성:** Ncloud Linux 서버에 HTTPS 프록시·웹·알림·영상 워커, 데이터는 기존 Supabase 사용. 서버는 아직 생성 전으로 확인했으며 OS·사양·접속은 신규 생성 단계에서 준비한다.
- **다음 작업:** [Ncloud 배포 실행 순서](NCLOUD_DEPLOYMENT.md)에 따라 서버 접속 → Linux 컨테이너 검증 → DNS/HTTPS → 운영값/로그인 → 회원 통합 검증을 진행한다.

## 2. 기반 구성과 확인한 범위

- **DB:** Supabase PostgreSQL + Drizzle, 마이그레이션 67개·앱 테이블 80개. 실행 역할 분리·RLS·원장 실제 감사 PASS12/WARN1/FAIL0. WARN은 pooler 이후 내부 TLS 구간을 클라이언트에서 직접 관측하지 못했다는 뜻이다.
- **인증·회원:** Supabase Auth. 사용자 확인과 서버 기록을 통해 카카오·Google 로그인, 기본 정보 입력 동선·프로필 생성·로그아웃 확인. 연락처 입력은 번호 소유 인증과 구분한다.
- **파일:** Supabase private Storage. 사진·프로필·영상·영상 원본의 로컬 참조가 0개이며, 실제 임시 파일 업로드·읽기·삭제 확인. 기존 개발 DB의 데모 데이터는 자동 이전하지 않았다.
- **실시간:** Redis를 활성 실행 경로에서 제외. 비공개 Supabase Broadcast로 방 UUID만 전달하고, 기존 SSE가 매번 DB 권한을 확인한다. 독립 서버 클라이언트 간 수신·비회원 채널 접근 거부 확인.
- **클라우드 전용 보호:** 로컬 DB·파일·테스트 인증으로의 전환 차단, TLS와 제한 실행 역할 검사. 비밀키는 서버 설정에만 둔다.
- **검사:** 직전 전체 검사 959/959, 비밀값·서식·타입·Drizzle 검사와 webpack 운영 빌드 통과. 서버 trace110개 오류0개, 실제 standalone 파일2505개에서 비밀 파일0개·영상 워커 바이너리0개 확인.
- **배포 준비 파일:** `Dockerfile.web`, `Dockerfile.notification-worker`, `Dockerfile.video-worker`, `compose.production.yaml`, `production.env.example`. Compose 구조 검사는 통과했지만 실제 Linux 컨테이너 빌드·기동은 미검증.

현재 설정의 `deploy:check`에서 미완료 FAIL은 **공개 HTTPS 원본 주소, AdSense 설정**이다. 이 도구는 설정 형식 검사다. DB 역할·마이그레이션 경고는 별도의 실제 DB 감사 결과와 함께 판단하며, 소유자 키를 웹 환경에 다시 넣어 경고를 지우지 않는다. 광고를 사용하지 않는 베타는 해당 환경에서 광고 설정을 완전히 비활성화하고 진행할 수 있다.

별도 도메인 구매 전에 호스팅이 제공하는 HTTPS 주소로 스테이징 검증을 시작할 수 있다. 운영 서비스 주소를 바꾸면 OAuth·지도·쿠키 원본 설정도 다시 확인한다. 구체적인 서비스 생성과 요금제 선택은 사용자 계정·예산을 확인한 뒤 진행한다.

결제 자동화는 **유료 자동 신청을 열기 전 필수**다. 초기 베타는 무료 모임과 현재 구현된 외부 신청·담당자 수동 승인으로 검증하고, 결제 플랫폼이 정해지면 자동 승인·환불·정산을 추가 검증하는 순서를 권장한다. 외부 플랫폼에서 실제 결제되었다는 확인 없이 참가를 자동 확정하지 않는다.

## 4. 남은 코드 보완과 환경 설정의 구분

**설정·계정 준비:** 호스팅/HTTPS·OAuth 허용 주소·지도 도메인·운영 VAPID·실제 문의 경로·광고 승인/단위. 이미 만들어진 연결 코드에 운영값을 넣는 작업이 중심이다.

**추가 구현 또는 배포 자동화:** 미첨부 파일 정리의 자동 스케줄과 실패 알림, 워커 상태·장애 감시, 배포 CI와 롤백 절차, 서비스 내 탈퇴 후 외부 Auth 계정/연결의 보관·삭제 처리 확정 및 반영. 외부 결제 공급자별 어댑터·환불 확인 자동화는 공급자 선정 후 구현한다.

**실제 검증:** 공개 환경에서 회원 간 권한·QR 카메라·전체 영상 변환·Android/iPhone 알림·서버 재시작·DB와 객체 복원·부하. 단위 테스트와 설정 PASS로 대체하지 않는다.

**출시 뒤 판단:** 대용량 파일 전송·Range 처리 개선, 사용량에 따른 CDN/캐시·검색·워커 증설, 자동 매칭·추가 추천. 2026-10-25 후속 수정에서 영상 Range는 권한 확인 후 실제 부분 스트리밍으로 전환했다. 후속 CDN/증설은 운영 트래픽을 측정해 판단한다.

## 5. 제한 공개 베타의 검증 시나리오

1. 두 회원이 각각 카카오/Google로 로그인하고 기본 정보를 저장한다. 비회원·차단·탈퇴 회원의 쓰기/비공개 접근도 확인한다.
2. 주최자가 실제 사진·영상과 신청 질문이 있는 무료 모임을 만들고 참가자가 신청한다.
3. 외부 링크 행사는 외부 신청 번호 제출·담당자 승인으로 참가 확정한다. 중복 승인·정원 초과를 막는지 확인한다.
4. 주최자 공지가 참가자에게 갱신되고, 참가자는 메시지를 보낼 수 없으며 취소 뒤 방 접근이 해제되는지 확인한다.
5. Android와 iPhone 홈 화면 웹앱에서 알림 허용·수신·알림 클릭·거부 복구를 확인한다. 웹의 알림함 생성도 함께 확인한다.
6. 현장에서 담당자가 QR로 출석을 확인하고 중복 입장을 막는다. 종료 확인·회고 발행·제작진 수락·포트폴리오·기록 검색을 이어서 검증한다.
7. 영상 워커 처리 중 재시작·신호 유실 후 공지 재조회·알림 재시도에서 중복·자료 손실이 없는지 확인한다.
8. 별도 복원 대상으로 DB와 파일을 복구하고 행사·회원·미디어 권한을 확인한다. 복원 환경의 결제·푸시 발송은 끈다.

최초 베타에서는 현재 noindex를 유지하고, 공개 확대 때 검색 노출 경로·robots/sitemap을 별도 확정한다. noindex는 접근 통제를 대신하지 않으므로 초대만 받는 비공개 베타라면 별도 접근 제한도 필요하다.
