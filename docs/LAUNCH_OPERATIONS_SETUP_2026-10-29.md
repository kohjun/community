## 관리자 지정은 나중에 실행

웹에서 최초 관리자 선점이 가능한 가입 버튼이나 공개 bootstrap API를 제공하지 않는다. 기존 서버 접근 권한을 가진 소유자가 프로필의 공개 UUID를 명시해 지정한다. 비밀번호·비밀키를 명령 인수나 채팅에 넣지 않는다.

1. 사용할 본인의 Google/Kakao 계정으로 로그인한다.
2. 자신의 플레이어 프로필 `/players/공개UUID`를 확인한다. Auth 내부 UUID·이메일 대신 공개 UUID를 사용한다.
3. 신뢰하는 로컬 프로젝트/서버 터미널에서 비공개 환경 설정에 `MIGRATION_DATABASE_URL`을 준비한다. 운영 웹에 이 소유자 연결을 배포하지 않는다.
4. 변경 내용을 먼저 확인한다. 이 명령은 권한을 바꾸지 않는다.

```powershell
npm run staff:grant -- --public-id 공개UUID --role admin
```

5. 출력의 previousRole을 확인해 같은 값으로 적용한다. 최초 지정은 none이다.

```powershell
npm run staff:grant -- --public-id 공개UUID --role admin --apply --expected-role none --reason "본인 소유 계정을 운영 관리자로 지정"
```

6. `/admin`, `/admin/operations`, `/admin/readiness`에서 신고·문의·준비 상태를 확인한다. 일반 회원은 접근할 수 없어야 한다.

moderator로 범위를 낮추거나 none으로 해제할 수 있다. 실제 변경은 감사 원장에 남고, 중복 적용은 새 이력을 만들지 않는다. 예상한 기존 권한이 바뀌었으면 다시 사전 확인한다. 마지막 활성 admin을 이 명령으로 해제할 수 없다. 테스트 계정용 `--local-admin`은 격리된 127.0.0.1:55432/sliper_dev에서만 실행된다. 이번 작업에서는 실제 운영 계정을 지정하지 않았다.

## 공개 정책과 문의

- 비로그인·로그인 실패·탈퇴 후에도 `/support`에서 공개 메일을 확인할 수 있다. 로그인 회원의 기존 문의 원장 권한을 확대하지 않는다. 공개 페이지는 Auth/DB를 조회하지 않고, 회원 문의 내역은 `/support/inbox`로 분리했다.
- 메일 링크는 사용자의 이메일 앱을 연다. 사이트가 대신 이메일을 전송하거나 가짜 접수 번호를 만들지 않는다. 실제 메일 수신과 응대 책임은 운영자가 확인한다.
- 이용약관·개인정보 항목/목적·현재 보관/삭제 범위·외부 서비스·권리 요청을 공개한다.
- 원장별 보유/파기 기간과 클라우드 위탁·국외 처리 조건은 최종 확인 전이다. 이를 완료로 표시하지 않고 관리자 준비 화면에 남긴다.
- 사업자 등록·신고와 실제 보관 조건 검토 후에만 사업자 항목과 `SLIPER_PRIVACY_POLICY_REVIEWED=true`를 설정한다. 현재 방침 페이지를 완성된 법률 검토로 해석하지 않는다.

공개 설정 키는 `.env.example`, `production.env.example`에 있다. 운영 값 변경은 별도 공개 설정 파일로 적용하며 Supabase·OAuth·결제 비밀 설정을 복사하지 않는다.

## 실제 콘텐츠와 무료 운영 도구

아카이브에서 새로 작성한 기본 체크리스트·10분 오프닝 큐시트·행사 회고 양식 3개를 내려받을 수 있다. 이들은 실제 행사나 판매 실적이 아닌 무료 양식이다. 기존 4주 운영 가이드와 연결한다.

운영자가 실제 주최자 3~5명의 동의를 받고 한 지역·2~3개 취향에 집중해 모임을 등록한다. 베타 목표는 실제 행사 3회와 공개 진행 자료 3개다. 샘플 글은 샘플로 유지한다. 관리자 준비 화면은 샘플 제외 예정 모집·공개 자료와 샘플/일반 글 수를 확인한다.

## 안정성

- 이미지의 공통 인증 프록시가 `no-store`를 덮어쓰지 않도록 GET/HEAD의 쿠키 갱신만 생략한다. 실제 파일 라우트의 인증·차단·숨김·부모 콘텐츠 권한은 그대로 확인한다.
- 공개 글 이미지는 `private, no-cache, must-revalidate`와 ETag로 브라우저가 재검증한다. 익명 공유 CDN 캐시나 장기 공개 URL을 만들지 않는다. 비공개/행사 기록/프로필 자산은 권한과 기존 보관 헤더를 유지한다.
- 백업 정기 실행·별도 보관처와 카메라 검증은 이전 사용자 보류를 유지한다. 준비 여부와 외부 저장소/복원 대상 확인이 필요하다.
- 2026-10-29 읽기 전용 `ua status --format json`에서 Ubuntu Pro/ESM **attached=false**를 확인했다. Ubuntu 20.04의 보안 지원 연결 또는 공유 서버 OS 이전이 필요하다. 기존 사이트의 SSH·OS·서비스를 변경하지 않는다.
- 제한 부하는 새 버전의 loopback 미리보기에서 낮은 동시성으로 읽기 요청만 수행한다. 실제 동시 참가·알림·영상 수용량을 보장하는 시험은 별도다.

## 검색과 광고

`SLIPER_SEARCH_INDEXING_ENABLED=true`와 정식 production HTTPS 주소에서 공개 목록·안내만 canonical/색인을 허용한다. 기본값은 비공개이며 개발·IP·개인 화면은 제외한다. 회원 기록·개인 프로필·구매 본문·검색 결과는 사이트맵에 넣지 않는다. `/robots.txt`, `/sitemap.xml`은 DB에 접근하지 않는다.

게시자 `ca-pub-7888129551635907`로 사이트 확인 메타 태그와 `/ads.txt`를 준비한다. 실제 광고 요청은 비활성으로 유지한다. AdSense 계정에서 사이트 sliper.kr 추가·소유 확인·검토 요청은 계정 소유자가 해야 한다. 승인 후 광고 단위 ID를 설정하고 실제 게재를 확인해야 한다. 운영 화면의 준비 표시가 Google 승인을 뜻하지 않는다.

## 안정성 후속 실행 조건

서울 프로젝트의 읽기 전용 백업 사전 검사는 PASS 4 / WARN 3 / FAIL 0이었다. Postgres 17, 앱 테이블 87개·마이그레이션 74개, 로컬 파일 참조 0개, 참조 파일 9개를 확인했다. 이는 파일 바이트 백업이나 복원 성공을 뜻하지 않는다.

보류된 백업을 재개할 때는 새 서울 프로젝트의 `BACKUP_DATABASE_URL`(5432 direct/session), 독립된 비어 있는 복원 프로젝트, 암호화 사본 보관처와 복호화 키의 별도 보관을 먼저 준비한다. 기존 운영 프로젝트를 복원 대상으로 사용하지 않는다. 정기 작업의 실패 경보와 실제 복원 연습까지 완료한 뒤 자동화를 켠다. DB 백업만으로 Storage 파일 바이트가 보관되지는 않는다.

공유 OS 이전은 현재 두 사이트의 Node 버전·Nginx·Sliper 워커·인증서·포트를 목록화하고, 지원되는 LTS의 별도 검증 환경에서 실제 로그인을 포함해 확인한 뒤 유지보수 시간을 정한다. 새 유료 인스턴스나 Ubuntu Pro 계약은 이번 작업에서 만들지 않았다. 무작정 SSH 비밀번호 접속을 끄거나 원격 연결 수단을 바꾸지 않는다.

권장 초기 복구 목표는 운영자가 허용 가능한 데이터 손실/복구 시간을 정한 뒤 문서화한다. 아직 측정하거나 합의하지 않은 수치를 운영 보장으로 공지하지 않는다. iPhone·정식 도메인 실기기 알림·보류된 카메라 검증은 별도로 남아 있다.
