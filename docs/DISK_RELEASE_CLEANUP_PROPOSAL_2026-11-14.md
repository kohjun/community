## 안전 검증 결과

- 프로세스 cwd·실행 파일·명령의 경로·열린 파일·메모리 매핑, 서비스·예약 작업·프록시 구성 참조를 조사했다. 후보에 현재 실행 참조는 없다.
- 12개 후보의 경로, 파일 트리 지문, 크기, 마운트, 하드링크, 실제 데이터 의심 경로 검증을 통과했다.
- 새 두 배포본 사이 약 1.07GB의 공유 하드링크는 보존 대상 안에 있으며, 이번 확보량에 중복 계산하지 않았다. 후보는 외부 파일과 공유 하드링크가 없다.
- 외부 심볼릭 링크는 `/var/lib/sliper/web-cache`를 향하는 캐시 링크다. 삭제 시 링크만 처리하고 대상 디렉터리는 따라가지 않는다.
- 과거 배포명은 일부 상태 JSON에도 남아 있으나 배포 완료 감사 기록이다. 내용 해시를 고정하고 실행 설정·스크립트에서 이 파일을 읽는 참조가 없음을 확인했다. 기록 파일 자체는 보존한다.
- 웹·실시간 서버·Redis·알림·영상·모니터·Nginx 및 새 미리보기 8개 서비스의 PID와 실행 경로를 확인했다. 기존 Contenido 프로세스도 보존한다.
- Sliper API·운영 감시·실시간 서버 health와 기존 사이트가 모두 HTTP 200이다.
- 삭제됐지만 열린 상태로 공간을 점유하는 파일은 조사 스크립트 임시 파일 약 8KB뿐이었다. 릴리스 누적이 주요 정리 대상이다.

## 승인 후 실행 절차

1. current·서비스 PID·미리보기·실행 참조·릴리스 목록·파일 지문을 다시 검사한다. 달라지면 삭제를 중단하고 새 상태로 재검사한다.
2. 승인된 정확한 12개 경로만 symlink 방어가 적용된 방식으로 하나씩 삭제한다. 각 단계에서 참조를 재검사한다.
3. 실제 확보량, 남은 릴리스, current, 프로세스 PID·시작 시각과 HTTP 정상성을 전후 비교한다.
4. 정리 완료 보고서를 남긴 후 낙서톡·단서각 구현을 시작한다.

이번 범위에는 DB·업로드·Supabase 자료·runtime·incoming·ops·공용 웹 캐시·환경 설정·인증서·기존 별도 사이트·로그 삭제가 포함되지 않는다. 별도로 systemd 저널 약 4GB도 확인했지만 이번에는 보존한다.

## 승인 및 재발 방지

이전 사용자 지시인 “삭제 전에 대상 목록과 예상 확보 용량을 사용자에게 보고”, “사용자 승인 없이 파괴적인 작업을 수행하지 않는다”에 따라 이 목록에 대한 승인을 받은 뒤 정리한다.
