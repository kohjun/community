## 설계 범위

커뮤니티의 글과 댓글로 예능 기반 이벤트를 소개하고 소통한다. 아래 기본 관계표는 초기 커뮤니티 구조다. 후속 확장에서는 행사 일정·정원·신청·외부 결제 확인·공지방·QR 참가·환불·크루 관리 테이블을 추가했고 각 기능 문서에 현재 흐름을 기록했다.

| 테이블           | 목적                                           | 주요 무결성                                              |
| ---------------- | ---------------------------------------------- | -------------------------------------------------------- |
| profiles         | 회원 기본 정보, 관심사, 공개용 ID              | id는 Supabase auth.users FK, public_id 별도 UUID         |
| categories       | 9개 관심 카테고리 + 3개 창작 게시판            | enum slug PK, 정렬 순서 unique                           |
| posts            | Markdown 글, 모집 정보, 투표 설정, 선택적 익명 | 회원·카테고리 FK, 글 상태·길이 검사                      |
| comments         | 중첩 댓글                                      | 부모와 같은 글 복합 FK, 부모·글·ID 변경 금지             |
| media_assets     | 이미지 메타데이터                              | 업로더와 글 작성자 일치, 무작위 파일명, 용량·형식 검사   |
| post_likes       | 게시글 좋아요                                  | (post_id, user_id) PK                                    |
| bookmarks        | 개인 북마크                                    | (post_id, user_id) PK                                    |
| post_daily_views | 날짜별 브라우저 방문자                         | (post_id, visitor_hash, viewed_on) PK                    |
| notifications    | 댓글·답글 알림                                 | 수신자·원본 관계 검사, (recipient_id, comment_id) unique |
| poll_votes       | 회원별 선택 및 투표 집계                       | (post_id, user_id) PK, 유효한 항목만 선택                |
| activity_events  | 활동점수 적립 기록                             | (user_id, source_key) PK, 서버 일별 한도                 |

관계의 중심은 `auth.users → profiles → posts → comments`다. 카테고리는 글과 연결되고, 좋아요·북마크는 회원과 글을 연결한다. 이미지의 글 연결은 글쓰기 중 업로드를 위해 선택적이다.

## 저장소와 공개 응답의 경계

관리형 `auth.users`는 FK 대상으로만 참조한다. Drizzle이 이 테이블을 생성하거나 변경하지 않는다. OAuth 공급자와 계정 연결, 비밀번호·토큰은 Supabase Auth가 담당한다.

앱 테이블은 `sliper` 스키마에 격리하며 **Supabase Data API의 Exposed schemas에 추가하지 않는다**. 모든 테이블에 RLS를 켜고 `anon`, `authenticated`, `PUBLIC`의 직접 접근 권한을 회수한다. 기본 공개 정책을 만들지 않는다. 익명은 비회원이나 Supabase의 anonymous auth 기능을 뜻하지 않고, 로그인 회원의 표시 옵션이다.

서버의 직접 DB 연결은 신뢰 경계 내부다. 현재 개발용 연결은 테이블 소유자 연결을 전제로 하며, **소유자는 RLS를 우회하므로 RLS가 서버 요청의 인가를 대신하지 않는다**. 서비스 계층은 소유권 검사를 수행한다. 현재 사용자 ID는 엄격히 제한된 개발용 어댑터에서 얻으며, OAuth 연동 시 검증된 Supabase 세션으로 교체한다. 운영 배포 전에 DDL 권한을 분리한 전용 런타임 DB 역할을 설정하고 실제 연결로 접근을 검증한다.

`src/db/client.ts`는 `server-only`로 보호한다. 저수준 `connection.ts`는 CLI와 이 서버 모듈에서만 사용한다. UI나 Route Handler에 DB 행을 그대로 반환하지 않는다.

```text
RSC 조회 ────────────────┐
Server Actions 변경 ────┼→ 인증·입력 검증 → 공통 서비스/인가 → Drizzle → PostgreSQL
Route Handlers HTTP ────┘                                      ↓
                                                공개 DTO로 명시적 변환
```

서버 내부 타입과 공개 DTO는 별도다. 익명 DTO에는 auth ID, 공개 프로필 ID, 닉네임, 아바타, 프로필 링크를 넣지 않는다. 본인 여부는 서버에서 계산한 `isMine`만 전달한다. 첫 버전 익명 이름은 모두 `익명`이며 글 간 추적 가능한 번호를 발급하지 않는다. 알림에도 작성자 정보 스냅샷을 저장하지 않는다.

## 댓글과 삭제

댓글은 인접 목록 `parent_id`를 사용한다. 복합 FK로 다른 글의 댓글을 부모로 지정하지 못한다. 삽입 시 부모가 먼저 존재해야 하고 삽입 이후 부모·글·ID를 바꿀 수 없어, 다중 행 삽입 및 이동을 통한 순환을 막는다. 깊이 수치에 제품 제한은 두지 않는다.

무제한 깊이를 한 응답에 무제한 로드한다는 뜻으로 해석하지 않는다. API는 부모별 커서 페이지네이션을 사용하고 프론트는 반복 처리·답글 펼치기를 사용한다. 작은 화면에서는 들여쓰기를 제한하고 답글 대상을 표시한다.

소프트 삭제 시 DB 트리거가 본문을 비우며, 글 제목도 삭제 표시로 바꾼다. 삭제 댓글은 관계만 유지하고 공개 DTO에서 본문·작성자를 제거한다. 삭제를 취소해 내용을 되살리는 기능은 없다. 회원 탈퇴는 profile과 개인 반응·알림을 삭제하고 기존 글·댓글의 작성자 연결을 null로 바꾸어 대화를 유지한다. 탈퇴와 글 삭제는 서로 다른 작업이다.

## 조회수·반응

날짜는 DB가 `Asia/Seoul` 기준으로 기록하고 클라이언트가 보낸 날짜를 덮어쓴다. 방문자는 서버에서 검증한 무작위 HttpOnly 쿠키 ID를 사용하도록 설계한다. 쿠키 발급·서명 검증·조회 API까지 구현되어 있다.

방문자 해시는 서버 비밀키와 게시글 ID를 포함한 HMAC-SHA256이다. 서로 다른 글에서 같은 방문자를 연결하기 어렵게 만든다. IP, 사용자 에이전트 원문은 저장하지 않는다. UUID를 소문자로 정규화하여 대소문자 변경으로 중복 판정을 우회하지 못하게 한다.

조회수는 브라우저별이며 다른 기기·시크릿 모드·쿠키 초기화까지 같은 사람으로 식별하지 않는다. 같은 브라우저는 로그인 전후에도 같은 쿠키를 유지한다. 서비스는 `INSERT ... ON CONFLICT DO NOTHING`을 사용한다. 좋아요·북마크도 토글 대신 `active: true/false` 입력으로 멱등성 있게 구현한다.

1단계에는 카운터 캐시를 두지 않고 실제 행 집계를 원본으로 삼는다. 트래픽이 커지면 집계 테이블이나 캐시를 추가한다. 일별 조회 행을 삭제하면 총 조회수가 줄므로 보존 정책은 별도 집계 도입 후 결정한다.

## 알림

최상위 댓글은 글 작성자에게, 답글은 부모 댓글 작성자와 글 작성자에게 전달하는 규칙을 사용한다. 수신자가 같으면 1건이며 직접 답글 유형을 우선한다. 자기 자신의 활동은 알리지 않는다. DB는 알림 대상의 관계와 중복을 검사한다.

댓글 저장과 알림 생성은 같은 트랜잭션에서 수행한다. 현재 트리거는 잘못된 알림 삽입을 막는 역할이며 알림을 자동 생성하지 않는다. 알림 목록·읽음 처리는 세션 수신자 조건을 반드시 사용한다.

## 이미지와 Markdown

이미지는 글당 최대 10개, 파일당 10 MiB, JPEG/PNG/WebP/GIF로 시작한다. 원본 파일명이나 회원 ID가 포함되지 않은 UUID 파일명을 저장한다. 업로더와 글 작성자는 일치해야 하고 업로드 메타데이터의 소유권은 재할당할 수 없다.

브라우저 Canvas는 사진을 하나씩 준비해 원본보다 작은 WebP를 전송한다. API 미지원/실패 시 입력 한도 안의 원본을 사용한다. 서버는 실제 바이트 디코딩·형식/치수 검사, WebP 재인코딩/메타데이터 제거와 글 상태·첨부 관계 확인을 다시 수행한 뒤 `/api/media/{id}`로 제공한다. local/private Supabase 어댑터와 행별 저장 방식은 구현되어 있으며 원격 버킷 검증·장기 파일 보존/파기는 후속 과제다.

Markdown은 원문을 보관한다. 렌더링은 raw HTML 비활성화, URL 프로토콜 제한, 출력 정제로 처리한다. 업로드 이미지는 서버가 확인한 자산 참조로 연결한다. 단순 `.md` 문자열 저장이나 Zod 길이 검사는 XSS 방어를 대체하지 않는다.

## 영상 처리와 공지방 갱신

`0039_mixed_gamma_corps.sql`의 `video_processing_jobs`, `video_processing_outputs`는 PostgreSQL 영구 작업·시도별 결과 원장이다. Web이 비공개 원본 저장을 확인하고 작업 ID를 반환하면 별도 Worker가 `FOR UPDATE SKIP LOCKED`로 선점해 FFmpeg를 실행한다. 300초 임대·시도별 UUID 토큰으로 오래된 Worker의 완료를 차단하고, ready 자산·결과 게시·작업 완료를 같은 트랜잭션으로 확정한다. 최대3회 재시도, 15분 업로드 예약·24시간 원본 TTL과 결과 삭제 재시도를 적용한다. 본문은 상태 조회를 통해 ready가 된 자산 ID만 연결한다. 원본에는 공개 경로가 없으며 Web/Worker가 같은 DB·저장소를 공유해야 한다.

공지방 공지·멤버·권한은 PostgreSQL이 원본이다. DB 커밋 뒤 Redis Pub/Sub에 방 UUID만 발행하고 SSE는 DB에서 내용·현재 권한을 다시 조회한다. 정상 구독에서는30초 재확인, 미설정/장애에서는5초 fallback으로 힌트 유실을 보완한다. 통합 알림·리마인더·Web Push 발송 작업은 기존 PostgreSQL과 별도 `push:worker`가 처리한다. Redis에 전체 알림 체계를 이전하지 않는다.

실행·정리 정책과 아직 남은 Docker/실기기 검증은 [미디어 Worker·공지방 실시간 문서](MEDIA_WORKERS_AND_ROOM_REALTIME.md)에 정리했다.

## 마이그레이션과 검증

- `0000_initial_schema.sql`: Drizzle 생성 테이블·인덱스·FK·RLS
- `0001_integrity_and_privacy.sql`: 직접 접근 회수, 댓글·작성자·이미지·조회·알림 트리거
- `0002_community_fields.sql`: 커뮤니티 표시 필드
- `0003_recruitment_application_link.sql`: 모집 신청 링크
- `0004_boards_polls_profiles.sql`: 창작 게시판·프로필·투표·활동 기록
- `0005_poll_integrity.sql`: 투표와 삭제 무결성
- `0039_mixed_gamma_corps.sql`: 영상 작업·시도별 결과 원장, RLS·상태/소유권 무결성·브라우저 역할 접근 차단
- 카테고리 시드는 반복 실행 가능하며 서비스 계층에서 카테고리 CRUD를 공개하지 않는다.
- 생성된 SQL과 커스텀 SQL을 함께 커밋한다. `db:push`로 운영 DB를 덮어쓰지 않는다.
- PGlite 테스트는 원본 마이그레이션을 실행한다. 테스트에서만 Supabase 관리형 스키마/역할을 최소 형태로 준비한다.
- 반복 요청·유일성은 검사하지만, PGlite 단일 엔진 검사가 실제 Supabase 다중 연결 부하 테스트를 대신하지는 않는다.

`0002_community_fields.sql`에서 글 유형, 추천 여부, 예시 여부, 장소·일정 표시용 필드를 추가했다. 서버 서비스에서 소유권 확인, 행 잠금, 이미지 연결, 알림 생성, 반응·조회 멱등 쓰기를 수행한다. 샘플의 장소·일정은 표시 정보이며 예약/신청 기능은 아니다. 실제 사용자가 입력한 값과 샘플을 구분한다.

## 페이지 처리 구현

`src/server/pagination.ts`에서 범위가 지정된 커서와 PostgreSQL 행 비교 조건을 공통으로 처리한다. 작성 시각은 마이크로초까지 유지하며 동률은 UUID로 정렬한다. 목록은 최신순 또는 좋아요 순, 댓글은 부모별 작성순, 알림은 수신자별 최신순을 사용한다. 기존 목록·댓글·알림 인덱스와 공통 서비스를 사용하므로 이 단계에서는 추가 스키마 마이그레이션이 없다. 인기순의 좋아요 수는 실시간 값이며 고정 순위 스냅샷을 제공하지 않는다. 자세한 API 응답과 제한은 [CRUD와 로컬 DB](crud-and-local-db.md)에 기록했다.

## 투표와 활동 기록 확장

11개 테이블로 확장했다. 투표 설정은 게시글 JSONB, 표는 `poll_votes`의 글/회원 유일 키로 저장한다. 집계와 본인 선택만 공개한다. 투표가 있는 질문·항목 수정 및 삭제 글 투표는 DB 트리거로도 막는다. `activity_events`는 회원/출처 키로 보상을 중복 방지하며 프로필 잠금 아래 KST 일별 한도를 적용한다. 프로필 기본 정보와 활동 기록은 본인 `/me` 경로로만 전달한다. 추가 마이그레이션은 기존 글과 인증 경계를 유지한다.

## 코드 리뷰 이후 서비스 경계

`community-service.ts`는 입력 검증·소유권·글/댓글 변경 트랜잭션을 관리하고 세 개의 내부 모듈을 조합한다. `post-reader.ts`는 명시적 공개 DTO와 집계, `profile-service.ts`는 본인 정보와 활동 기록, `notification-service.ts`는 수신자별 알림을 담당한다. 외부 서비스 인터페이스와 REST 응답 계약은 유지한다.

활동점수는 프로필에 `FOR NO KEY UPDATE` 잠금을 걸어 사용자별 한도를 직렬화한다. 글·댓글·투표의 프로필 외래키가 획득하는 `KEY SHARE`와 호환되는 잠금이다. 실제 PostgreSQL 두 연결의 동시 쓰기 회귀 검사로 확인했다. 정책은 `domain/activity.ts`를 서버와 마이페이지가 함께 사용한다.

클라이언트는 요청 순서와 글 변경 버전을 사용해 이전 목록·방문 응답이 최신 수정 결과를 덮어쓰지 못하게 한다. 삭제한 글은 늦은 목록 응답에서도 제거하고, 필터가 바뀐 동안에는 이전 커서로 페이지를 요청하지 않는다. 자동 전환은 포인터·키보드 포커스·수동 일시정지·숨겨진 탭·동작 줄이기 상태를 각각 검사한다.

## 행사 운영·룰북·플레이어·환불 구조

0006~0011은 행사 설정·참가 신청·내부/외부 결제 확인·담당자·읽기 전용 공지방을 추가한다. 0012~0015는 룰북/템플릿, 구매 열람 승인, 행사별 진행 사본, 플레이어 공개 설정, 참가 전적, 매너 평가, 환불 요청과 일정/금액 정합성 제약을 추가한다. 모든 27개 Sliper 테이블은 RLS와 공개 DB 역할 접근 차단을 적용한다.

룰북/템플릿과 플레이어 스키마는 `library-schema.ts`, `player-schema.ts`로 분리한다. 이 모듈은 기존 `schema.ts`의 사용자·게시글을 참조하므로 역방향 re-export로 초기화 순환을 만들지 않는다. 서비스는 `library-service.ts`, `player-service.ts`, `refund-service.ts`에서 명시적 DTO·소유권·공개 동의·사용 범위를 검사한다. 유료 자료 전문과 호스트 진행 사본은 각각 구매 승인과 담당자 권한을 확인한다.

동일 행사의 변경은 모집글 행 잠금을 먼저 획득한다. 결제 확인·정원·참가 상태·공지방 접근·환불 실제 금액을 하나의 트랜잭션에서 처리한다. 일정이 있는 신규 참가 신청은 시작일·정책을 저장하고, 환불 접수는 DB 시각을 기준으로 한국 달력 날짜 차이와 금액을 보존한다. 과거 시작일 없는 신청에 새 정책을 소급하지 않는다. 이미 취소·환불한 참가자는 늦은 결제로 다시 초대하지 않으며, 종료 후 결제는 검토 상태로 보존한다.

참가 전적은 종료한 행사 담당자만 기록하고 자기 전적 기록은 차단한다. 매너 평가는 실제 공동 참가자만 제출하며 공개 응답에는 집계만 포함한다. 개인정보와 미공개 전적을 공개 프로필에 담지 않고 기능 체험 샘플은 신뢰 점수에서 제외한다. 자세한 API와 정책은 [룰북·플레이어 문서](PLAYBOOKS_AND_PLAYERS.md), [행사 운영 문서](PARTICIPATION.md)를 참고한다.

## 번개와 거리 검색

0016~0018은 행사 설정에 공개 행사장 좌표와 번개 구분을 추가하고, 좌표 범위/쌍과 무료·작은 정원·근시일 일정 계약을 보장한다. 신규 테이블은 만들지 않는다. `lightning-service.ts`가 게시글·설정·활동 보상을 원자적으로 생성하고 기존 참가 신청·공지방을 사용한다. `community-service.ts`의 피드는 실제 DB 거리 계산과 조건·커서 검사를 사용하며 검색 기준 좌표를 저장하지 않는다. 일반 글로 변경한 게시글에서는 이전 행사 메타데이터를 숨긴다. API·반응형 화면·검증 범위는 [번개·위치 검색 문서](LIGHTNING_AND_DISCOVERY.md)를 참고한다.
