# 외부 참가 승인 · 행사 관리 · 공지방

## 모집글의 두 가지 참가 흐름

**외부 신청 링크가 있는 모집글**의 제목 오른쪽 `신청하기`는 해당 플랫폼을 새 탭으로 연다. 신청, 결제, 환불 및 정산은 그 플랫폼에서 진행한다. Sliper에서 다시 참가 신청하거나 내부 결제 주문을 생성하지 않는다.

외부 신청·결제를 마친 회원은 `/events/{postId}`의 `외부 신청 · 결제를 완료했어요`에서 이름, 연락처, 외부 신청 번호, 선택 요청사항과 담당자 정보 제공 동의를 제출할 수 있다. 이는 담당자가 외부 내역과 회원을 연결하기 위한 **선택적인 사후 참가 확인 요청**이다. 폼을 제출하는 것만으로 결제 확인이나 참가 확정, 정원 예약, 공지방 입장이 되지 않는다.

- **수동 승인 (`approvalMode: manual`, 기본값)**: 등록자 또는 지정된 담당자가 플랫폼의 실제 신청·결제 내역을 확인한 후 관리 화면에서 승인한다. 서명된 결제 알림을 받아도 수동 승인 행사에서는 담당자 승인 대기로 남는다.
- **자동 승인 (`approvalMode: automatic`)**: 서버가 검증한 외부 플랫폼 결제 알림에 회원과 행사 정보가 일치하면 참가를 확정한다. 연동 플랫폼이 회원의 공개 프로필 ID를 전달할 수 있으면 Sliper 사후 확인 폼 없이도 참가 내역을 생성한다. 외부 연동 설정과 실제 플랫폼 어댑터가 필요하다.
- 승인 트랜잭션에서 해당 모집글의 공지방 회원을 자동 생성한다. 확인 요청 자체는 정원을 예약하지 않는다. 자동 승인 시 정원이 꽉 차 있으면 검증된 결제 이력을 `review`로 보존하고 자동 초대하지 않는다. 외부 플랫폼에도 자체 정원/환불 정책을 적용해야 한다.
- 취소·반려 이후 늦게 확인된 결제나 같은 회원의 다른 활성 참가 내역과 충돌하는 결제는 담당자 확인 이력으로 보존한다. 동일 회원의 중복 참가 확정과 자동 초대를 차단하며 담당자가 외부 플랫폼에서 내역·환불을 확인해야 한다.

**외부 신청 링크가 없는 모집글**은 기존 Sliper 내부 신청 흐름을 유지한다. `/events/{postId}`에서 이름, 연락처, 선택 요청사항과 동의를 받고 무료 행사는 즉시 확정한다. 유료 행사는 주문 금액을 DB에 고정하고 30분 동안 정원을 예약한다. 외부 결제 브리지의 검증된 완료 알림 이후 확정하며 결제 화면 복귀만으로 참가가 확정되지 않는다.

모집글의 자유 형식 비용 안내는 결제 금액으로 자동 해석하지 않는다. 등록자가 관리 화면에서 금액(원), 정원, 접수 여부와 외부 행사 승인 방식을 별도로 설정한다. 진행 중인 참가 내역이 있는 모집글의 삭제·유형 변경·내부/외부 신청 방식 변경을 제한한다. 신청 마감은 기존 확정 참가자의 공지방 접근을 유지한다.

## 행사 관리와 공지방

`/management`는 본인이 등록하거나 담당자로 지정된 모집글의 요약을 제공한다. `/management/events/{postId}`는 해당 행사 담당자만 접근할 수 있는 관리 대시보드다.

- 확정, 승인 대기, 결제 대기, 담당자 확인 필요, 환불, 취소/만료, 반려 상태별 집계 및 필터.
- 참가자 이름·연락처·외부 신청 번호 검색, 30개씩 더 보기. 검색 결과와 별도로 행사 전체 상태 집계를 표시한다.
- 외부 참가 요청 승인, 사유를 남긴 반려, 외부 환불 완료 확인. 이미 결제가 검증된 내역은 단순 반려 대신 외부 환불 확인으로 처리한다.
- 등록자의 금액·정원·접수·승인 방식 설정과 공개 프로필 ID를 통한 담당자 지정. 지정 담당자는 참가 내역을 처리하고 공지를 작성하며 설정 변경과 담당자 지정은 등록자가 수행한다.
- 첫 페이지에서 주기적으로 현황을 갱신한다. 이전 내역을 더 불러온 경우 조회 위치를 유지한다. 담당자 권한이 해제되면 후속 요청을 거절하고 화면의 참가자 정보를 숨긴다.

승인·환불 체크박스는 **담당자가 외부 플랫폼에서 처리/확인한 내역의 기록**이다. Sliper가 실제 결제, 환불 송금 또는 정산을 실행하는 기능이 아니다. 외부 확정 참가자는 Sliper에서 직접 취소할 수 없으며 플랫폼의 환불 절차 이후 담당자 확인 또는 검증된 환불 알림으로 상태를 바꾼다. 결제가 아직 확인되지 않은 요청만 회원이 취소할 수 있다. 결제 확인을 받은 승인 대기 요청은 담당자 확인·환불 경로로 처리한다. 확인 요청 취소는 외부 플랫폼 신청·결제를 취소하지 않는다.

`/participation`은 본인의 참가 내역과 공지방 목록, `/rooms/{postId}`는 행사 공지방이다. 등록자와 지정 담당자만 메시지를 작성하며 참가자는 읽기만 한다. 참가자의 메시지 삽입은 서버와 DB에서 차단한다. 신청자 개인정보는 본인과 해당 행사 담당자만 조회할 수 있다.

공지는 SSE로 갱신한다. 서버가 5초마다 DB와 접근 권한을 확인해 변경사항을 전송하며 약 55초 뒤 연결을 종료하고 EventSource가 재연결한다. 환불 확인 시 방 참여 권한을 해제한다. 브라우저를 닫은 상태의 푸시 알림은 포함되지 않는다.

## 한국시간 환불 요청

행사 시작일과 요청일의 한국 달력 날짜 차이로 5일 이상 100%, 4일 80%, 3일 60%, 2일 40%, 1일 20%, 당일 이후 0%를 적용한다. 참가 신청 시 시작일·금액·정책을 저장하고 요청 접수 시 DB 시각으로 비율과 환불 예정액을 계산해 보존한다. 처리일이 늦어져도 요청일 기준액을 사용한다.

본인은 참가 화면에서 취소·환불 요청을 제출하고 담당자는 대시보드에서 확인한다. 요청 자체는 참가 취소나 실제 환불을 실행하지 않는다. 담당자가 외부 플랫폼에서 예정액으로 처리한 뒤 완료 체크를 하거나 검증된 취소·환불 알림을 받으면 참가 상태와 공지방 접근을 함께 변경한다. 수동 완료 금액은 요청액과 일치해야 한다. 시작일이 없는 과거 신청은 이후 일정 설정으로 새 정책을 소급 적용하지 않으며 담당자와 기준을 확인한다.

자세한 자료·플레이어 구조와 환불 기준은 [룰북·플레이어 문서](PLAYBOOKS_AND_PLAYERS.md)를 참고한다.

## 실제 연동 상태

카카오·구글 인증은 이전 요청대로 아직 연결하지 않았다. 개발 모드 + 전용 로컬 DB + 지정된 루프백 호스트에서만 테스트 계정을 제공한다. 프로덕션에서는 실제 로그인 연동까지 회원 신청·담당자 기능이 차단된다. 브라우저 헤더를 통한 회원 가장 기능은 없다.

실제 결제 플랫폼, Supabase 클라우드 연결 및 배포도 아직 완료하지 않았다. 아래 계약은 **플랫폼 어댑터용 공통 브리지**이며 특정 플랫폼의 네이티브 API와 호환된다고 가정하지 않는다. 플랫폼 선정 후 해당 플랫폼의 공식 서명 검증, 행사/주문/회원 연결, 결제·환불 상태 매핑을 구현해야 한다.

외부 링크 행사의 수동 승인에는 Sliper의 결제 주문 생성 API 설정이 필요하지 않다. 자동 승인은 검증 가능한 플랫폼 API 또는 웹훅과 회원 연결이 필요하다. 이름·연락처가 같다는 이유로 회원을 자동 연결하지 않는다. 카드번호 등 결제 수단 정보와 지급 잔액은 Sliper에서 받거나 관리하지 않는다.

## 외부 신청 플랫폼의 승인 연동 계약

외부 링크가 있는 모집글은 다음 설정을 사용한다. 내부 신청의 결제 주문 브리지 설정과 분리되어 있다 (`.env.example` 참고).

| 변수                             | 내용                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------- |
| EXTERNAL_APPROVAL_PROVIDER       | 플랫폼 식별자: 영문/숫자/밑줄/하이픈 1~40자, `manual`·`local-test` 사용 금지 |
| EXTERNAL_APPROVAL_WEBHOOK_SECRET | 외부 참가 확인 HMAC 키, 최소 32자, 서버 전용                                 |

`POST /api/payments/external-webhook`, `Content-Type: application/json`:

```json
{
  "eventId": "플랫폼-알림-고유-ID",
  "postId": "모집글-UUID",
  "publicProfileId": "회원-공개-프로필-UUID",
  "externalReference": "플랫폼-신청-또는-주문-번호",
  "attendeeName": "참가자 이름",
  "contact": "플랫폼에서 확인한 연락처",
  "amountKRW": 10000,
  "currency": "KRW",
  "status": "paid"
}
```

참가 취소·환불은 동일한 행사·회원·신청 번호·원 결제 금액에 `status: refunded`를 전달한다. 선택 필드 `refundAmountKRW`는 실제 환불 총액이며 0부터 원 결제액까지 허용한다. 생략하면 기존 전액 환불 계약으로 처리한다. `amountKRW`는 환불액으로 바꾸지 않고 원 결제 금액을 유지한다. 이름은 1~60자, 연락처 3~100자, 외부 신청 번호 3~160자, 원 결제 금액은 0~10,000,000원이다. 무료 외부 행사의 참가 확인은 금액 0으로 전달할 수 있다. 일부 금액을 돌려주더라도 참가 취소가 완료된 거래만 `refunded`로 전달한다. 참가를 유지하는 부분 보상과 지급/정산 알림은 이 계약에 포함하지 않는다.

`publicProfileId`는 마이페이지와 참가 확인 화면에 표시하는 **공개 프로필 ID**이며 인증 계정 ID가 아니다. 플랫폼/어댑터에서 외부 신청을 이 ID와 해당 모집글에 연결해야 한다. 실제 어댑터는 연결 정보가 해당 회원의 외부 신청임을 검증해야 하며, 클라이언트가 보낸 결제 성공 상태를 그대로 서명해서 전달하면 안 된다. 존재하지 않는 회원이나 잘못된 금액은 거절한다.

- `x-sliper-timestamp`: 10자리 초 단위 Unix timestamp.
- `x-sliper-signature`: `HMAC-SHA256(secret, timestamp + '.' + 원본 JSON 바이트)`의 소문자 hex. JSON을 파싱 후 다시 직렬화한 결과에 서명하지 않는다.
- 본문 최대 64,000바이트, 서버 시간 전후 5분까지 허용.
- 같은 `(provider, eventId)`와 같은 내용은 멱등 처리한다. 재전송 시 새로운 전송 시각으로 서명한다. 같은 이벤트 ID의 다른 내용은 거절한다.
- `(postId, externalReference)` 고유성으로 다른 회원에게 동일 외부 신청 번호를 재사용하는 것을 차단한다. 기존 확인 내역의 제공자·금액·회원도 검증한다.
- 환불 알림이 먼저 오거나 이미 환불된 뒤 늦게 결제 성공 알림이 와도 공지방 권한을 복구하지 않는다. 처리된 환불 총액과 다른 후속 환불 알림은 `409 CONFLICT`로 거절해 기존 거래를 변경하지 않는다. 종료된 행사에 늦게 도착한 결제는 담당자 확인 대상으로 남기고 자동 초대하지 않는다.
- 2xx는 이력 저장/처리 또는 멱등 재전송 완료를 의미한다. 수동 승인 대기·정원 초과·참가 충돌은 즉시 확정되지 않을 수 있으므로 응답 상태와 관리 화면을 확인한다. 네트워크 오류/5xx는 같은 이벤트 ID로 재전송하고 4xx는 서명·회원 연결·금액·계약을 확인한다.
- HTTPS로 공개된 웹훅 주소와 플랫폼별 어댑터를 연결해야 한다. 환경 변수만 설정해도 실제 플랫폼에서 자동 알림이 오는 것은 아니다.

플랫폼의 네이티브 서명 규칙이 위와 다르면 공식 SDK/문서에 맞는 검증 어댑터를 적용한다. 네이티브 알림의 헤더 이름만 바꾸어 공통 계약으로 전달하지 않는다.

## 내부 신청의 외부 결제 브리지

외부 신청 링크가 없는 유료 모집글에만 사용하는 설정이다.

| 변수                     | 내용                                                                |
| ------------------------ | ------------------------------------------------------------------- |
| PAYMENT_PROVIDER         | 플랫폼 식별자: 영문/숫자/밑줄/하이픈 1~40자, `local-test` 사용 금지 |
| PAYMENT_CHECKOUT_API_URL | 서버가 호출할 HTTPS 주문 생성 브리지 주소                           |
| PAYMENT_API_KEY          | 서버 간 API 인증 키                                                 |
| PAYMENT_WEBHOOK_SECRET   | 결제 알림 HMAC 키, 최소 32자, 서버 전용                             |
| PAYMENT_CHECKOUT_ORIGINS | 결제 화면을 허용할 정확한 HTTPS origin, 쉼표 구분                   |
| APP_ORIGIN               | 사이트의 정확한 origin, 실제 배포 시 HTTPS                          |

Sliper 서버가 `POST PAYMENT_CHECKOUT_API_URL`로 주문 생성 요청:

```json
{
  "orderId": "Sliper-주문-UUID",
  "amountKRW": 10000,
  "currency": "KRW",
  "title": "행사 제목",
  "returnUrl": "https://사이트/events/모집글-UUID"
}
```

헤더는 `Authorization: Bearer <API key>`와 `Idempotency-Key: <orderId>`. 재시도 시 같은 주문을 중복 생성하지 않아야 한다. 참가자 이름·연락처는 이 호출에 전달하지 않는다. 응답은 다음 형태다.

```json
{ "checkoutUrl": "https://허용된-플랫폼/결제-세션" }
```

주소의 HTTPS, 정확한 허용 origin과 사용자정보 포함 여부를 검사한다. 기존 모집글의 외부 신청 링크를 내부 주문의 결제 세션으로 사용하지 않는다. 브라우저가 주문 금액이나 결제 완료 상태를 지정하는 인터페이스는 없다.

결제·참가 취소 후 환불 완료는 `POST /api/payments/webhook`으로 전달한다.

```json
{
  "eventId": "외부-알림-고유-ID",
  "orderId": "Sliper-주문-UUID",
  "paymentId": "플랫폼-결제-고유-ID",
  "amountKRW": 10000,
  "currency": "KRW",
  "status": "paid"
}
```

서명 헤더·원본 바이트·64,000바이트 제한·5분 허용 범위·재전송 규칙은 외부 승인 브리지와 동일하며 키는 `PAYMENT_WEBHOOK_SECRET`이다. 주문 플랫폼·금액·통화·결제 ID를 검증한다. `(provider, eventId)` 및 `(provider, paymentId)` 고유성으로 중복과 결제 재사용을 차단한다. 환불은 기존 주문의 원 결제 금액과 동일한 결제 ID로 `status: refunded`를 전달하고 실제 환불 총액을 선택 필드 `refundAmountKRW`로 지정한다. 생략하면 전액 환불이며 0원 참가 취소도 지원한다. 결제 완료 알림에 환불액을 포함하거나 원 결제액보다 큰 환불액을 보내면 거절한다. 이미 처리한 환불 총액과 다른 후속 알림은 `409 CONFLICT`다. 기한 만료·취소 또는 행사 종료 뒤 결제된 주문은 `review`로 남기고 자동 초대하지 않으며 외부 플랫폼에서 확인·환불해야 한다.

외부 연결이 없는 로컬 환경에서는 `테스트 결제 확인 (실제 결제 없음)` 버튼으로 흐름을 체험한다. `/orders/{id}/simulate`는 로컬 개발 전용으로 본인의 대기 중 내부 주문에만 동작한다. 외부 링크 행사·외부 주문·프로덕션에는 사용할 수 없다.

## DB와 권한

마이그레이션 0006/0007은 `event_settings`, `event_applications`, `payment_orders`, `payment_events`, `room_managers`, `room_members`, `room_messages`를 추가했다. 0008~0011은 외부 참가 출처·참조 번호·승인 상태·승인 방식과 결제 확인 테이블 `external_receipts`, 수신 알림 테이블 `external_webhook_events` 및 정합성 제약을 추가한다. 0012~0015는 룰북·템플릿·플레이어·취소/환불 요청 7개 테이블과 행사 일정·정책 스냅샷·실제 환불액 정합성 제약을 추가한다. 총 27개 테이블은 비공개 `sliper` 스키마에서 RLS를 활성화하며 공개 Data API 역할 접근을 차단한다. 신청자 개인정보를 Supabase Realtime 공개 테이블 구독으로 전송하지 않는다.

참가 등록·확인, 담당자 결정, 설정 변경 및 결제 알림은 모집글 행을 먼저 잠근다. 정원 검사·결제/환불 기록·참가 상태 변경·공지방 참여 변경을 하나의 트랜잭션으로 처리한다. 내부 결제 대기의 만료는 조회에 반영하고 이후 해당 행사 변경 작업에서 DB 상태도 정리한다. 외부 확인 요청에는 내부 주문이나 결제 기한이 없다.

DB 트리거가 신청 금액·회원·출처·외부 참조 변경, 잘못된 상태 전환, 결제 미확인 초대, 참가자의 메시지 삽입을 방어한다. 확인이 필요한 외부 결제 이력과 활성 참가를 구분하여 과거 결제 이력을 보존하면서 동일 회원의 중복 확정을 막는다. 관리 조회·공지·참가 목록은 30개씩 PostgreSQL 마이크로초 정밀도 커서로 조회한다. 관리 대시보드의 커서는 담당자·행사·검색/필터 범위가 다른 요청에 재사용할 수 없다.

외부 결제 기록은 감사 목적의 참조 제약으로 보호한다. 실제 회원 탈퇴 연결 시 결제 감사 기록 보존과 연락처 삭제/익명화 정책을 구현해야 한다. 현재 인증·회원 탈퇴는 미연동이며 자동 개인정보 삭제를 제공한다고 표시하지 않는다. 외부 플랫폼의 지급·정산 문제는 해당 플랫폼에서 처리한다.

## 로컬 확인과 검증

```powershell
npm run db:migrate
npm run dev
```

외부 링크 행사는 등록 후 `내 행사 관리`에서 금액·정원·접수와 승인 방식을 저장한다. `신청하기`가 외부 플랫폼으로 연결되는지, Sliper 사후 확인 요청은 승인 대기로 표시되는지 확인한다. 담당자는 관리 대시보드에서 외부 실제 내역을 확인한 후 승인하고 공지방 참여를 확인한다. 미확인 요청의 반려 및 외부 환불 확인도 같은 화면에서 처리한다. 실제 외부 거래 없이 운영 결제를 확인했다고 기록하지 않는다.

내부 신청 행사는 외부 링크 없이 등록하고 금액·정원을 설정한다. 무료는 즉시 확정, 유료는 로컬 테스트 결제 버튼으로 체험한다. `/participation`에서 내역과 방을 확인하며 등록자는 공지 작성 및 담당자 지정을 할 수 있다.

현재 로컬 브라우저는 단일 테스트 계정을 사용한다. 본인이 만든 행사에서는 담당자 입력창이 표시된다. 서로 다른 회원의 참가·담당자 권한은 서비스 및 PostgreSQL 통합 테스트로 확인하며 실제 다중 회원 로그인 검증을 대신하지 않는다.

```powershell
npm run check
npm run test:api
npm run build
```

`check`는 포맷·타입·도메인/서비스/DB 회귀·Drizzle 검사를 수행한다. `test:api`는 개발 서버와 전용 로컬 PostgreSQL에서 HTTP/SSE·출처·참가 확인·담당자 승인·관리 접근을 검사한다. 빌드는 개발 서버를 종료한 후 실행한다. 실제 플랫폼 샌드박스 거래와 브라우저 직접 클릭 검증은 별도로 수행해야 한다.

`test:payments`는 빌드 후 **테스트 전용 운영 서버**를 로컬 포트 3001에서 실행한다. 내부 서명 결제·환불·중복/역순 알림, 위조/만료 서명과 금액 불일치 거절, 외부 신청 자동 승인·환불, 운영 환경의 로컬 결제 우회 차단, 실제 PostgreSQL 두 연결의 정원 경합을 검사한다. 실제 플랫폼 API를 호출하지 않으며 테스트 레코드만 만들고 정리한다.

```powershell

$env:PAYMENT_CHECKOUT_API_URL='https://example.invalid/checkout'
```

다른 터미널에서 `npm run test:payments`를 실행한다. 위 서명 키는 공개된 테스트 값이므로 실제 연동에 사용하지 않는다. 테스트 완료 후 서버와 해당 환경 변수를 설정한 터미널을 종료하고 원래 환경의 새 터미널에서 `npm run dev`를 실행한다. 기존 `.env`를 테스트 값으로 덮어쓰지 않는다.

`npx tsx scripts/seed-participation-demo.ts`는 실제 행사·결제가 아닌 내부 신청 샘플과 예시 공지를 준비한다. 로컬 테스트 계정은 참가자여서 읽기 전용 공지방을 확인할 수 있다. `npx tsx scripts/seed-external-participation-demo.ts`는 담당자 관리 화면을 확인하는 외부 승인 샘플을 준비한다. 신청 링크와 참가 내역은 허구이며 실제 결제·환불은 없다. 두 스크립트는 전용 로컬 DB에서만 실행하고 재실행 시 기존 샘플 설정·결정·메시지를 덮어쓰지 않는다.

설계 참고: [원본 본문·중복·순서 검증](https://docs.stripe.com/webhooks), [PostgreSQL 행 잠금](https://www.postgresql.org/docs/18/explicit-locking.html). 특정 결제 플랫폼을 채택했다는 의미는 아니다.

## 공지방 멤버와 프로필 사진 (2026-10-02)

방의 `멤버 N명`은 주최자·지정 담당자·참가가 확정되어 입장 권한이 남아 있는 참가자의 합계다. 한 사람이 여러 역할을 겸하면 한 번만 집계하고 주최자 → 담당자 → 참가자 순으로 표시한다. 결제·승인 대기자는 포함하지 않으며 취소·환불 또는 담당자 해제 후에도 참가 권한이 남아 있는지는 현재 역할을 다시 확인한다.

`GET /api/participation/rooms/{postId}`와 SSE snapshot은 총 인원·최대 8명 미리보기·목록 revision을 내려준다. `GET /api/participation/rooms/{postId}/members`는 기본 50명, 최대 50명씩 조회한다. 멤버 DTO는 공개 프로필 ID·닉네임·기본 아이콘·사진 경로·역할·본인 표시로 제한한다. 전화번호·신청 답변·인증 사용자 ID는 제공하지 않는다. 커서는 방과 조회자에 묶이고 목록 변경 후에는 409 응답으로 처음부터 조회한다. 현재 공지방 접근 권한을 행사 행 잠금 안에서 확인하며, 인원·revision·페이지는 하나의 SQL snapshot에서 읽는다. 멤버 후보는 해당 방의 인덱스 기반 권한 목록에서 가져와 전체 사용자 목록을 매번 조회하지 않는다.

내 정보의 프로필 편집에서 5MiB 이하 JPG·PNG·WebP·GIF 사진을 추가·변경·삭제한다. 서버는 실제 이미지 형식과 2천만 화소 제한을 확인하고 중앙 정사각형 512px WebP로 변환하여 EXIF·위치 메타데이터를 제거한다. `POST /api/community/me/photo`는 multipart의 file 한 개만 허용하며, `DELETE`는 현재 사진을 제거한다. 두 응답은 갱신된 본인 프로필이다. 프로필 사진 파일은 `.local/profile-photos`, 파일 키와 소유권은 RLS가 활성화된 `sliper.profile_photos`에 보관한다.

`GET /api/profile-photos/{photoId}`는 본인 사진만 조회한다. 다른 멤버의 사진에는 `?room={postId}`가 필요하며, 조회자와 사진 소유자가 모두 그 방의 현재 멤버인지 확인한다. 공개 폴더나 게시글 사진 API로 우회하지 않으며 응답은 private, no-store다. 교체·삭제 후 이전 사진 ID를 사용할 수 없고, 참가 취소 후에는 공유 사진도 조회할 수 없다. 저장 실패 시 새 파일을 정리하고 교체·삭제 후 이전 파일을 정리한다. 계정 삭제에 따른 파일시스템 고아 파일의 자동 수거는 아직 별도 구현이 필요하다.

멤버 패널은 공지 앞에 배치하고 접힌 상태에서 인원과 사진 미리보기를 표시한다. 펼치면 사진·닉네임과 역할을 확인한다. 기존 5초 주기의 SSE 갱신은 멤버 변화도 반영한다. UI는 권한 종료 또는 revision 변경 뒤 늦게 도착한 목록이 이전 멤버를 복구하지 않도록 요청 세대·취소·권한 ticket·revision을 검사한다. 일반 참가자는 계속 공지를 읽기만 하며 연락처와 신청서 조회·공지 작성은 담당자에게만 허용한다.

검증: 관련 서비스·권한 테스트 14개를 포함한 회귀 254개 통과. 별도 `npm run test:room-members-api`에서 실제 HTTP 이미지 변환·메타데이터 제거·권한·업로드 검증·교체·삭제·SSE 갱신·참가 취소 차단을 확인했다.
