# F1 — 신뢰 운영과 공개 베타 준비

2026-10-14 · 운영 큐와 읽기 전용 점검 기능을 구현했습니다. F 전체의 실서비스 공개·실기기·백업 복원 검증을 완료한 상태는 아닙니다. [전체 구현 계획](COMMUNITY_IMPROVEMENT_IMPLEMENTATION_PLAN.md)과 [외부 연동 준비](PRODUCTION_INTEGRATION.md)를 함께 참고합니다.

후속 F2의 이의신청·30일 보관·분리 복원 도구는 [구현 문서](COMMUNITY_APPEALS_RETENTION_AND_RESTORE.md)에 정리합니다. 아래 검증 결과는 F1 당시의 범위입니다.

## 운영자 화면

| 화면 | 대상 | 제공 기능 |
| --- | --- | --- |
| `/admin/operations` | 활성 관리자·모더레이터 | 신고·문의·자료 거래 분쟁의 통합 처리함 |
| `/admin/health` | 활성 관리자 | 알림·푸시·영상 원장의 집계와 연결 설정 분류 |
| `/admin?tab=reports&id=UUID` | 활성 운영자 | 특정 신고의 당시 증거·현재 처리 사유·기존 조치 |
| `/admin?tab=support&id=UUID` | 활성 운영자 | 특정 문의의 내용·전체 답변·기존 답변 처리 |
| `/admin?tab=audit` | 활성 운영자 | 기존 조치와 담당·검토·기한 변경의 감사 이력 |
| `/archive/purchases/구매ID#dispute-분쟁ID` | 기존 거래·운영 권한 | 원래 자료 거래·판매자 답변·중재 흐름 |

기존 `/admin` 화면에 통합 처리함을 연결했습니다. 관리자는 운영 점검·이용 현황으로도 이동할 수 있습니다. 신고·문의 원본은 첫 20개 밖에 있어도 UUID로 직접 조회하며, 조회 실패 시 이전 항목의 양식을 숨겨 잘못된 원본을 처리하지 않도록 합니다.

## 통합 처리함의 기준

원본 상태를 새 작업 테이블에 복제하지 않습니다. 신고·문의·분쟁의 상태와 검토 시작 시각에서 다음 단계를 계산합니다.

- **미처리:** 원본이 `open`이고 검토 시작이 없음.
- **검토 중:** 원본이 `open`이고 검토 시작이 있음.
- **완료:** 원본이 `open`이 아님. 신고 조치/기각, 문의 답변/종료, 분쟁 중재/철회를 구분해 원래 화면에서 확인합니다. 문의의 `answered`도 답변 완료에 포함되며 종료 여부는 원본에 남습니다.

종류·상태·담당(전체/미배정/내 담당) 필터와 20개 단위 번호 페이지를 제공합니다. 같은 조건의 미처리·검토 중·완료 수를 함께 확인합니다. 접수·목표 기한·응답 시각은 한국 시간으로 표시합니다.

‘내가 맡기’ → ‘검토 시작’으로 진행하고, 자신의 담당 접수는 해제할 수 있습니다. 관리자는 다른 운영자의 담당도 해제할 수 있습니다. 본인 담당자 또는 관리자가 미래의 처리 목표 시각을 입력/해제합니다. 목표 시각은 내부 운영 목표이며 회원에게 보장하는 답변 기한이나 자동 제재 기준이 아닙니다. 접수의 판정과 답변은 기존 원본 API에서 수행합니다.

검토 시작은 보존하며 담당 해제로 이전 검토 이력을 지우지 않습니다. 완료 접수의 담당·기한을 다시 수정하는 기능을 제공하지 않습니다. 분쟁 당사자가 운영자라도 자신의 거래는 통합 큐에서 제외되고, 직접 주소를 요청해도 담당 배정·검토·기한 변경·판정을 할 수 없습니다.

## 데이터·권한·수정 충돌

마이그레이션 `0059_operations_triage_metadata.sql`, `0060_operations_triage_integrity.sql`을 추가했습니다. 새 테이블은 없습니다. 기존 `safety_reports`, `support_tickets`, `library_purchase_disputes` 각각에 `assigned_to`, `review_started_at`, `due_at`, `revision`만 추가했습니다. 기존 접수는 미배정·기한 없음으로 유지하며 원문·증거·응답·판정·결제 정보를 재작성하지 않습니다.

담당·검토·기한 변경은 원본 행 잠금과 `expectedRevision`으로 비교합니다. 기존 신고 조치·문의 답변·분쟁 처리로 원본이 변경돼도 DB 트리거가 버전을 증가시켜 이전 화면의 후속 변경을 409로 거절합니다. 문의·분쟁의 기존 `updatedAt` 비교도 계속 사용합니다.

담당 배정은 활성 운영자만 가능하며 원본 3종의 DB 보호도 추가했습니다. 분쟁 판정은 기존 보호와 함께 중립적인 활성 운영자인지 확인합니다. 새로운 처리 이력은 기존 `moderation_audit`에 남기고 분쟁은 기존 `library_purchase_audit`에도 기록합니다. 실제 답변·처리 사유의 이전 감사 내역은 보존합니다.

`GET /api/safety/admin/operations`는 `kind`, `stage`, `assignment`, `page`만 허용하며 중복/잘못된 조건을 거절합니다. 목록은 현재 권한을 확인한 읽기 전용 트랜잭션에서 건수와 20개 페이지를 조회합니다. `GET/PATCH /api/safety/admin/operations/{report|support|dispute}/{UUID}`는 운영 정보 조회와 담당·검토·기한 변경입니다. 원본 신고·문의 상세 GET도 기존 안전 API에 추가했습니다.

활성 관리자·모더레이터만 접수 내용을 볼 수 있습니다. 담당 표시는 공개 프로필 ID·닉네임으로 제공하며 일반 회원·비회원·권한 회수 계정에게 원문/증거를 반환하지 않습니다. 유료 운영 자료·푸시 endpoint·비밀키·개인 신청 답변을 새 운영 큐에 넣지 않습니다. 거래 당사자의 기존 비공개 구매 내역 열람 권한은 유지합니다.

화면은 서버의 `allowedActions`에 따라 버튼을 표시하지만 실제 권한은 서버에서 다시 검사합니다. 동시 수정 충돌 후 최신 내용을 조회합니다. 쓰기 성공 여부나 이후 조회가 불명확하면 재조회 전 추가 변경을 막습니다. 취소된/오래된 조회 결과로 새 필터나 원본이 덮어써지지 않도록 요청을 구분합니다.

## 운영 점검 화면의 의미

`GET /api/safety/admin/health`는 관리자 전용이며 조회만 수행합니다. PostgreSQL 원장에 있는 다음 집계를 표시합니다.

| 집계 | 의미 |
| --- | --- |
| 처리 가능한 대기 | 실행 가능 시각이 지난 작업. 만료된 푸시·미완료/만료 영상 업로드 제외 |
| 처리 중 | 유효한 임대가 있는 작업 |
| 재시도 대상 | 재시도 횟수가 있는 미완료 작업. 대기 수와 중복될 수 있음 |
| 보관된 실패 | 원장에 남은 누적 실패 수. 오늘 발생한 장애 수와 다름 |
| 임대 만료 | 처리 중이었으나 임대 시각이 지난 작업 |
| 가장 오래 기다린 시각 | 현재 처리 가능한 작업의 가장 빠른 실행 가능 시각 |
| 최근 성공 처리 | DB에 남은 성공 기록의 최종 시각 |

기존 Worker가 재시도/임대 복구를 수행합니다. 점검 GET으로 발송·재처리·삭제를 실행하지 않습니다. 작업이 없거나 과거 성공이 있다고 현재 프로세스가 실행 중인 것은 아닙니다. 새 heartbeat·자동 복구·상시 모니터링 서비스는 추가하지 않았습니다.

저장소·공지방 갱신·VAPID·알림 Worker 모드는 설정 분류만 제공합니다. 주소·키·오류 원문을 반환하지 않고 외부 연결을 호출하지 않습니다. 실제 Redis 연결·Storage 권한·기기 푸시 수신은 별도 검증이 필요합니다. Redis는 계속 공지방 갱신 힌트만 전달하고 알림과 작업의 원본은 DB에 유지합니다.

24시간 이상 글/기록에 첨부되지 않은 사진·영상 수, 기존 영상 정리 조건에 도달한 원본과 미공개 결과 수도 표시합니다. 후보를 자동 삭제하지 않습니다. 기존 영상 Worker가 실제 조건을 재검사해 정리하며, F1 당시에는 사진/ready 영상 장기 보관이 후속 작업이었습니다. 현재는 F2에서30일 정책·정리 원장·명시적 CLI 실행을 구현했고 자동 스케줄은 아직 없습니다.

## 제한 베타의 다음 검증

운영 큐 완료는 공개 베타 출시 완료와 구분합니다. 아래는 F1 당시의 후속 순서이며, 현재1의 이의신청·신뢰 표시와2의30일 미첨부 정책·정리 도구,3의 암호화 로컬 분리 복원은 F2에서 완료했습니다. 계정/거래 파기·자동 스케줄·원격 복원·실기기 검증은 별도로 남아 있습니다.

1. **이의신청·신뢰 표시:** 기존 문의/분쟁을 원조치와 명시적으로 연결하고 활동점수·QR/담당자 출석·수락한 제작 경력·매너 평가의 의미를 구분합니다. 현장 QR과 매너 온도를 신원/안전 보장으로 표현하지 않습니다.
2. **보관·장애 대응:** 미첨부 사진/영상의 보관 기간, 계정·거래 기록의 파기 범위, 운영 담당 연락 경로와 장애 로그·알림을 정합니다. 실제 참가자만 받는 행사 연락 안내를 확인합니다.
3. **DB와 미디어 복원:** 원래 DB를 덮어쓰지 않는 별도 복원 대상으로 DB와 파일을 함께 검증합니다. 백업 원본과 비밀키는 암호화된 별도 저장소에서 관리합니다.
4. **외부 준비와 실제 기기:** 개발 Supabase·운영 DB 역할·카카오/구글·private Storage·HTTPS·별도 Worker·결제 승인/환불 계약을 준비한 뒤 두 회원과 호스트의 실제 흐름을 확인합니다. Android와 홈 화면 iPhone의 설치·알림·로그인·신청·QR을 직접 확인합니다.

### 백업·복원 리허설 기준

- 글/기록 사진 `.local/uploads`, 프로필 `.local/profile-photos`, 영상 원본 `.local/video-sources`, 변환 결과 `.local/videos`와 DB의 소유권·처리 상태가 한 시점에 맞아야 합니다. Supabase 사용 시 private 버킷의 해당 객체 범위를 같이 보존합니다.
- 행사/업로드 쓰기와 Worker를 통제한 검증 시점을 정하고, DB 덤프와 필요한 파일만 보관합니다. `.env`, 테스트 계정 파일, 실행 중인 PostgreSQL 디렉터리 전체를 일반 사이트 파일 묶음에 넣지 않습니다. 인증·VAPID 등 비밀 설정의 별도 안전한 복구 계획이 필요합니다.
- 빈 별도 DB와 저장소에 복원하고 테이블/마이그레이션·파일 해시·소유권·영상 작업 상태를 확인합니다. 원래 로컬/운영 DB를 초기화하거나 덮어쓰지 않습니다.
- 복원 환경에서는 푸시·결제 웹훅·외부 승인·Worker 자동 발송을 끄고 먼저 회원/담당자/비회원의 원문·기록 미디어·영상 HEAD/Range 권한을 확인합니다. 실제 회원에게 복원된 대기 알림을 재전송하지 않습니다.
- 성공 기준은 복원된 행사 한 건에서 본문·신청·공지·QR·회고·미디어·자료 버전·권한을 대조하고 실패 없이 읽는 것입니다. 소요 시간과 실패 지점을 기록해야 하며 백업 명령의 성공만으로 복원 성공이라 하지 않습니다.

이 문서는 F1 당시의 실행 기준입니다. F1에서는 실제 백업 복원을 수행하지 않았으나 F2에서 로컬 DB와 미디어의 암호화 백업·분리 복원을 검증했습니다. 실기기·원격 업체 연결·원격 복원은 아직 검증하지 않았습니다. 운영 키가 준비되지 않은 상태에서 `deploy:check`의 로컬 개발 설정 FAIL은 예상되며 출시 승인을 뜻하지 않습니다. noindex·검색 공개 범위·사이트맵은 도메인과 공개 경로가 확정된 뒤 결정합니다.

- `npm run check`: 보안 값·Prettier·TypeScript·전체 **820개** 단위/DB 테스트·Drizzle 검사 통과. 추가 검사 18개는 운영 원본/권한/버전 9개, 점검 집계/조회 무변경/키 비노출 6개, 화면 권한/한국 시간/원문 링크 3개입니다.
