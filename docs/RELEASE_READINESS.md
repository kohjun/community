# 실서비스 연결 준비 점검

2026-10-16 기준. 설정 형식을 확인하는 읽기 전용 도구이며 출시 승인이나 외부 연결 성공 보고서가 아닙니다.

## 화면과 API

활성 관리자 계정으로 `/admin/readiness`를 열면 검사 시각과 통과·확인 필요·수정 필요 집계를 볼 수 있습니다. `/admin/health`의 대기열·작업 상태 점검과 구분합니다. 일반 회원·운영 검토자·이용 제한/탈퇴 계정에게 준비 결과를 제공하지 않습니다.

`GET /api/safety/admin/readiness`도 같은 관리자 권한을 먼저 확인합니다. 검색 조건을 받지 않으며 응답은 private/no-store입니다. 결과에는 다음 항목만 있습니다.

- `checkedAt`: 검사 시각
- `scope`: `configuration-only`
- `checks`: 고정된 검사 ID·상태·일반적인 안내
- `summary`: 상태별 개수
- `externalVerification`: `not-performed`

환경변수 원본, URL·호스트·게시자 ID·계정 정보·비밀키·내부 오류 원문을 반환하지 않습니다. 검사 과정에서 OAuth·Storage·결제·Redis·Google 등에 확인 요청을 보내지 않습니다. 접근 권한 확인에 필요한 기존 DB 조회 외에 설정·DB·파일을 변경하거나 작업을 실행하지 않습니다. 키 입력·연결 테스트·광고 활성화·마이그레이션·미디어 삭제·Worker 시작 버튼은 제공하지 않습니다.

## CLI와 결과의 의미

```powershell
npm run deploy:check
npm run deploy:check -- --json
npm run deploy:check -- --strict
```

화면/API와 CLI는 `deploymentReadiness`의 같은 검사 정책을 사용합니다. 화면은 현재 서버의 실행 환경, CLI는 Next 운영 환경변수 우선순위로 읽은 환경을 검사합니다. 서로 다른 배포 환경에서 실행하면 결과가 달라질 수 있습니다. CLI도 비밀값을 출력하거나 원격에 접속하지 않으며, `--strict`는 FAIL이 있을 때 종료 코드1을 반환합니다.

| 상태 | 의미                                                                                           |
| ---- | ---------------------------------------------------------------------------------------------- |
| PASS | 해당 설정 형식의 조건을 충족합니다. 실제 연결·권한·승인 성공을 뜻하지 않습니다.                |
| WARN | 선택 연동이 미설정이거나 별도 운영 확인이 필요합니다. 출시 준비가 모두 끝났다는 뜻이 아닙니다. |
| FAIL | 부분 설정·잘못된 형식 또는 운영 환경에서 피해야 할 개발 접근 등이 있습니다.                    |

현재 로컬 개발 설정의 인증·HTTP·DB·Worker 관련 FAIL은 실서비스 환경을 준비하지 않았다는 뜻입니다. 로컬 CRUD 검사 실패와 구분합니다. 검사 페이지를 열어도 환경변수를 고치거나 외부 기능을 활성화하지 않습니다.

## 확인하는 범위

- 로컬 테스트 접근 해제, 서비스 HTTPS 원본 주소, Supabase 인증 공개키 형식
- 실행 DB 연결·SSL 형식과 마이그레이션 역할 분리 조건, 조회수 서명 키 존재
- 공지방 Redis 주소·TLS 형식, 알려진 비밀키가 공개 환경변수에 들어간 경우
- private Storage 설정 형식, 행사 결제·외부 승인·자료 결제의 부분 설정
- VAPID 키 쌍 형식과 별도 알림 Worker 모드
- AdSense 미설정·사이트 확인 전용·광고 활성화 설정의 구분

인증 공개키는 `sb_publishable_` 형식 또는 기존 `anon` JWT 형식만 허용합니다. 공백·제어문자·임의 문자열·`sb_secret_`·관리자 JWT는 거부합니다. 레거시 JWT의 서명 진위는 Supabase에서 확인해야 합니다. 알려진 공개 비밀값 검사는 비밀 정보가 전혀 없음을 증명하는 전체 보안 감사가 아닙니다.

AdSense는 ID가 없으면 WARN, 유효한 게시자·공개 도메인으로 사이트 확인만 준비한 상태도 활성화 대기 WARN입니다. 명시적 활성화와 올바른 본문 광고 단위까지 있으면 설정 형식 PASS를 표시합니다. 잘못된 ID·부분 설정·알 수 없는 활성화 값은 FAIL입니다. 이 판정은 배포 예정인 production 설정을 정적으로 해석할 뿐 실행 환경을 바꾸거나 Google 광고를 요청하지 않습니다. 실제 사이트 승인·게재·CMP는 [AdSense 설정](ADSENSE_SETUP.md)을 따라 별도 확인합니다.

## 현재 구현과 다음 운영 확인

마이그레이션은 `0000`부터 `0066_event_private_contacts`까지 journal의 **67개 항목을 순서대로** 적용합니다. 현재 `sliper` 스키마는 **80개 테이블**입니다. F2 복원 검사 당시 대조한 **전체81개**는 당시 앱 79개와 인증·마이그레이션 관리 테이블을 포함한 수입니다. 신규 연락처 테이블 추가 후의 전체 복원은 그 과거 결과에 포함되지 않습니다.

F2에서 미첨부 사진·ready 영상의 **30일 보관**, 첨부 경쟁을 보호하는 PostgreSQL 정리 원장, 읽기 전용 관리자 점검과 명시적 CLI 실행을 구현했습니다. `npm run media:cleanup`은 미리보기이고 `-- --apply`를 붙여야 정리합니다. 자동 스케줄은 아직 없습니다. 게시글·행사 기록·출처 파일·프로필의 제외 조건과 재시도는 [F2 안내](COMMUNITY_APPEALS_RETENTION_AND_RESTORE.md)에 정리했습니다.

암호화 로컬 DB·미디어 백업과 원래 DB를 덮어쓰지 않는 별도 복원은 실제로 검증했습니다. 원격 Supabase DB·객체 저장소의 백업/복원, 운영 키의 별도 보관과 복구 목표 시간은 아직 검증하지 않았습니다. 로컬 복원 도구를 운영 복구 도구로 간주하지 않습니다.

실서비스 준비의 다음 순서는 다음과 같습니다.

1. Supabase·HTTPS 도메인·실행/마이그레이션 역할과 private Storage를 준비하고 전체 마이그레이션을 적용합니다.
2. 두 실제 회원으로 카카오/구글 왕복 로그인·가입·권한 분리와 사진/영상 저장·재생을 확인합니다.
3. 외부 결제·승인·환불·정산의 회원/거래 연결과 중복/역순 알림을 검증합니다.
4. 운영 Worker·Redis 전달·장애 복구, Android와 iPhone 홈 화면의 푸시·QR·영상·지도를 직접 확인합니다.
5. 원격 복원·정리 자동 스케줄·장애 감시·운영 연락/대응 절차를 마련하고 제한 베타·다중 사용자 부하를 측정합니다.
6. 실제 AdSense 계정·도메인 승인 후 광고 단위와 표시·개인 화면 제외·CMP를 확인합니다.

실제 OAuth, private Storage, 거래·환불·정산, 기기 수신·화면 조작, 부하, 원격 복원, AdSense 승인은 이 정적 검사에 포함하지 않습니다. [실서비스 연결 절차](PRODUCTION_INTEGRATION.md)와 [전체 현황](PROJECT_STATUS_AND_ROADMAP.md)을 함께 확인하세요.

## Supabase 입력 준비와 실제 DB 검사

프로젝트 URL과 키 이름을 `.env.supabase.local`에 준비했다. 빈 비밀값은 사용자가 직접 입력하며 현재 로컬 `.env`는 유지한다. [입력 안내](SUPABASE_CONNECTION_PREPARATION.md)를 따른다. 별도 `npm run deploy:db-check -- --env-file .env.supabase.local --json --strict`는 명시한 DB의 실제 카탈로그·역할·RLS·마이그레이션을 읽기 전용으로 확인한다. 기존 화면/API/`deploy:check`의 configuration-only 의미는 그대로다. [실제 DB 검사의 범위와 한계](PRODUCTION_DATABASE_AUDIT.md)를 확인한다.
