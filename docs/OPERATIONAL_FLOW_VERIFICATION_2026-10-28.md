# 운영 흐름·안드로이드 검증 — 2026-10-28

## 결과와 범위

우선순위 1·2의 검증을 진행했다. 운영 서버의 신청·담당자 승인·공지방·QR 권한과 이미지/영상 처리를 확인했고, 사용자는 안드로이드에서 실제 댓글 답변·공지 알림 수신 및 공지방 이동을 확인했다. 회고·경력·포트폴리오·검색의 후반 흐름은 분리된 로컬 PostgreSQL에서 검증했다. 운영 서버의 전체 행사 완료 흐름을 모두 확인한 것으로 표시하지 않는다.

정기 백업 자동화와 별도 보관처 설정은 계속 보류한다.

## 운영 서버에서 확인한 내용

- Supabase가 실제 발급한 서로 다른 5개 테스트 회원 세션을 사용했다. 운영 인증 우회·테스트 쿠키·인증 제공자 설정 변경은 하지 않았다. OAuth 성공은 기존 사용자의 Google/Kakao 확인 결과와 구분한다.
- 이메일 테스트 계정은 OAuth 콜백을 거치지 않으므로 테스트 회원에게만 콜백과 동일한 빈 프로필을 준비한 뒤 실제 기본정보 API를 호출했다. 분석 제외 표시를 설정했다.
- 공개 모집 알림을 막기 위해 샘플 글로 표시한 뒤 번개 설정을 준비했다. 실제 번개 개설 UI 전체를 검증한 결과로 해석하지 않는다.
- 필수 질문 누락 거절, 신청서 버전 확인, 프로필의 닉네임·연락처 자동 반영, 반복 신청 시 신청 ID 보존.
- 승인 대기 상태에서는 공지방 접근 불가, 담당자 반복 승인으로 중복 확정되지 않음, 정원 초과 승인 거절.
- 주최자를 포함한 멤버 수·닉네임 표시, 참가자 발송 거절, 담당자 공지 조회.
- 타인 신청 취소 거절, 취소 즉시 공지방 접근 회수, 무료 번개 결제 주문 0건.
- 타인 QR 조회·자기 QR 승인 거절, 담당자의 반복 QR 확인 시 최초 입장 시각 보존, 입장 집계 1명.
- 행사 종료 전 완료 요청 거절.
- 합성 이미지의 WebP 압축·Supabase private Storage 저장.
- 2초 합성 영상의 실제 업로드·별도 운영 영상 워커 변환·Supabase 저장·Range 206 응답.
- 미첨부 이미지/영상은 업로더만 미리보기 가능. 타인 GET과 비회원 HEAD는 404.

운영 검증 도구에 기록된 성공 확인은 46개다. 반복 준비 단계의 확인도 포함하므로 독립 테스트 시나리오 수와 동일하지 않다.

## 사용자가 확인한 실제 알림

1. 본인 계정으로 별도 샘플 모임 신청·댓글 작성.
2. 담당자 승인 후 댓글 답변과 공지 생성.
3. 안드로이드 알림 센터에서 두 알림 수신 확인.
4. 공지 알림을 눌렀을 때 해당 공지방 이동 확인.

서버의 `sent`는 푸시 제공자의 수락을 의미한다. 이 경우에는 별도로 사용자 수신·이동 확인까지 받았다. 전송 내역의 여러 건은 회원의 여러 기기 구독을 포함하므로 휴대폰 수와 같지 않다.

## 분리된 DB에서 확인한 후반 흐름

기존 로컬 전용 `127.0.0.1:55432/sliper_dev`에 누락된 최신 마이그레이션을 적용한 뒤, 운영 `.env`를 바꾸지 않고 기존 `tests/records.integration.ts`를 실행했다. 2개 통합 검사가 통과했다.

- QR 1명·담당자 확인 1명·미참석 1명 → 참가 2명, 확인 방식별 1명.
- 완료 처리 → 회고 저장·회원 공개 → 제작진 수락 → 포트폴리오 → 회원 검색.
- 비회원·차단·회고 공개 철회·직접 미디어 권한, 전적 변경 및 역할 중복 집계 방지.
- 서로 다른 DB 연결의 동시 완료 실행에서 초안 1개와 최초 완료 담당자·시각 보존.

운영 DB의 샘플 행사 시각을 직접 바꾸고 샘플 표시를 잠깐 해제해 후반을 검증하려던 실행은 자동 승인 검토가 실제 회원 노출 위험을 이유로 거절했다. 해당 실행은 수행되지 않았고 해당 절차는 로컬 도구에서 제거했다. 운영 행사·회고·후기·경력·공개 검색 기록을 이 방식으로 추가하지 않았다.

## 발견한 지도 결함과 수정

모바일 탐색 메뉴에서 `/map` 이동 시 네이버 인증 거부 콜백이 발생했다. SDK가 내부 상태를 정리한 뒤 Sliper가 다시 리스너를 제거하면서 `Cannot read properties of null (reading 'isArray')` 예외가 발생해 오류 안내 전에 페이지가 중단됐다.

`NaverMapSession.dispose()`가 각 자원을 독립적으로 정리하고, SDK가 이미 파괴된 경우에도 남은 정리와 오류 안내를 계속하도록 수정했다. 반복 정리·늦은 이벤트·타이머 중단 정책을 유지한다. 동일 예외를 던지는 회귀 검사는 수정 전 실패·수정 후 통과했다.

- 지도 집중 검사 9개 통과.
- 비밀값 검사·포맷·타입·전체 1,094개 검사·마이그레이션 검사 통과.
- 운영 적용 및 적용 후 브라우저 결과는 아래 최신 상태에 기록한다.

네이버 인증 거부는 운영 주소 등록 후 해소됐다. 사용자가 Web 서비스 URL을 저장한 뒤 지도 타일 표시를 확인했다. 주소 변환은 Geocoding 항목이 꺼져 있어 별도로 403을 반환했으며, 사용자가 활성화한 뒤 실제 Geocoding HTTP 200·공개 주소 결과 1건을 확인했다. 공식 가이드는 포트·경로를 제외한 호스트 등록, http/https 미구분을 안내한다. [Application 설정](https://guide.ncloud-docs.com/docs/application-maps-app-vpc), [지도 인증 문제 해결](https://guide.ncloud-docs.com/docs/maps-troubleshoot), [현재 ncpKeyId 파라미터](https://navermaps.github.io/maps.js.en/docs/tutorial-1-Getting-Client-ID.html).

## 성능 측정에서 확인한 후속 과제

테스트 계정으로 실제 관리·신청 API를 순서대로 호출한 표본에서 성공 응답 40건의 중앙값은 약 5.32초, 최대는 약 9.05초였다. 목록 전체나 동시 사용자 부하 측정 결과는 아니다.

Ncloud 서버에서 가벼운 `SELECT 1` 5회의 왕복 지연은 208~209ms, 공개 Supabase 인증 설정 요청 3회는 234~438ms, 로컬 웹 health는 5~6ms였다. 순차 DB 왕복이 많은 관리 흐름에서 지연이 누적될 가능성을 뒷받침하지만, 정확한 쿼리별 시간·대기열 분석은 아직 하지 않았다. 우선순위 4에서 쿼리 횟수와 트랜잭션·권한 조회를 측정하고, 민감한 데이터를 공개 캐시에 넣지 않는 방식으로 개선한다.
