# Supabase 전환 후 응답 속도 추가 개선 — 2026-10-17

## 원인과 수정

현재 클라우드 DB는 시드니 리전에 있다. 준비된 연결에서도 단순 왕복 약 155~180ms가 걸렸다. 읽기 전용 EXPLAIN에서 실제 쿼리 실행은 대부분 1ms 이내였다. 이번 데이터 규모에서는 인덱스 누락이나 DB 계산보다 요청마다 여러 차례 DB를 왕복하는 구조가 주된 병목이었다.

- 목록은 개수 조회 → 기본 섹션 조회 → 이미지·영상·투표·인증 후기 보강을 기다렸다. 이제 각 게시글의 권한 확인과 메타데이터를 같은 SQL에서 처리하고, 일반/추천/인기/예정 목록은 각자의 필터·정렬·개수 제한을 유지한 UNION ALL로 한 번에 읽는다.
- UNION의 반환 순서에 의존하지 않고 각 분기의 순위 번호로 다시 정렬한다. 이미지·영상 순서와 회원별 투표·차단·운영 숨김 검사를 유지한다.
- 첫 페이지의 개수 조회와 데이터 조회는 병렬로 실행한다. 2페이지 이상은 개수를 먼저 읽어 범위를 조정한 뒤 조회해 과도한 offset을 막는다.
- 상세의 본문과 첫 댓글 목록은 병렬로 읽는다. 댓글 SQL도 부모 게시글의 공개·차단·숨김을 확인한다. 별도 댓글 API의 부모 확인은 유지한다.
- 공통 메뉴와 로고를 클릭할 때 로컬 필터 변경 API와 Next 페이지 이동이 동시에 일어나던 중복 요청을 제거했다.
- 루트 loading.tsx로 이동 중 즉시 로딩 상태를 표시한다. 첫 로딩 응답과 데이터 완료 시간은 구분해 측정했다.

요청을 넘는 회원 데이터 캐시, 인증 생략, RLS 완화, 리전 이전이나 인덱스 변경은 적용하지 않았다. Redis를 목록 캐시로 추가하지 않았다. 공지방 갱신은 기존 Supabase private Broadcast를 유지한다.

## 동일 데이터로 비교한 수치

익명, 게시글 1개인 시점에 같은 서비스 호출을 측정했다. 변경 후 숫자는 준비된 연결의 중앙값이다. 실제 로그인 회원·운영 트래픽·모바일 실기기의 성능 보장은 아니다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 홈 feed 서비스 | 974ms | 357ms |
| 홈 feed SQL | 9회 | 2회 |
| 게시글 상세 서비스 | 1,254ms | 326ms |
| 게시글 상세 SQL | 7회 | 2회 |
| 추천·인기·예정 갱신 SQL | 3회 | 1회 |

별도 반복 HTTP 측정에서 홈 전체 응답은 579~627ms, 이야기 546~561ms, 목록 API 383~425ms, 상세 API 350~383ms였다. loading 스트리밍으로 홈의 첫 헤더는 129~175ms에 받았으며, 이를 데이터 조회 완료 시간으로 계산하지 않았다.

새 DB 연결은 여전히 약 1.5초 걸렸고 개발 모드 첫 컴파일도 별도다. 서버와 DB의 리전 배치, 실제 회원 요청과 부하 검증은 운영 배포 전에 추가 측정해야 한다. [Ncloud 배포 준비](NCLOUD_DEPLOYMENT.md)를 참고한다.

## 검증과 근거

- 속도 수정 당시 전체 검사 960개, TypeScript·비밀값·서식·Drizzle 및 webpack 운영 빌드와 서버 trace 110개가 통과했다.
- 투표 총계/회원 선택 분리, 이미지·영상 순서, 비회원·차단·숨김, 커서/번호 페이지와 UNION 결과가 뒤섞여 도착하는 경우를 검사했다.
- Chrome와 Android 화면 에뮬레이션에서 메뉴·로고·모달, 초기 중복 목록 요청 0건, 비회원 푸시 설정 요청 0건을 확인했다.
- 이 수치는 기존 글 복원 전에 비교한 결과다. 복원 후 데이터 24개에 대한 화면·HTTP 확인은 별도로 기록한다.

Git 제외된 `.local/`의 `performance-baseline-20261017.json`, `performance-after-20261017.json`, `performance-http-20261017.json`, `performance-browser-20261017.json`에 측정 결과를 보관했다. SQL 매개변수·사용자 본문·비밀값은 측정 결과에 출력하지 않았다.

관련 구현: `src/server/post-reader.ts`, `src/server/post-metadata-sql.ts`, `src/server/community-service.ts`, `src/app/loading.tsx`, `src/components/sliper-community.tsx`.


## 복원 후 최종 확인

공개 글 24개(기존 새 글1개+복원23개)로 읽기 전용 측정을 다시 실행했다. 준비된 연결의 홈 서비스 중앙값은492ms, 상세313ms였으며 SQL은각2회였다. 해당 SQL의 실제 실행은 최대약1.95ms였다. 이 수치는 DB 서비스 호출 기준이며 사진 다운로드나 브라우저 전체 표시 완료 시간을 뜻하지 않는다.

최종 소스의 `npm run check`는 **968/968**, 비밀값·서식·타입·Drizzle 검사가 통과했다. 격리된 동일 소스의 webpack 운영 빌드, 서버 trace110개·오류0개와 standalone 파일2512개·비밀 파일0개·영상 워커 파일0개를 확인했다. 실제 Chrome/Android 화면 에뮬레이션20개 동작에서 복원된 목록·2페이지·모달·메뉴가 통과했고 JS 오류와 불필요한 목록 API는0건이었다. 실제 Android 단말·실제 회원 세션·부하 검사는 별도다.

최종 로그는 `.local/performance-and-restore-final-check-20261017.log`, `.local/performance-and-restore-final-build-20261017.log`이며, 복원 후 측정은 `.local/performance-restored-20261017.json`이다.
