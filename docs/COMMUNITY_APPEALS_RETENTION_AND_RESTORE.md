# F2 — 이의신청·미디어 보관·로컬 복원

2026-10-14 · 신뢰 운영 F1의 후속 구현입니다. 실서비스 공개, 원격 Supabase 연결, 실제 휴대폰 검증은 별도 단계입니다.

## 내 운영 조치와 이의신청

`/settings/appeals`에서 본인에게 적용된 경고·이용 제한·콘텐츠 숨김과 그 조치에 연결된 신청을 확인합니다. 계정·안전 설정과 일반 문의 화면에서 진입합니다. 일반 회원의 다른 신고·문의는 기존 흐름을 유지합니다.

- 원조치 ID를 기존 문의에 연결합니다. 회원과 원조치의 조합마다 문의는 하나만 만들며 반복 접수로 원래 내용을 덮어쓰지 않습니다.
- 추가 의견은 같은 문의의 답변 이력에 이어지고 다시 미처리 상태로 전환됩니다. 버전을 비교해 동시에 작성한 의견이나 운영 답변을 덮어쓰지 않습니다.
- 이용 제한 중인 회원도 본인 신청을 조회·접수할 수 있습니다. 탈퇴한 계정과 다른 회원의 조치는 차단합니다.
- 원조치 담당자와 신청 당사자는 자신의 재검토를 담당·처리·답변할 수 없습니다. 독립적인 활성 운영자가 처리하며 담당·검토·목표 기한은 기존 통합 처리함을 사용합니다.
- 회원에게는 조치 종류·범위·시각·일반적인 설명만 표시합니다. 신고자·담당자·증거·운영 내부 자유문구를 포함하지 않습니다. 회원 계정 상태와 신고 결과의 내부 사유도 일반적인 안내로 바꿨습니다. DB와 운영 화면의 원래 증거·사유는 보존합니다.
- 운영팀의 답변과 회원의 추가 의견을 구분합니다. 통합 처리함의 최근 응답은 운영팀 답변을 기준으로 표시합니다.

기존 자료 거래 분쟁은 구매 원본과 기존 분쟁 흐름을 계속 사용합니다. 자동 제재 해제나 새 운영 알림 발송은 추가하지 않습니다. 오래된 일반 문의를 임의로 새 조치에 연결하지 않습니다.

프로필 안내도 활동점수·참가 확인·제작 경력·매너 평가의 의미를 구분합니다. QR 참가 확인과 매너 온도를 신원 인증이나 안전 보장으로 표현하지 않습니다.

## 미첨부 사진·영상은 30일 보관

사용자가 선택한 30일 정책을 적용했습니다. 처음 업로드한 미첨부 파일은 정책 적용/업로드 시각부터, 글에서 떼어낸 파일은 마지막 첨부 해제 시각부터 계산합니다. 기존 미첨부 파일에는 마이그레이션 적용일부터 새 30일 유예를 줍니다. 글쓰기 편집기에 이 기준을 안내합니다.

게시글·행사 기록에 연결된 파일, 기록에서 사용했던 출처 파일, 프로필 사진은 이 정리 대상에서 제외합니다. 영상 원본과 미공개 변환 결과의 기존 Worker 정리 기준은 별개로 유지합니다. 계정·거래·감사 기록의 일괄 파기는 이 명령의 대상이 아닙니다.

`/admin/media-retention`은 활성 관리자 전용의 읽기 전용 집계입니다. 파일 이름·소유자·키를 제공하지 않고 조회로 파일을 삭제하지 않습니다.

```sh
# 기본값은 미리보기. 파일과 DB를 바꾸지 않음
npm run media:cleanup
# 별도로 정리를 실행. 최대 50개 작업을 처리
npm run media:cleanup -- --apply
```

자동 스케줄은 아직 등록하지 않았습니다. 운영 환경에서는 이 명령을 신뢰된 관리 프로세스로 실행합니다. 관리자 화면에 삭제 버튼을 두지 않습니다.

정리는 PostgreSQL의 `media_retention_jobs` 원장에서 관리합니다. 대상 행을 잠그고 부모 연결 여부를 확인한 뒤 파일을 비공개 대기 상태로 예약합니다. 예약한 파일은 다시 첨부하거나 공개 상태로 되살릴 수 없습니다. 실제 저장소 삭제는 DB 트랜잭션 밖에서 수행하며 성공 시 원장에 완료를 남깁니다. 삭제 후 원래 자산 메타데이터를 지우지 않습니다.

120초 임대와 작업별 토큰으로 중복 완료를 막습니다. 저장소 실패는 30초부터 지수적으로 재시도하고 최대 5회 후 실패로 보관합니다. 실패 원문과 비밀 주소는 저장·노출하지 않습니다. 이미 없는 파일의 삭제는 멱등적으로 처리하며, 마지막 시도의 임대가 만료된 작업이 다른 작업의 처리를 막지 않습니다. 로컬 경로는 UUID 파일명과 저장소 경계·심볼릭 링크를 검사합니다.

## 암호화된 로컬 백업과 분리 복원

아래 도구는 개발용 `127.0.0.1:55432/sliper_dev`만 지원합니다. 실제 운영 DB나 Supabase 객체가 포함된 환경은 거절하며, 운영 복구 검증을 대신하지 않습니다.

```sh
# 먼저 이 프로젝트의 웹 서버와 쓰기 Worker를 중지
npm run backup:local -- --quiescent
# 위 명령이 출력한 백업 ID 사용
npm run backup:verify -- --backup=출력된백업ID --quiescent
```

`--quiescent`는 서버·Worker·다른 쓰기를 멈췄다는 실행자의 확인입니다. 이 플래그가 임의의 외부 프로세스를 자동으로 중지하지는 않습니다. 캡처 전후 DB 전체 내용·시퀀스와 파일의 목록·해시도 비교해 캡처 중 변경을 거절합니다.

백업은 `.local/backups/백업ID`, 키는 별도의 `.local/backup-keys/백업ID.key`에 저장합니다. DB 덤프는 평문 임시 파일 없이 암호화 스트림으로 저장하고 미디어도 파일별 AES-256-GCM으로 암호화합니다. HKDF로 용도별 키를 구분하고 manifest는 HMAC으로 인증합니다. Windows의 폴더 ACL도 현재 사용자·SYSTEM으로 제한합니다. 비밀키는 로그나 manifest에 넣지 않습니다. `.env`와 테스트 계정 파일, PostgreSQL 데이터 디렉터리 전체는 묶지 않습니다.

백업에는 `.local/uploads`, `profile-photos`, `video-sources`, `videos`의 허용된 파일만 포함합니다. 연결된 필수 파일이 없으면 실패하며, 30일 정리로 삭제된 영상의 보존 메타데이터는 정상적인 정리 상태로 판별합니다. 제한은 파일 20,000개 미만, 미디어 8GB, DB 덤프 2GB, 전체 10GB입니다.

복원은 전체 manifest·암호문 해시·인증 태그·평문 해시를 검증한 뒤에만 새 `sliper_restore_*` DB를 만듭니다. 원래 DB의 초기화·삭제·덮어쓰기 경로는 없습니다. 미디어는 `.local/restores/새DB명`에 분리하고 전체 테이블·시퀀스 내용과 행사/신청/공지방/QR/자료 버전 관계를 비교합니다. 성공 시 그 폴더의 `verified.json`에 집계만 기록합니다. 원문·연락처·키를 출력하지 않습니다.

복원된 작업 원장은 보존하지만 Worker를 시작하거나 대기 푸시를 재발송하지 않습니다. 성공 시 복원용 임시 평문 덤프만 삭제하고 복원 DB·미디어는 점검을 위해 남깁니다. 실패한 분리 대상도 원본을 건드리지 않고 남깁니다.

로컬 디스크와 같은 PC에 있는 키는 개발 리허설용입니다. 실제 운영에서는 암호화 백업과 키를 별도의 안전한 저장소에 보관하고 접근·보관 기간·정기 복원 책임자를 정해야 합니다. 환경 비밀 설정을 백업에 포함하지 않으므로 별도의 안전한 복구 수단이 필요합니다.

## 데이터와 검증

마이그레이션 0061·0062는 원조치 링크·중복 방지·소유권·중립 운영자 보호를, 0063·0064는 미첨부 시각·정리 원장·첨부 경쟁 보호를 추가합니다. 기존 참가·결제·감사·글 내용은 재작성하지 않습니다. Redis 역할은 계속 공지방 갱신 힌트이며 이의신청과 정리 원본은 PostgreSQL입니다.

최종 실제 검증 결과와 다음 단계는 [전체 현황](PROJECT_STATUS_AND_ROADMAP.md)에 기록합니다. 다음 준비는 운영 인증·private Storage·외부 결제/환불 계약·HTTPS·별도 Worker와 실제 Android/iPhone 사용 흐름입니다. 사용자 관찰과 운영 부하는 코드 검사와 구분합니다.
