> 후속 상태: 사용자 승인 후 20개 정리 완료. 디스크 95% → 38%. 실행 결과는 [정리 완료 보고서](DISK_RELEASE_CLEANUP_2026-10-31.md)를 참고하세요. 아래 내용은 실행 전 조사 기록입니다.

- 조사 시각: 2026-10-31 00:16–00:25 KST
- 대상: contenido-v1 / 211.188.59.204 / Ubuntu 20.04.6 / `/dev/xvda1` ext4
- 수행 범위: SSH 읽기 전용 조사 및 로컬 보고서 작성
- 상태: **운영 서버의 파일 삭제·서비스 시작/중지/재시작·설정 변경·링크 전환을 수행하지 않음. 정리는 사용자 승인 대기.**

## 1. 결론

디스크 증가의 주원인은 이전 배포 디렉터리의 누적이다. 완료 릴리스 19개와 `.building` 4개, 총 23개가 남아 있다. 각 완료 릴리스에는 전체 의존성 및 빌드 캐시를 담은 `worker`와 별도로 복사한 웹 런타임 `standalone`이 함께 보존되어 있다.

이전 배포 과정에 완료 릴리스의 보존 개수 상한이 없어 누적되었다. 일부 실패 빌드의 의존성·캐시 정리만으로는 전체 릴리스 증가를 막지 못했다. 서버의 사용자 콘텐츠가 32GiB 증가한 것으로 볼 근거는 발견되지 않았다.

현재 웹과 실제 워커가 서로 다른 릴리스를 사용한다. 따라서 `current`와 직전 릴리스만 남기는 단순 정리는 위험하다. 아래 **3개를 보존하고 20개를 정리하는 안**을 권장한다. 실행 직전에는 프로세스·심볼릭 링크·마운트·정리 대상의 변경을 다시 검사해야 한다.

## 5. 무엇이 용량을 차지하는가

완료 릴리스의 전형적인 구조:

```text
release/
├── artifact-audit.json (초기 릴리스는 native-artifact-audit.json)
├── standalone/                 # 실제 웹 런타임: 약 109~131MiB
│   ├── server.js
│   ├── node_modules/           # 추적된 런타임 의존성 복사본: 약 71MiB
│   └── .next/cache -> /var/lib/sliper/web-cache
└── worker/                     # 전체 소스 + 전체 의존성 + 전체 웹 빌드
    ├── SLIPER_RELEASE_MANIFEST.json
    ├── node_modules/           # 릴리스마다 약 900MiB
    └── .next/
        ├── cache/              # 존재하는 경우 약 616~640MiB
        └── standalone/        # 최상위 standalone과 별도의 런타임 사본

미완료 릴리스.building/
└── source/                     # 현재 남은 4개는 소스·manifest 등 약 21~22MiB
```

- 전체 릴리스의 모든 `node_modules` 사본 합계: 약 **19.338GiB**.
- 전체 릴리스의 물리적 빌드 캐시 합계: 약 **9.871GiB**. 위 node_modules 합계와 중복되지 않는다.
- 큰 개별 파일: webpack `server-production/0.pack` 약 395~407MiB, `client-production/0.pack` 약 152~160MiB, Next SWC 네이티브 바이너리 각각 약 94~96MiB, ffmpeg/ffprobe 각각 약 75~76MiB.
- `worker/.next`에는 웹 빌드와 중간 standalone 사본이 남아 있어 실제 워커 실행에 필요한 것보다 넓은 산출물을 릴리스마다 보관하고 있다.
- 일부 릴리스의 빌드 캐시는 이전에 정리되어 크기가 약 1.15GiB다. 나머지 완료 릴리스는 디렉터리 블록 포함 약 1.74~1.79GiB다.
- `scripts/native-build-source.sh`는 매번 `npm ci --include=dev` 후 webpack 빌드를 수행한다. 최신 배포 스크립트는 링크 전환/웹 상태 확인/실패 시 롤백을 제공하지만 완료 릴리스 보존 개수 제한은 없다.

## 6. 데이터·링크·파일 보호 확인

- 파일 인벤토리에서 릴리스 간 공유 하드링크 0개, 외부 링크 수가 남는 하드링크 0개. 복사본들이 실제 독립 블록을 차지한다. 외부 공용 블록을 회수할 수 있다고 잘못 계산한 결과는 아니다.
- 모든 심볼릭 링크를 추가 검사했다. 릴리스 외부를 가리키는 링크는 각 완료 릴리스의 `standalone/.next/cache -> /var/lib/sliper/web-cache`뿐이었다. 이 링크의 **대상 디렉터리는 유지**해야 하며, 정리 시 링크를 따라가면 안 된다. 현재 웹도 동일한 공용 캐시를 사용한다.
- 릴리스 내부에서 별도 파일시스템 경계나 중첩 마운트는 발견되지 않았다. 승인 후 실행 직전 `/proc/self/mountinfo`까지 재검증해 bind mount도 차단한다.
- 소스 manifest 23개 모두 검사한 해시와 일치하며 누락 소스가 없다. 빌드가 생성한 `next-env.d.ts`의 차이는 별도 분류했다.
- node_modules·빌드 산출물을 제외한 경로에서 업로드/스토리지/백업/DB 디렉터리명, DB 확장자, `.env*`, 키 파일 등 의심 경로를 조사했고 해당 패턴은 발견되지 않았다. 패턴 검사는 내용의 완전한 데이터 분류를 보장하지 않으므로 정리 직전에도 변경 여부를 검사한다.
- `/var/lib/sliper`, `/etc/sliper`, `/opt/sliper/runtime`, `/opt/sliper/incoming`, `/opt/sliper/ops`, 실제 업로드·스토리지·백업·MongoDB 등 DB 경로는 정리 대상에서 제외한다. DB 접속이나 데이터 변경은 하지 않았다.
- `/proc` 전체에서 삭제됐지만 열린 일반 파일은 임시 shell heredoc 파일 1개, 할당량 **8KiB**뿐이었다. 이번 조사 명령의 임시 파일 형태로 보이며 대량 미회수 파일의 증거가 아니다. 이 조사에서 프로세스 접근 권한 오류는 없었다.

## 7. 프로세스 매니저·프록시·예약 작업 확인

- Sliper는 systemd 관리다. 웹·알림·영상 서비스는 active/running이다. PM2는 기존 별도 사이트의 프로세스다. PM2 저장 메타데이터도 `/root/Contenido_website`를 참조한다. 저장 상태는 실시간 상태로 해석하지 않았고, PM2 명령으로 새 데몬을 시작하지 않았다.
- Nginx 도메인 설정은 `sliper.kr`의 요청을 loopback 13001로, `/ops/health`를 13002로 전달한다. 릴리스 디렉터리를 직접 정적 root로 사용하지 않는다. 설정 검사 성공, 재로드는 하지 않았다.
- IP HTTPS는 별도 `sliper-tls.service`/Caddy 프로세스다. Caddy 설정에도 이전 릴리스의 절대 경로 참조가 없다.
- systemd 단위/드롭인, cron 디렉터리, Sliper ops 스크립트에서 이전 릴리스의 절대 경로 고정 참조를 찾지 못했다. 조사 시 Sliper 예약 작업은 상태 점검과 도메인 인증서 갱신이었다. 릴리스 자동 보존/정리 타이머는 발견되지 않았다.
- 조사 중 `https://sliper.kr/ops/health`, `https://sliper.kr/api/health`, 기존 사이트 `http://127.0.0.1:3000/` 모두 HTTP 200을 확인했다. 전체 사용자 기능을 재실행한 회귀 테스트는 아니다.

## 8. 승인 후 정리 절차 제안 — 현재 미실행

1. 이 문서의 후보 20개를 명시적으로 승인받는다. 승인 대상 경로와 조사한 소스 manifest/구조 정보를 로컬 실행 계획으로 고정한다.
2. 실행 직전 current, 모든 프로세스의 cwd/exe/fd/maps, 실행 서비스 및 설정 참조를 다시 수집한다. 후보가 새로 참조되거나 경로/파일 구성이 달라졌으면 삭제하지 않고 중단한다.
3. 각 경로가 `/opt/sliper/releases`의 직접 자식인 실제 디렉터리인지 확인한다. 보호 경로 포함·경로 이탈·심볼릭 링크 루트·별도/바인드 마운트가 있으면 중단한다. 경로 뒤 `/`를 붙여 링크를 따라가는 방식은 사용하지 않는다.
4. 활성 배포나 preview/build 프로세스가 없는지 확인하고, 정리와 동시 배포가 일어나지 않도록 작업을 조정한다. 승인된 정확한 경로만 하나씩 정리하며 임의 wildcard 삭제나 링크 대상 탐색 삭제를 하지 않는다.
5. 각 단계와 종료 후 `df`, 잔여 보존 릴리스, 기존 PID와 서비스 상태, Sliper/기존 사이트 health를 검증한다. 정리에는 서비스 재시작이 필요하지 않다. 예상 외 상태가 나오면 추가 삭제를 중단한다.
6. 실제 확보 용량·잔여 공간·서비스 상태를 별도 완료 보고서에 남긴다.

## 9. 재발 방지 권장안 — 미적용

우선순위는 다음과 같다.

1. **배포 완료 후 보존 정책**: 정상 배포 검증이 끝난 뒤 현재 웹 + 모든 실제 실행 프로세스가 참조하는 릴리스 + 직전 정상 롤백 릴리스를 합집합으로 보호한다. 보호 대상은 보존 개수 제한보다 우선한다. 단순 이름/mtime 순 N개 삭제로 구현하지 않는다.
2. **dry-run 기본값**: 정리 목록·예상 확보량을 먼저 출력하고, 한정된 릴리스 경로만 허용하는 안전 검사를 통과해야 삭제하도록 한다. 초기에는 수동 승인으로 운영하고 검증 후 자동화한다. 실패/진행 중 빌드는 배포 잠금과 나이 기준으로 따로 관리한다.
3. **배포 전후 용량 검사**: 현재 구조 기준 다음 빌드의 피크 공간을 실측하고, 임시 기본값으로 가용 6GiB 미만이면 신규 빌드를 보류한다. 80% 경고·90% 긴급 경고를 외부 이메일 감시와 연결한다. 이번 조사에서 경보 설정은 변경하지 않았다.
4. **산출물 축소**: 워커 전용 production 의존성과 웹 standalone을 분리한다. 워커 릴리스에 전체 Next 빌드/중간 standalone/컴파일 캐시/개발 의존성을 계속 보관하지 않도록 패키징을 개선한다. 실제 워커의 동적 import·ffmpeg 의존성을 검증한 뒤 적용해야 한다.
5. **워커 릴리스 추적**: web/notifications/video의 실제 릴리스와 PID를 배포 메타데이터로 기록하고, 보호 집합을 `/proc`와 함께 검증한다. 워커를 최신 릴리스로 옮기는 작업은 별도 점검·승인으로 수행한다. 이번 정리를 위해 강제로 재시작하지 않는다.
6. **로그 관리 별도 점검**: `/var` 6.3GiB 전체가 로그라는 근거는 없다. Nginx·journald·PM2 로그별 사용량과 기존 logrotate 설정을 별도로 조사한 뒤 보존 기간을 정한다. DB 파일이나 로그를 임의 삭제하지 않는다.
